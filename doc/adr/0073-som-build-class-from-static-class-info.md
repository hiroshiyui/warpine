## Context

Code generated by IBM's SOM compiler does not build a class through `somNew`, `somInitClass` and `somAddStaticMethod` calls, as Warpine's hand-written bindings do. Its `<Class>NewClass` passes one statically initialized description, `somStaticClassInfo`, to `somBuildClass(inheritVars, sci, majorVersion, minorVersion)`. The kernel builds the class from it:
- its parents and metaclass, by name;
- its static methods, whose tokens go into the class's `ClassData`;
- its overrides;
- its instance data and public data tokens;
- procedure and `va_list` entries written into `ClassData`;
- `CClassData`;
- a class init function.

Without it no IBM-built class library can make a class.

The structure has grown over layout versions 1 to 3, with `SOM_SCILEVEL` 4. Its later fields serve the initializer and destructor control blocks and DirectToSOM C++, which are left for the next stage (B2).

## Decision

### `somBuildClass`

`somBuildClass` is exported by name at 3078. Its IBM ordinal is in the unknown range above 47 (ADR-0070).

1. **Reading the structure.** Every field is read through bounds-checked guest reads. Layout versions 1–4 are accepted, and the layout-3 fields only from version 3 on. Every count is capped (`MAX_METHODS`, `MAX_PARENTS`) and the instance-data size too (`MAX_INSTANCE_DATA`). An unknown version or a missing `ClassData` raises `SOMERROR_BadArgument`.
2. **Already built.** If `ClassData.classObject` is set, that class is returned.
3. **Parents and metaclass.** Parents are found by name among the registered classes; `SOMERROR_NoParentClass` if one is missing. With none, the parent is `SOMObject`. An explicit metaclass is found by name; `SOMERROR_NoMetaClass` if it is missing. The metaclass then comes from the existing rule (`WrpSomMetaclassFor`, ADR-0060), considering the first parent's metaclass.
4. **The class object** is a new instance of the metaclass, initialized with its parents and `instanceDataSize` through the multiple-inheritance path.
5. **The tables, in this order:**
   - **`smt`:** each static method is added and its token written where `classData` points.
   - **`mt`** (layout 3): static, dynamic and nonstatic methods are all added as static ones; an override by token (action 6) replaces that method. Other actions are skipped.
   - **`omt`:** overrides by name. A scoped name (`Class::method`) is matched by its last part.
   - **`imt`** (layout 3): the method gets parent `parentNum`'s implementation, parents counted from 1.
   - **`nit`:** a data token for the field at `basisForDataOffset − nitReferenceBase` in the class's part, written where `classData` points. Offsets past the instance data are skipped.
   - **`pmt` / `vft`:** their entry is written where `classData` points.
6. **The class is made ready** and registered, and its version recorded.
7. **`ClassData` and `CClassData`.** `ClassData.classObject` is set. `CClassData.parentMtab` points to a new `somParentMtabStruct`: the class's own table, then a list of its parents' tables, the class object and the instance size, as for the root classes (ADR-0072). `instanceDataToken` is the class when it has instance data.
8. **The class init function** (`cif`), if any, is called last with the class, as a guest call; `somBuildClass` then returns the class.

### Field data tokens

`somDataResolve` now accepts a second kind of data token. A token made for a field is a small runtime-heap block naming (class, offset); `som_data_resolve` resolves it to the class's part offset plus the field offset. A class object remains the token of its whole part.

### Warpine's choices (unverified)

- **`inheritVars`** is not used: implementations are inherited from every parent.
- **Methods:** dynamic and nonstatic methods treated as static; the `mt` actions other than adding and overriding by token skipped; scoped override names matched by their last part.
- **Parents:** `imt`'s `parentNum` counted from 1; only the first parent's metaclass considered for a multiple-inheritance class with no explicit metaclass.
- **Data:** the field data token's form; `dataAlignment` and `somDynamicSCI` not used (Warpine aligns instance data to 4).
- **Order:** the class init function called after the class is ready, `ClassData` and `CClassData` filled first.
- **Not used yet:** `maxMethods`, `implicitParentMeta`, `protectedDataOffset`, `classDataEntryNames`, the migrated methods.

## Consequences

- **What works now.** A class library whose generated code calls `somBuildClass` builds its classes: their methods resolve through the tokens it wrote, parent calls go through `CClassData.parentMtab`, and public data through its data tokens. This holds for classes in DLLs that `somFindClass` loads, too.
- **The limit.** IBM-built binaries import `somBuildClass` by ordinal. Until IBM's ordinals above 47 are known (ADR-0070), only programs importing it by name reach it.
- **The entry-point count** grows from 782 to 783 (SOM: 113 implemented, 3 stubs).
- **Still open (Stage B2/B3):**
  - initializers and direct-init classes;
  - the initializer, destructor and assignment control blocks in `somParentMtabStruct`;
  - DirectToSOM classes, migrated methods and `somDynamicSCI`;
  - `somConstructClass`.
- **Tests:**
  - `som.rs`: `build_class_from_static_class_info` and `build_class_errors` (malformed, missing and oversized input);
  - `samples/som_build_test`: 18 checks, among them the DLL loaded by `somFindClass`.
