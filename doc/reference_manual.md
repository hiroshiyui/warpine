# Warpine Reference Manual

Warpine is an OS/2 compatibility layer for Linux that runs 32-bit OS/2 (LX format) and 16-bit OS/2 1.x (NE format) applications natively using KVM hardware virtualization.

## Command-Line Interface

### Usage

```
warpine <os2_executable> [--gdb <port>]
warpine --compat
warpine --licenses
```

### Arguments

| Argument | Type | Description |
|----------|------|-------------|
| `<os2_executable>` | Path | Path to an OS/2 LX or NE executable |
| `--gdb <port>` | u16 | Enable GDB Remote Stub on the given TCP port |
| `--compat` | Flag | Print API compatibility report and exit |
| `--licenses` | Flag | Print Warpine's licence and the notices and licences of the fonts built into the binary (IBM Plex, GNU Unifont), and exit |

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Guest exited normally via `DosExit()` |
| 1 | Warpine startup error (bad arguments, file not found, load failure) |
| 89 | Started past the process nesting limit (`WARPINE_DEPTH` above 8 or malformed); no guest code ran |
| 89 | No slot left under the session's `THREADS=` limit for the process's thread 1 (see [CONFIG.SYS](#configsys-threads)); no guest code ran |
| Other | Guest exit code (passed through from `DosExit()`) |

## Environment Variables

### Warpine-Specific

| Variable | Values | Default | Effect |
|----------|--------|---------|--------|
| `WARPINE_TRACE` | _(unset)_, `0`, `false` | _(unset)_ | Default pretty log format |
| `WARPINE_TRACE` | `1`, `strace` | — | Compact strace-like API call format |
| `WARPINE_TRACE` | `json` | — | JSON Lines (one object per event) |

| `WARPINE_VIO` | `window`, `fullscreen` | `window` | How a text-mode (VIO) program on a terminal is shown: in a window on the PM desktop (an "OS/2 window" session) or in the separate 640 × 400 text window ("OS/2 full screen"). | `WARPINE_HEADLESS` | any value | _(unset)_ | Run a text-mode program on the host terminal (ANSI output, raw keyboard) even when stdout is a terminal; a piped stdout is headless anyway |
| `WARPINE_CGROUP` | `off` | on | The session's cgroup (ADR-0116): a session's first process asks the systemd user manager for a scope holding the whole session, with `WARPINE_SESSION_MEMORY_MAX` (default `8G`; K / M / G / T suffixes) and `WARPINE_SESSION_TASKS_MAX` (default 8192). | `WARPINE_COUNTRY` | OS/2 country code (`1`, `49`, `81`, …) | from the host locale | Country reported by `DosQueryCtryInfo`. Without it the host locale (`LC_ALL`, `LC_CTYPE`, `LANG`) chooses, like an OS/2 installation in that language: `ja_JP` → 81, `de_DE` → 49, `C` / unset → 1. A country it names also decides the formats (date order and separator, clock, currency) and, without `WARPINE_CODEPAGE`, the codepage, whatever the host locale |
| `WARPINE_CODEPAGE` | A supported codepage (`437`, `850`, `852`, `866`, `932`, `936`, `949`, `950`, `1250`–`1258`) | from the host locale | The process codepage a program starts with (`DosQueryCp`; also the VIO screen's and new message queues' codepage). | `WARPINE_GUI_SCRIPT` | Path to a script file | _(unset)_ | Replay a scripted PM session (`click`, `rclick`, `drag`, `rdrag`, `wheel`, `drop`, `key`, `text`, `dump`, `quit` steps) for testing; combine with `SDL_VIDEODRIVER=dummy` to run without a display. On a real display, host mouse and keyboard input is ignored while the script runs. See the developer guide, "GUI regression tests" |
| `WARPINE_DEPTH` | `0` … `8` | _(unset)_ = 0 | Set by Warpine for the child processes it starts (`DosExecPgm`, `WinStartApp`, CMD.EXE): how deeply the process is nested. A process at depth 8 starts no children (`DosExecPgm` fails with `ERROR_NO_PROC_SLOTS`, `WinStartApp` with `PMERR_CANNOT_START`), and one started deeper or with a malformed value exits with code 89 at once. | `WARPINE_THREADS` | `64` … `4095` | _(unset)_: `THREADS=` of `C:\CONFIG.SYS`, else 64 | The session's thread limit, overriding CONFIG.SYS (values outside the range are clamped; a non-number is ignored with a warning). | `WARPINE_THREAD_DIR` | Path | _(unset)_: a new `$XDG_RUNTIME_DIR/warpine-threads-<uid>-<pid>` | Set by Warpine for its child processes: the session's private thread-accounting directory (mode 0700, owned by the user) |
| `WARPINE_THREAD_SLOT` | `r-<pid>-<n>` | _(unset)_ | Set by Warpine for a child process: the thread slot its parent reserved for it |
| `WARPINE_PID`, `WARPINE_PPID` | `1` … `65535` | _(unset)_: 42 and 0 | Set by Warpine for a child process: its OS/2 process id, chosen by the parent from a counter shared by the session (from 100), and the parent's id. The process reports them in `pib_ulpid` / `pib_ulppid`; a malformed value is ignored |
| `WARPINE_CLOCK` | `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM`, `YYYY-MM-DDTHH:MM:SS` (local time, years 1980–9999; a space may replace the `T`) | _(unset)_: the host's clock | The date and time the session's clock starts at: `DosGetDateTime`, `DosQuerySysInfo(QSV_TIME_LOW / QSV_TIME_HIGH)` and `WARPINE.DLL` report it, running on from there, without touching the host's clock (ADR-0039). A malformed value is reported and ignored |
| `WARPINE_CLOCK_OFFSET` | Milliseconds (signed) | _(unset)_ | Set by Warpine for a child process: its parent's clock offset from the host's (after `WARPINE_CLOCK` or `DosSetDateTime`); it takes precedence over `WARPINE_CLOCK` |
| `RUST_LOG` | Filter string | `info` | Log level: `trace`, `debug`, `info`, `warn`, `error`. Module-scoped filters supported (e.g. `warpine::loader=debug`) |

### Filesystem

| Variable | Default | Effect |
|----------|---------|--------|
| `XDG_DATA_HOME` | `$HOME/.local/share` | Base directory for the guest C: drive |
| `HOME` | _(from passwd)_ | Fallback when `XDG_DATA_HOME` is unset |

The default C: drive maps to `$XDG_DATA_HOME/warpine/drive_c/` and is created automatically. If neither variable is set, falls back to `./drive_c/` in the current working directory.

### Locale

Warpine reads the host locale to populate OS/2 `COUNTRYINFO` fields:

| Variable | Priority |
|----------|----------|
| `LC_ALL` | 1 (highest) |
| `LC_CTYPE` | 2 |
| `LANG` | 3 (lowest) |

The language/territory is parsed (e.g. `ja_JP.UTF-8` → country=Japan) and mapped to OS/2 date format, time format, separators, and currency symbol. Date format: MDY for `en_US`, YMD for `ja`/`ko`/`zh`/`hu`/`sv`/`fi`, DMY for all others. Time format: 12-hour for `en_*`, 24-hour for all others.

## Execution Modes

Warpine automatically selects an execution mode based on the executable and environment:

### PM (GUI) Mode

**Trigger:** Executable imports `PMWIN` or `PMGPI`.

- Opens an SDL window for Presentation Manager rendering.
- Main thread runs the SDL event loop; vCPU runs on a worker thread.
- Window title: `Warpine — <filename>`.
- All PM APIs (windows, menus, dialogs, graphics, clipboard) are active.

### CLI Text Mode in a PM Window (default)

**Trigger:** CLI executable (no PM imports), stdout is a terminal, `WARPINE_VIO` unset or `window`, and the program is not marked incompatible with PM windowing.

- Opens the PM desktop with the program's 80×25 text screen in a frame titled `Warpine — <filename>`, sized to the screen (it follows `VioSetMode`) and moved by its title bar.
- CP437 8×16 VGA font, CGA 16-colour palette, blinking cursor, as in the full-screen mode.
- Keys typed while the frame is active go to the program (`KbdCharIn`); the close button or a double click on the system-menu icon ends it.
- The frame has minimize and maximize buttons and a sizing border. Smaller than the screen, it shows scroll bars over it; it cannot grow past the whole screen; maximize fits it to the screen (up to the desktop); the view follows the cursor.
- The system menu (a click on its icon, Alt+Space or Shift+Esc) has Restore, Move, Size, Minimize, Maximize, Hide, Close, Window list, Help, Font Size, Scroll, Mark, Copy, Copy All and Paste. Alt+F4 / F5 / F7 / F8 / F9 / F10 / F11 close, restore, move, size, minimize, maximize and hide the window; Ctrl+Esc opens the window list.
- **Mark**, then drag over the text and Copy, puts that rectangle on the clipboard (shared with the host); a drag past the window's edge scrolls it. In Mark mode the arrows, Page Up / Down, Home / End and Ctrl+Home / Ctrl+End move a one-cell mark (starting at the text cursor), Shift with them extends it, and Enter copies it. Copy All copies the whole screen; Paste types the clipboard text into the program.
- **Scroll** ("Scrolling: " in the title) makes the same keys scroll the window's view; Esc leaves Mark or Scroll mode.
- **Font Size** lists the cell sizes 8 × 8, 8 × 12, 8 × 14, 8 × 16 (the default), 12 × 24 and 16 × 32; the window is resized for the one chosen.
- **Hide** hides the window; the window list (Ctrl+Esc, here or in another program's window) brings it back. **Help** lists these keys.
- Alt+Home switches the program to full screen and back; it keeps running.
- The mouse reaches programs that use the MOUCALLS API, in text cells.

### CLI Text Mode, Full Screen (SDL)

**Trigger:** as above with `WARPINE_VIO=fullscreen`, or a program marked incompatible with PM windowing (LX module flags).

- Fills the screen with the 80×25 character grid, scaled by whole multiples with black borders (an ordinary 640×400 window when full screen is refused). Alt+Home switches a window-compatible program to its PM window and back.
- CP437 8×16 VGA font, CGA 16-colour palette, blinking cursor.
- vCPU runs on a worker thread; main thread runs the text renderer.
- Keyboard input delivered via SDL events.

### CLI Headless Mode

**Trigger:** CLI executable and stdout is **not** a terminal (piped or redirected).

- No SDL window. VIO output rendered as ANSI escape sequences on stdout.
- CP437 high bytes (0x80–0xFF) converted to Unicode for terminal display.
- vCPU runs on the main thread.
- Keyboard input read from raw terminal (termios). When stdin is not a terminal (pipe, file, `/dev/null`), `DosRead` of stdin returns 0 bytes at end of input, and the built-in CMD.EXE exits there (`echo dir | warpine CMD.EXE`).
- No audio output (MMPM/2 and `DosBeep` are silent; `DosBeep` returns at once).
- Child processes spawned via `DosExecPgm` automatically use headless mode.
- Detection is automatic via `is_terminal()` — no environment variable needed.

## Builtin CMD.EXE Shell

Warpine includes a native Rust command shell that requires no Open Watcom compiler.

### Invocation

```bash
warpine CMD.EXE                    # Interactive session (in a window on the PM desktop)
WARPINE_HEADLESS=1 warpine CMD.EXE # Terminal/headless mode
warpine CMD.EXE /C "DIR C:\"      # Run one command and exit
warpine CMD.EXE /K "VER"          # Run one command then stay interactive
```

The shell can also be launched from within a running OS/2 application via `DosExecPgm("CMD.EXE")` or `DosExecPgm("OS2SHELL.EXE")`.

**SDL vs terminal:** When stdout is a terminal and `WARPINE_HEADLESS` is not set, the shell runs like any CLI app: in a window on the PM desktop, or in the 640×400 text window with `WARPINE_VIO=fullscreen`. Set `WARPINE_HEADLESS=1` or pipe stdout to force terminal/headless mode.

### Flags

| Flag | Effect |
|------|--------|
| `/C <command>` | Execute `<command>` and exit |
| `/K <command>` | Execute `<command>` then enter interactive mode |
| (none) | Enter interactive mode immediately |

### Line editor

The prompt shows the current drive and directory: `[C:\path] `.

| Key | Action |
|-----|--------|
| Enter | Submit line |
| Backspace | Erase last character |
| Esc | Clear the current line |
| ↑ | Previous history entry |
| ↓ | Next history entry |

| `C:` – `Z:` | `C:` | Switch the current drive. |

### Running OS/2 programs

Any token that is not a built-in is treated as a program name.
- **A bare name** is looked for in the current directory, then in each directory of the `PATH` variable.
- **A name with a drive or a directory** (`C:\BIN\TOOL`, `WORK\TOOL`) is looked for only there.
- **Without an extension,** `.EXE` is tried before `.CMD`.

```
[C:\] hello
Hello, OS/2!
```

A program runs as a child Warpine process. It starts with the shell's environment and with its current drive and directories, as every child process does (`DosExecPgm`, `WinStartApp`; ADR-0077).

### .CMD scripts

Run a `.CMD` file by typing its name (with or without the `.CMD` extension), with arguments, or using `/C`:

```
[C:\] warpine CMD.EXE /C "MYSCRIPT.CMD first second"
```

A script runs line by line, in OS/2's batch syntax (ADR-0078):
- **Shared state.** It shares the shell's environment (its `SET`s stay), output and input, so `MYSCRIPT.CMD > LOG.TXT` works.
- **Its return code** is that of its last command.
- **EXIT** ends the whole shell with its code.
- **Starting another script.** One started without `CALL` takes the script's place: the caller does not go on.
- **Limits:** scripts nest at most 32 deep, and a script is at most 4 MiB.

| Command | Effect |
|---------|--------|
| `@command` | Run the line without echoing it |
| `ECHO ON` / `ECHO OFF` | Echo each line after the prompt before it runs (on when a script starts), or not; at the prompt, show or hide the prompt |
| `ECHO` | Show whether ECHO is on |
| `ECHO.` / `ECHO.text` | Write an empty line / the text |
| `REM text`, `:: text` | A remark |
| `:label` | A label for GOTO; does nothing when reached |
| `%0`–`%9` | The script's name as typed, then its arguments (nothing past the last) |
| `SHIFT` | `%1` becomes `%0`, `%2` becomes `%1`, … |
| `GOTO label` | Go on after `:label` (matched without case); the rest of the line is not run; a missing label ends the script |
| `IF [NOT] ERRORLEVEL n command` | Run `command` if the return code is `n` or more |
| `IF [NOT] EXIST name command` | Run `command` if a file or directory matches `name` (wildcards allowed) |
| `IF [NOT] a==b command` | Run `command` if the strings are equal (case and quotes count; blanks around `==` allowed) |
| `FOR %%v IN (set) DO command` | Run `command` for each item of the set (split at blanks, commas, semicolons), `%%v` replaced by it; a wildcard item stands for the files it matches. At the prompt, `%v` |
| `CALL script [args]` | Run another script and come back |
| `SETLOCAL` / `ENDLOCAL` | Save / restore the environment and the current drive and directories; the script's end restores what is still saved |
| `PAUSE` | Write "Press any key when ready . . ." and wait for a key |

A false `IF` leaves the return code as it was. Batch commands that only make sense in a script (`GOTO`, `SHIFT`, `SETLOCAL`, `ENDLOCAL`) do nothing at the prompt.

### REXX scripts

A `.CMD` file whose first line starts with `/*` runs as REXX, in Warpine's own interpreter (ADR-0081, ADR-0083, ADR-0084):

```
/* hello.cmd */
'@ECHO OFF'
parse arg who
say 'Hello,' who
'TOOL exit 3'
say 'RC was' rc
exit 0
```

- **The language core (R1):**
  - **Numbers:** decimal arithmetic rounded to `NUMERIC DIGITS` (9 by default);
  - **Instructions:** all of REXX's (`IF`, `DO`, `SELECT`, `CALL`, `PROCEDURE EXPOSE`, `SIGNAL`, `INTERPRET`, `PARSE` with full templates, `PUSH` / `QUEUE` / `PULL`, `ADDRESS`, `NUMERIC`, `TRACE`);
  - **Built-in functions:** the string, word, conversion, number and information functions; DATE and TIME use the session clock; `VALUE(name, new, 'OS2ENVIRONMENT')` reads and sets the shell's variables.
- **Commands.** A clause that is not REXX is a command for `ADDRESS CMD`, this shell. `RC` takes its return code. While ECHO is on, the shell echoes it with the prompt, hence `'@ECHO OFF'`.
- **Routines.** A function or routine not found as a label or built-in is looked for as another REXX `.CMD` file (current directory, then `PATH`).
- **The return code.** The script's `EXIT` value, if a whole number, is its return code.
- **Errors.** An error writes the failing line and `REXnnnn: Error n running C:\NAME.CMD, line l: text`, and its number becomes the return code.
- **Conditions (R2).** `SIGNAL ON` / `CALL ON` trap ERROR (a command's non-zero return code), FAILURE (a negative one), HALT, NOTREADY (a stream), NOVALUE and SYNTAX (any REXX error, its number in `RC`); `NAME label` names another label. `CONDITION()` describes the condition last trapped.
- **Streams (R2).** `CHARIN`, `CHAROUT`, `CHARS`, `LINEIN`, `LINEOUT`, `LINES` and `STREAM` read and write files on the drives, by their OS/2 names; `STDIN`, `STDOUT` and `STDERR` (or no name) are the shell's input and output. Lines are written with CR LF. `STREAM(name, 'C', …)` takes `OPEN [READ | WRITE | BOTH] [REPLACE]`, `CLOSE`, `SEEK` and `QUERY EXISTS | SIZE | DATETIME | TIMESTAMP | SEEK`.
- **TRACE (R2).** `TRACE A | C | E | F | I | L | N | O | R` writes clauses (`    12 *-* say x`) and values (`       >>>   "42"`) to the shell's output; N (the default) shows failed commands with `+++ RC(n) +++`.
- **REXXUTIL (R2).** Registered from the start, so `call SysLoadFuncs` works as on OS/2: `SysCls`, `SysSleep`, `SysOS2Ver`, `SysBootDrive`, `SysDriveMap`, `SysFileTree`, `SysFileSearch`, `SysFileDelete`, `SysMkDir`, `SysRmDir`, `SysSearchPath`, `SysTempFileName`, with `RxFuncAdd`, `RxFuncQuery`, `RxFuncDrop` and `SysDropFuncs`. The screen, keyboard, EA, INI and Workplace Shell functions are not there (Error 43).
- **Numbers.** `NUMERIC FORM ENGINEERING` writes exponents in multiples of three (`12.3E+9`).

### Command lines

The shell follows OS/2's CMD.EXE syntax (ADR-0077). A line is processed in this order:

1. **Remarks and labels.** A `REM` line is skipped whole, `&` and `|` included, and so is a label line (`:name`).
2. **Variables.** `%name%` becomes the variable's value (names match without case; an undefined one becomes nothing), and `%%` becomes `%`. A `%` that starts no `%name%` stays, and a value is not expanded again.
3. **Commands.** The line is split at `&`, `&&` and `||`, outside quotes:

   | Syntax | Effect |
   |--------|--------|
   | `a & b` | Run `a`, then `b` |
   | `a && b` | Run `b` only if `a` returned 0 |
   | `a \|\| b` | Run `b` only if `a` returned non-zero |

   They run left to right, each looking at the return code the line has so far.
4. **Escapes.** `^` outside quotes takes the next character as it is (`echo a^&b` prints `a&b`).
5. **Groups.** `( … )` makes one command of several: `(echo a & echo b) > F.TXT`, `x && (y & z)`, `IF a==a (echo 1 & echo 2)`. Inside, `&`, `|` and redirections belong to the group; the group's return code is its last command's. Groups nest up to 64 deep.

**Return codes.** Every command leaves one:
- a program, its exit code (0–255);
- a built-in, 0, or 1 after an error message;
- a name that is no command or program, 1.

`CMD.EXE /C` ends with the return code of its command line. The host arguments of `warpine CMD.EXE …` are joined by blanks into one command line, so `warpine CMD.EXE /C TOOL exit 7` ends with 7.

### Redirection and pipes

| Syntax | Effect |
|--------|--------|
| `cmd > file` | Write the output to `file`, replacing it |
| `cmd >> file` | Append the output to `file` |
| `cmd < file` | Read the input from `file`, which must exist |
| `cmd1 \| cmd2` | Feed the output of `cmd1` to `cmd2` as its input |

- **Inside the drives.** A redirection target is an OS/2 path on a mounted drive, resolved through the VFS like any file a program opens. A path that maps to no drive (an unmounted drive, `..` above the root, a host path) is an error ("not on a drive"), and the file is not created through a dangling symbolic link (ADR-0075).
- **Programs read pipes and files.** A program reads the pipe or `< file` before it as its standard input, byte for byte, until it ends. A program with neither shares the shell's input.
- **At the same time.** Programs in a pipeline run at the same time, each reading the one before through a pipe; a program still writing when the command after it is done gets a broken pipe and ends. A built-in's or a script's output is held for the next command (at most 16 MiB). A program's return code is the last command's.
- **For one command only.** A redirection holds for its command; afterwards output and input go back to where they were.

## Virtual Filesystem

### Default Drive Mapping

| Drive | Host Path | Label | Notes |
|-------|-----------|-------|-------|
| C: | `$XDG_DATA_HOME/warpine/drive_c/` | OS2 | Auto-created; default boot drive |

Other drives (A:–B:, D:–Z:) are not mounted by default.

### CONFIG.SYS: THREADS=

Warpine reads `C:\CONFIG.SYS` (on drive C as mapped above) when a process starts; it never writes or creates the file. It uses three statements: `THREADS=` here, and [`LIBPATH=` and `SET`](#configsys-libpath-and-set) below. `THREADS=n` is the most threads the whole session runs at once, counted over all its processes (the first one and every process started by `DosExecPgm`, `WinStartApp` or CMD.EXE; each needs one thread for its thread 1).

| | |
|---|---|
| Range | 64 … 4095 (values outside are clamped; the lower bound is unverified — some OS/2 sources give 32) |
| Default | 64 (no file, or no valid statement) |
| Syntax | `THREADS=n`, keyword case-insensitive, blanks around `=` allowed; lines starting with `REM` are comments; the last valid statement wins; a value that is not a number is ignored |
| Override | `WARPINE_THREADS` (environment) |

At the limit:

| Call | Result |
|------|--------|
| `DosCreateThread` | `ERROR_MAX_THRDS_REACHED` (164) |
| `DosExecPgm` | `ERROR_NO_PROC_SLOTS` (89): no slot for the child's thread 1 |
| `WinStartApp` | fails with `PMERR_CANNOT_START` |
| CMD.EXE external command | a message; the program is not started |
| A Warpine process that finds no slot at its start | exit code 89 before any guest code runs |

Ending threads and processes give their slots back — also a process killed by a signal (its record is recognised as stale). Warpine's own limits on process nesting (`WARPINE_DEPTH`) still apply as well.

### CONFIG.SYS: LIBPATH and SET

`LIBPATH=dir;dir;…` lists the directories searched for DLLs (ADR-0092). `DosLoadModule` and a program's imports look for a module named without a path in these places, in order:

1. BEGINLIBPATH, as set by `DosSetExtLIBPATH(…, BEGIN_LIBPATH)`;
2. the program's own directory (Warpine's addition: OS/2 searches it only when LIBPATH lists it);
3. the `LIBPATH=` directories, or `C:\OS2\DLL` without the statement;
4. ENDLIBPATH, as set by `DosSetExtLIBPATH(…, END_LIBPATH)`.

In a value given to `DosSetExtLIBPATH`, `%BeginLIBPATH%` and `%EndLIBPATH%` (any case) stand for the current settings, and NULL or an empty string removes it; a value is at most 1024 bytes (`ERROR_INVALID_PARAMETER`, or `ERROR_NOT_ENOUGH_MEMORY` when the expansion makes it longer; unverified). A process starts with its parent's BEGINLIBPATH and ENDLIBPATH as they were when the parent started it; later changes on either side stay there.

Each directory is an OS/2 path on a mounted drive, with `.` meaning the current directory. Names match as they do on the drive, and an entry cannot lead outside the drives. Up to 64 directories of up to 260 bytes are used.

`SET name=value` puts a variable in the environment a program starts with when no other program gives it one. This applies to the first program of a session, a CMD.EXE nobody started, and CMD's `START` without `/I`. That environment is Warpine's base, `PATH=C:\`, `COMSPEC=C:\CMD.EXE`, `OS=OS2` and `TMP=C:\TMP`, with the `SET` statements applied in order:
- the name is upper-cased;
- a later statement replaces an earlier one;
- an empty value removes the variable;
- `%name%` is left as written.

A program started by another gets its parent's environment, as before.

Each Warpine process reads CONFIG.SYS once, when it starts, so an edit applies to programs started afterwards. On OS/2 an edit needs a reboot.

```
LIBPATH=.;C:\OS2\DLL;C:\MYAPP\DLL
SET PATH=C:\OS2;C:\MYAPP
SET HELP=C:\MYAPP\HELP
```

### Path Translation

| OS/2 Path | Resolution |
|-----------|------------|
| `C:\dir\file.exe` | Absolute drive path → host directory |
| `\dir\file.exe` | Absolute on current drive |
| `foo\bar.txt` | Relative to current drive + current directory |
| `C:foo.txt` | Relative to C: current directory |

Backslashes are translated to forward slashes. Paths cannot escape the volume root (sandbox enforced).

### Filesystem Features

- **Case-insensitive, case-preserving** lookup (optimistic stat + readdir fallback)
- **Long filenames** up to 254 characters (HPFS semantics)

- **OS/2 wildcard matching** (`*`, `?`) in `DosFindFirst`/`DosFindNext`; `*.*` matches all files (HPFS)
- **Sandbox isolation** — path traversal beyond the volume root is blocked

## GDB Debugging

### Starting the GDB Stub

```bash
cargo run -- --gdb 1234 samples/hello/hello.exe
```

The vCPU pauses at the entry point and waits for a GDB connection.

### Connecting

```bash
gdb -ex 'target remote :1234'
```

### Supported Operations

| Command | Description |
|---------|-------------|
| `c` | Continue execution |
| `si` | Single-step one instruction |
| `b *0x<addr>` | Set software breakpoint |
| `info reg` | Show all registers |
| `p $eax` | Print individual register |
| `x/<N>x <addr>` | Examine memory (hex) |
| `x/<N>i <addr>` | Disassemble at address |
| `set {int}<addr> = <val>` | Write guest memory |
| `Ctrl-C` | Interrupt (pause vCPU) |

### How It Works

- **Software breakpoints:** INT 3 (0xCC) patched into guest memory; original byte restored on hit; RIP rewound to breakpoint address.
- **Single-step:** `KVM_GUESTDBG_SINGLESTEP` flag on vCPU.
- **Memory access:** The whole 256 MB guest address space.
- **Synchronisation:** `GdbState` (Mutex + Condvar) coordinates vCPU and GDB threads; `AtomicBool` for Ctrl-C.

### Source-level debugging

A program built with `-g` by GCC or clang and linked by `lx-link` has a debug companion beside it, `prog.dbg` (ADR-0102): the linked code at its addresses, the symbols, and the DWARF. Load it before connecting:

```bash
warpine --gdb 1234 prog.exe
gdb -ex 'symbol-file prog.dbg' -ex 'target remote :1234' -ex 'break main' -ex 'continue'
```

Breakpoints by function or `file:line`, `next` / `step`, arguments and locals, `print` of structures, `finish`, `bt` and globals then work.

DLLs need nothing more (ADR-0104):
- The stub lists every loaded DLL that has a `.dbg` beside it, at the addresses the loader gave its objects, and GDB loads it (`info sharedlibrary`). Some GDB versions (16) list the DLLs loaded before the first stop without reading their symbols: run `sharedlibrary` after `target remote`.
- `DosLoadModule` and `DosFreeModule` stop the program briefly so that GDB reads the list again. With `set breakpoint pending on`, a breakpoint in a DLL loaded later takes effect before its `_DLL_InitTerm` runs.
- When the program's DLLs have `_DLL_InitTerm` routines, the first stop is at Warpine's start thunk, which runs them before the program's entry point.

Current directories:

**Memory:**
DosAllocMem (299), DosFreeMem (304), DosSetMem (305), DosQueryMem (306), DosAllocSharedMem (300), DosGetSharedMem (302), DosGetNamedSharedMem (301), DosGiveSharedMem (303), DosSubSetMem (344), DosSubAllocMem (345), DosSubFreeMem (346), DosSubUnsetMem (347), DosAllocThreadLocalMemory (454), DosFreeThreadLocalMemory (455)

Shared memory: `DosAllocSharedMem` names must start with `\SHAREMEM\` (`ERROR_INVALID_NAME`), are case-insensitive and unique (`ERROR_ALREADY_EXISTS`; free again after `DosFreeMem`); the flags need `PAG_READ`, `PAG_WRITE` or `PAG_EXECUTE` (`ERROR_INVALID_PARAMETER`, also for unknown bits). `DosGiveSharedMem` needs the base address of a block allocated with `OBJ_GIVEABLE` (`ERROR_INVALID_ADDRESS` for any other address, `ERROR_ACCESS_DENIED` for a block that is not giveable or an access it was not allocated with) and an access bit (`PAG_GUARD` allowed, other bits `ERROR_INVALID_PARAMETER`); an unknown process is `ERROR_INVALID_PROCID`. Shared blocks are shared by all processes of a session (ADR-0049): they live in the shared arena, the top 32 MB of every process's guest memory (`0x0E000000`–`0x0FFFFFFF`), at the same address in each process. `DosGetNamedSharedMem` needs an access bit (`ERROR_INVALID_PARAMETER`) and a `\SHAREMEM\` name (`ERROR_INVALID_NAME`; an unknown name is `ERROR_FILE_NOT_FOUND`). `DosGetSharedMem` needs an access bit and a block allocated with `OBJ_GETTABLE` (`ERROR_ACCESS_DENIED`; an address that is not a block is `ERROR_INVALID_ADDRESS`, unverified). `DosGiveSharedMem` reaches any live process of the session, including a child that `DosExecPgm` has just started; the giver must hold the block. A block lasts while some process holds it: `DosFreeMem` lets it go (a second time is `ERROR_INVALID_ADDRESS`), and so does the end of the process, even a killed one. Then its name is free and its pages read zero. A new block is zero. Without a session (an unusable session directory) shared memory stays within the process. A process's code reaches only the blocks it holds (ADR-0049 addendum): touching any other part of the arena, or writing a block it holds read-only, raises `XCPT_ACCESS_VIOLATION`, and a block let go cannot be touched any more. A block got (`DosGetNamedSharedMem`, `DosGetSharedMem`) or given (`DosGiveSharedMem`) without `PAG_WRITE` is read-only to that process; one allocated without `PAG_WRITE` is read-only to all. `DosQueryMem` reports a block held as `PAG_SHARED | PAG_COMMIT` with its access (`PAG_BASE` on its first page), any other arena page as `PAG_FREE`. When a parent reaps a child (`DosWaitChild`, a synchronous `DosExecPgm`, …), the blocks only that child held are gone at once. API calls are held to the same: a buffer in a block the caller does not hold, or a read-only one it would write into, fails the call (`ERROR_INVALID_PARAMETER` for `DosRead` and `DosWrite`). 16-bit programs reach none of the arena. Warpine's own choices (unverified): giving to the calling process itself is `NO_ERROR`; getting a block twice counts once, keeping the larger access; read-only unless `PAG_WRITE` is asked for. `QSV_MAXSHMEM` is the arena's size.

Thread-local memory: `DosAllocThreadLocalMemory(cb, &p)` reserves `cb` DWORDs (1–8, else `ERROR_INVALID_PARAMETER`) of the 32-DWORD thread-local area and returns one pointer; every thread sees its own words behind it, also those an API call writes there. The words are reserved in every thread, and a thread starts with them zero. `ERROR_NOT_ENOUGH_MEMORY` when no run of `cb` free words is left. `DosFreeThreadLocalMemory(p)` frees a block by the pointer it was given (anything else: `ERROR_INVALID_PARAMETER`). Each 32-bit thread runs with its own page tables for this: the guest's memory is mapped one-to-one except the page holding the area (`TLM_PAGE`, `0x0181F000` in the system area, ADR-0094), which leads to the thread's own page (ADR-0088). A program cannot change its paging, as on OS/2: one that turns paging off, loads CR3 or writes its page tables ends as a trap (`TC_TRAP`, exit code 1; its exit list runs on repaired tables) within about 250 ms, and so does one that reads or writes memory past the guest's 256 MB 1,000 times in a row. Warpine's own choices (unverified): the area's address; new threads' words starting zero; the first fitting run handed out; Warpine's own host threads (the GUI's, for example) seeing thread 1's words; a host access that crosses the area's page boundary not being translated.

Suballocation: `DosSubSetMem` with `DOSSUB_INIT` makes a pool of at least 72 bytes (the size is rounded down to a multiple of 8; 64 bytes are control information), `DOSSUB_GROW` makes it larger (`ERROR_DOSSUB_SHRINK` for a smaller size; `DOSSUB_SPARSE_OBJ` must match the pool's, else `ERROR_DOSSUB_BADFLAG`), without `DOSSUB_INIT` it attaches to a pool set up before; `DOSSUB_SERIALIZE` is accepted (every call is serialised anyway). `DosSubAllocMem` rounds the size up to 8 bytes and hands out free space first fit (`ERROR_DOSSUB_NOMEM` when nothing is large enough); `DosSubFreeMem` returns a block (`ERROR_DOSSUB_OVERLAP` when it overlaps free space); `DosSubUnsetMem` ends the pool; a pool whose memory `DosFreeMem` frees without it ends then too, so the memory can hold a new pool. The pool's bookkeeping is kept by Warpine, not in the pool's memory. Warpine's own choices (unverified): unknown flags `ERROR_DOSSUB_BADFLAG`; a pool under 72 bytes, outside memory, at 0 or not set up before (attach, grow) `ERROR_INVALID_PARAMETER`; a pool overlapping another `ERROR_DOSSUB_OVERLAP`; a block size of 0 `ERROR_INVALID_PARAMETER`, above the pool size less 64 `ERROR_DOSSUB_BADSIZE`; a pool never set up `ERROR_DOSSUB_CORRUPTED` (alloc, free, unset); a block outside the pool or off the 8-byte grid `ERROR_INVALID_PARAMETER`; at most 1024 pools and 65536 separate free ranges per pool (`ERROR_NOT_ENOUGH_MEMORY`).

**Threading:**
DosCreateThread (311), DosWaitThread (349), DosGetInfoBlocks (312), DosSleep (229), DosKillThread (111), DosSuspendThread (238), DosResumeThread (237), DosEnterCritSec (232), DosExitCritSec (233)

Critical sections: while a thread is inside `DosEnterCritSec` … `DosExitCritSec`, the process's other threads do not run. The section nests up to 65535 levels (`ERROR_CRITSEC_OVERFLOW` beyond, the count unchanged); `DosExitCritSec` outside a section is `ERROR_CRITSEC_UNDERFLOW`. **Timers:**
DosAsyncTimer (350), DosStartTimer (351), DosStopTimer (290)

`DosAsyncTimer` posts a shared event semaphore once after the interval, `DosStartTimer` every interval until `DosStopTimer`; intervals are rounded up to the 32 ms clock tick (`DosQuerySysInfo(QSV_TIMER_INTERVAL)` = 320, in tenths of a millisecond). Errors: `ERROR_TS_SEMHANDLE` when the semaphore is not a shared event semaphore (`DC_SEM_SHARED` or named), `ERROR_TS_NOTIMER` past 64 timers, `ERROR_TS_HANDLE` from `DosStopTimer` for an unknown handle. Timers end with the process. Warpine's own choices (unverified): an interval of 0 is one tick; a NULL `phtimer` is `ERROR_INVALID_PARAMETER`; a one-shot timer's handle is invalid once it has posted; a timer whose semaphore was closed stops.

`DosExit(EXIT_THREAD)` and a thread function returning end only that thread; the process ends with its last thread, with that thread's result code. `DosWaitThread` supports `DCWW_WAIT` / `DCWW_NOWAIT` and 0 for any thread; `DosKillThread` ends the thread at once if it runs guest code (also a thread spinning without system calls), after the call if it is blocked in one, and when it is resumed if it is suspended. Thread ids of created threads start at 2. Unverified: thread 1 calling `DosExit(EXIT_THREAD)` while other threads run lets the process go on until the last one ends. `DosCreateThread` with `CREATE_SUSPENDED` starts the thread suspended; `STACK_COMMITTED` is accepted (memory is always committed); other flag bits are ignored (unverified). `DosSuspendThread` stops another thread of the process until `DosResumeThread`; suspensions count (two suspends need two resumes — unverified), a thread running guest code stops at once, one blocked in a call when the call returns. Errors: `ERROR_INVALID_THREADID` for the calling thread itself (unverified), a thread that does not run or has ended; `DosResumeThread` on a thread that is not suspended is `ERROR_NOT_FROZEN`. Thread 1 can be suspended by another thread (unverified). Sample `thread_control_test`.

**Exit lists:**
DosExitList (296)

The routines run on thread 1, as the Control Program Guide describes, however the process ends: `DosExit(EXIT_PROCESS)` or a fault on another thread asks thread 1 to run them (the calling thread waits for it, at most 5 seconds); a `HLT`, a triple fault or a failed `KVM_RUN` on thread 1 runs them there with `TC_TRAP` (`TC_HARDERROR` for the KVM error) and the process ends with exit code 1. Once thread 1 has ended they do not run. Warpine's own choices (unverified): the 5-second wait; thread 1 in 16-bit code ends the process without them (ADR-0087).

`EXLST_ADD` (invocation order in bits 8–15 of the order code), `EXLST_REMOVE`, `EXLST_EXIT`. When the process ends — `DosExit(EXIT_PROCESS)` from any thread, thread 1 returning from the program's entry point, thread 1 ending as the last thread, or an unhandled exception (termination code `TC_EXCEPTION`, exit code 1) — the other threads stop and the routines run lowest order first, the last added first among equal orders, each from the thread's initial stack with the termination code at `[ESP+4]` (`TC_EXIT` for the normal ends); each ends with `DosExitList(EXLST_EXIT, 0)`, and routines may add or remove others meanwhile. The process then ends with the exit code it was ending with. As the *Control Program Guide* says, the list does not run once thread 1 has ended (the last thread being another one). The list also runs (thread 1 running it) when the process is asked to end from outside: its window closed, Ctrl+Esc, the host's `SIGTERM` or the parent's `DosKillProcess` (`TC_KILLPROCESS`, through `XCPT_SIGNAL_KILLPROC`), the end of piped keyboard input (`TC_EXIT`), a triple fault or a VM exit Warpine cannot handle (`TC_TRAP`; on thread 1 after its starting segment state is put back) and a KVM error on another thread (`TC_HARDERROR`). Not run: a KVM error on thread 1, `HLT`, a process that does not end within 5 seconds of being asked to. Errors: `ERROR_INVALID_DATA` for a non-zero high word, an order with `EXLST_REMOVE` / `EXLST_EXIT`, a NULL routine or removing one that is not on the list; `ERROR_INVALID_FUNCTION` for an unknown action or `EXLST_EXIT` outside exit-list processing; `ERROR_NOT_ENOUGH_MEMORY` past 256 routines. Warpine's own choices (unverified): routines run on the thread that ends the process, not on thread 1; a routine that returns, calls `DosExit` or has an unhandled exception has ended as if it called `EXLST_EXIT` (OS/2 would hang); adding a listed routine again moves it to the new order.

**Semaphores:**
DosCreateEventSem (324), DosOpenEventSem (325), DosCloseEventSem (326), DosResetEventSem (327), DosPostEventSem (328), DosWaitEventSem (329), DosQueryEventSem (330), DosCreateMutexSem (331), DosOpenMutexSem (332), DosCloseMutexSem (333), DosRequestMutexSem (334), DosReleaseMutexSem (335), DosQueryMutexSem (336), DosCreateMuxWaitSem (337), DosOpenMuxWaitSem (338), DosCloseMuxWaitSem (339), DosWaitMuxWaitSem (340), DosAddMuxWaitSem (341), DosDeleteMuxWaitSem (342), DosQueryMuxWaitSem (343)

Event semaphores count posts: `DosPostEventSem` adds one (`ERROR_ALREADY_POSTED` when already posted — the post still counts; `ERROR_TOO_MANY_POSTS` past 65535), `DosResetEventSem` returns the count and clears it (`ERROR_ALREADY_RESET` when it is 0), `DosQueryEventSem` returns it. `DosQueryMutexSem` returns the owner's process id (that of `pib_ulpid`) and thread id and the request count, all 0 when unowned. A muxwait list holds at most 64 semaphores (`ERROR_TOO_MANY_SEMAPHORES`), all event or all mutex semaphores (`ERROR_WRONG_TYPE`, also for a muxwait semaphore), each once (`ERROR_DUPLICATE_HANDLE`); its flags need exactly one of `DCMW_WAIT_ANY` / `DCMW_WAIT_ALL` (else `ERROR_INVALID_PARAMETER`). `DosWaitMuxWaitSem` returns the user value of the first ready record (waiting for any) or of the last record (waiting for all) and takes the mutexes it waited for; on an empty list it returns `ERROR_EMPTY_MUXWAIT`, as `DosDeleteMuxWaitSem` does. `DosQueryMuxWaitSem` writes the `SEMRECORD`s and the creation flags (`DC_SEM_SHARED` added for a named semaphore); with too little room it returns `ERROR_PARAM_TOO_SMALL` and the number of records needed. Named semaphores start with `\SEM32\` (`ERROR_INVALID_NAME`), are unique across kinds (`ERROR_DUPLICATE_NAME`), case-insensitive, and open by name (`ERROR_SEM_NOT_FOUND`) or handle; each open adds a use and the last close deletes the semaphore. Unverified choices: deleting a semaphore that is not in the list is `ERROR_INVALID_HANDLE`; a full list reports `ERROR_TOO_MANY_SEMAPHORES` before a duplicate; a waiter on a list whose semaphore was closed gets `ERROR_INVALID_HANDLE`. Closing a semaphore another thread is blocked on (`DosWaitEventSem`, `DosRequestMutexSem`, `DosWaitMuxWaitSem`) returns `ERROR_SEM_BUSY` (an owned mutex nobody waits for closes). A mutex whose owner thread ends without releasing it is left in the owner-died state: `DosQueryMutexSem` reports the dead owner's process and thread (count 0) with `ERROR_SEM_OWNER_DIED`, and the next `DosRequestMutexSem` — also one already blocked — or `DosWaitMuxWaitSem` taking it gets the mutex with `ERROR_SEM_OWNER_DIED`, after which it is an ordinary mutex again (the reference describes the owner-died state for a process end; the hand-over to the next requester is Warpine's reading, unverified). `DosCreateEventSem` accepts `DC_SEM_SHARED`, `DCE_POSTONE` and `DCE_AUTORESET` (other bits: `ERROR_INVALID_PARAMETER`); the two `DCE_*` flags come from the toolkit headers without a public description, and Warpine reads them as (unverified): a wait released by a `DCE_AUTORESET` semaphore resets it, with `DCE_POSTONE` it takes one post, so one post releases one waiter (in muxwait lists too). `DosWaitMuxWaitSem` sleeps until a semaphore of the process changes (no polling). **Across processes** (ADR-0050): named and `DC_SEM_SHARED` event and mutex semaphores are shared by all processes of a session. Their handles (with the high bit set) are the same in every process, so `DosOpenEventSem` / `DosOpenMutexSem` work by name or by a handle another process passed on; a post or release in one process wakes waiters in the others. A mutex whose owning process ends (or is killed) is in the owner-died state for the next requester. Each process's opens count, and the semaphore is deleted when the last process closes it or ends. `ERROR_SEM_BUSY` concerns the closing process's own waiting threads. Muxwait semaphores stay within their process, named ones too, but their lists can hold shared semaphores. Warpine's limits: 512 shared semaphores per session (`ERROR_TOO_MANY_SEMAPHORES`), 28 processes having one open (`ERROR_TOO_MANY_OPENS`).

**Process:**
DosExit (234), DosExecPgm (283), DosWaitChild (280), DosKillProcess (235), DosQueryAppType (323)

`DosExecPgm` starts the child as a separate Warpine process. The child gets the argument block's two strings as its command line (`pib_pchcmd`; the program's full name sits right before it, after the environment), the environment given in `pEnv` or, for NULL, the parent's own, and every inheritable pipe handle at the same number: an anonymous pipe, or the client end of a named pipe (the server end stays with its process). A handle made non-inheritable with `DosSetFHState(OPEN_FLAGS_NOINHERIT)` (or `NP_NOINHERIT`) is not passed, so a reader sees the end of the data once the other write handles are closed. The program's own OS/2 name (`C:\NAME.EXE`, what a shell starts to run a copy of itself) is its host executable. For `EXEC_ASYNC` / `EXEC_ASYNCRESULT` the child's process id is in `codeTerminate` (CP Reference). Every process of a session has its own id: the first process is 42 (parent id 0), and each child gets the next id of a counter the session's processes share (100, 101, …, after 65535 from 100 again). The parent chooses it and passes it on, so the id the child reports (`pib_ulpid`, `DosQueryMutexSem`, `WinQueryWindowProcess`) is the one the parent holds for `DosWaitChild`, `DosKillProcess` and `DosSendSignalException`, and the child's `pib_ulppid` is its parent's id. An whole exit code (`DosExit`'s ULONG) reaches the parent's `RESULTCODES.codeResult` (`EXEC_SYNC`, `DosWaitChild`), `WM_APPTERMINATENOTIFY` and CMD's ERRORLEVEL: the child reports it on a pipe its parent gave it, since a host exit status carries only 8 bits (ADR-0090); a child that reports nothing (killed) gives the host status.

The program's entry point is called with the stack OS/2 sets up for an executable: return address, module handle, a reserved 0, the environment and the command line (`[esp+12]`, `[esp+16]`), which the C runtime's start-up code turns into `argc` / `argv` and the environment. Programs built with an Open Watcom snapshot of roughly March to August 2026 read these one slot off (Open Watcom #1649): they get an empty `argv` and no environment, and Warpine logs a warning; rebuild them with a newer Open Watcom (`vendor/setup_watcom.sh --refresh`). Files, pipes and other handles share one handle space: a new handle is the lowest free number from 3, and closed numbers are used again.

`DosKillProcess(ulAction, pid)` sends `XCPT_SIGNAL_KILLPROC` to a child (`DKP_PROCESS`) or to it and its descendants (`DKP_PROCESSTREE`; each child passes it on to its own children) and returns at once; the child's handlers see the signal and, unless one continues, its exit-list routines run with `TC_KILLPROCESS` and it ends with exit code 1. `DosWaitChild` then reports `codeTerminate = TC_KILLPROCESS`. The own process id signals the process itself. Errors: `ERROR_INVALID_DATA` (another action), `ERROR_ZOMBIE_PROCESS` (the child has ended and was not waited for yet), `ERROR_INVALID_PROCID` (not a child; grandchildren cannot be named, so `ERROR_NOT_DESCENDANT` is not returned). Warpine's own choices (unverified): a process asked to end — by `DosKillProcess`, by the host's `SIGTERM`, by closing its window — has 5 seconds to do so, also when a handler continues the signal; then it ends without its exit list (and a parent's `DosKillProcess` ends the child's host process 2 seconds later if it is still there).

**Pipes:**
DosCreatePipe (239), DosCreateNPipe (243), DosConnectNPipe (241), DosDisConnectNPipe (242), DosPeekNPipe (244), DosQueryNPHState (245), DosRawReadNPipe (246), DosRawWriteNPipe (247), DosQueryNPipeInfo (248), DosQueryNPipeSemState (249), DosSetNPHState (250), DosSetNPipeSem (251), DosTransactNPipe (252), DosCallNPipe (240), DosWaitNPipe (253); `DosOpen("\PIPE\name")` opens the client end.

`DosCreatePipe` handles are close-on-exec host pipes; `DosRead` / `DosWrite` on them block without holding up other threads. Named pipes (`\PIPE\` names, case-insensitive) are byte (`NP_TYPE_BYTE`) or message (`NP_TYPE_MESSAGE`) pipes, inbound / outbound / duplex, with 1–254 or unlimited (`NP_UNLIMITED_INSTANCES`) instances; the first instance fixes type, instance count and the default `DosWaitNPipe` timeout (0 = 50 ms). Instance states: `DosCreateNPipe` and `DosDisConnectNPipe` leave it disconnected, `DosConnectNPipe` listening (blocking: until a client opens it; non-blocking: `ERROR_PIPE_NOT_CONNECTED`, listening), a client's `DosOpen` connects it, and the client's close makes it closing (`DosConnectNPipe` then `ERROR_BROKEN_PIPE`, reads return 0 bytes, writes `ERROR_BROKEN_PIPE`). A client end starts blocking in byte-read mode. A message pipe keeps each `DosWrite` as one message; read in message mode, a message that does not fit returns its first part with `ERROR_MORE_DATA` and the rest on the next read; read in byte mode, messages run together. A non-blocking read with nothing there is `ERROR_NO_DATA`. `DosPeekNPipe` never blocks and returns the data (the current message in message-read mode), `AVAILDATA` (`cbpipe` = bytes in the pipe including 2 per message, `cbmessage` = what is left of the current message) and the state. `DosDisConnectNPipe` drops what the client has not read; the client's reads then fail with `ERROR_PIPE_NOT_CONNECTED`, its writes with `ERROR_BROKEN_PIPE`. `DosSetNPHState` takes `NP_NOWAIT` and the read mode (message read mode on a byte pipe, other bits: `ERROR_INVALID_PARAMETER`; going non-blocking while a thread is blocked on the end: `ERROR_PIPE_BUSY`). `DosQueryNPHState` reports blocking mode, end, type, read mode and instance count. `DosQueryNPipeInfo` level 1 writes `PIPEINFO` (buffer sizes, instance limit and count, name; what does not fit is cut with `ERROR_BUFFER_OVERFLOW`), level 2 a client id of 0, others `ERROR_INVALID_LEVEL`. `DosTransactNPipe` (and `DosCallNPipe`, which opens, transacts and closes) needs a duplex message pipe in message-read mode (`ERROR_BAD_FORMAT`) and ignores the non-blocking mode. `DosWaitNPipe` waits until an instance listens (`ERROR_SEM_TIMEOUT`; 0 = the pipe's default timeout, `NP_INDEFINITE_WAIT` = forever). A name nobody serves is `ERROR_FILE_NOT_FOUND` (`DosOpen`, `DosWaitNPipe`, `DosCallNPipe`), an instance limit reached or no listening instance `ERROR_PIPE_BUSY`, a call on a handle that is no named pipe `ERROR_BAD_PIPE`. Named pipes reach across the processes of one Warpine session (the first Warpine process and the children it starts); other host programs and other sessions do not see them. Warpine's own choices (unverified): reads and writes on a server that is not connected are `ERROR_PIPE_NOT_CONNECTED`; a full non-blocking pipe writes nothing (0 bytes, `NO_ERROR`); `DosTransactNPipe` with unread data is `ERROR_PIPE_BUSY`; `DosCallNPipe` returns `ERROR_PIPE_BUSY` when no instance listened within its timeout; `DosPeekNPipe` on an instance that is not connected returns no data and `NO_ERROR`; a message is at most 1 MiB; the client's `PIPEINFO` instance count is the one when it connected. `DosSetNPipeSem` attaches an event semaphore with a key (a USHORT; larger: `ERROR_INVALID_PARAMETER`) to one pipe end, replacing the one there; it is posted when data arrives for that end, when the other end closes (or the server disconnects) and when a write that found the pipe full has room again. `DosQueryNPipeSemState` writes a 6-byte `PIPESEMSTATE` per state of every end the semaphore is attached to — `NPSS_RDATA` with the bytes to read, `NPSS_WSPACE` with the room to write, `NPSS_CLOSE` — and an `NPSS_EOI` record last; `ERROR_BUFFER_OVERFLOW` (nothing written) when they do not fit. Warpine's own choices (unverified): only event semaphores (`ERROR_SEM_NOT_FOUND` otherwise; the reference also names muxwait semaphores), shared or not; `hsem` 0 detaches; a server end without a client may get a semaphore (`ERROR_PIPE_NOT_CONNECTED` is never returned) and reports nothing until connected; the room reported is the pipe's buffer size for that direction; `fFlag` (`NPSS_WAIT`) is always 0; a semaphore attached while data waits is posted at once; the query does not reset it. `DosRawReadNPipe` (246) / `DosRawWriteNPipe` (247) have public prototypes only (Toolkit 4.5 `bsedos.h`); Warpine's own format (unverified, ADR-0087): on a message pipe each message is a record, a little-endian USHORT length and its bytes. A raw read takes as many whole records as fit; a record that does not fit is cut, with `ERROR_MORE_DATA`, and its rest comes as the next record; a message longer than 65,535 bytes reads as several records. A raw write sends each record as one message (a record running past `cbWrite`: `ERROR_INVALID_PARAMETER`, nothing written) and reports the bytes taken, headers included. On a byte pipe both are `DosRead` / `DosWrite`. Not implemented: remote (`\\server\PIPE\`) pipes.

**Modules:**
DosLoadModule (318), DosFreeModule (322), DosQueryModuleHandle (319), DosQueryModuleName (320), DosQueryProcAddr (321), DosSearchPath (228)

Built-in modules (DOSCALLS, PMWIN, UCONV, WARPINE …) load without a file; `DosQueryProcAddr` finds their entry points by ordinal or by name, but only calls Warpine implements (`ERROR_PROC_NOT_FOUND` for the others, so a program probing for an optional call falls back). PMWIN and PMGPI names come from a table `build.rs` reads from their dispatchers; they match in any case (unverified, ADR-0087).

`DosSearchPath` looks for a file in each directory of a `;`-separated path (quoted elements may contain `;`), the current directory first with `SEARCH_CUR_DIRECTORY`, the path taken from an environment variable with `SEARCH_ENVIRONMENT` (`ERROR_ENVVAR_NOT_FOUND`); `SEARCH_IGNORENETERRS` is accepted. The result is fully qualified (`C:\DIR\FILE`); a name with wildcards is matched like `DosFindFirst` and returned with them. Errors: `ERROR_FILE_NOT_FOUND`, `ERROR_BUFFER_OVERFLOW` (result and NUL do not fit; nothing written), `ERROR_INVALID_PARAMETER` (reserved flag bits, NULL strings). `DosQueryModuleName` writes a module's fully qualified name: module handle 0 (the executable's handle in Warpine: `pib_hmte`, the entry point's argument) is the executable as named in its command line (`C:\NAME.EXE`), a DLL beside the executable `C:\NAME.DLL`, a DLL elsewhere on a drive its OS/2 path, and a built-in module loaded with `DosLoadModule` (DOSCALLS, PMWIN, UCONV …) `C:\OS2\DLL\NAME.DLL`; `ERROR_INVALID_HANDLE`, `ERROR_BAD_LENGTH` when the name and NUL do not fit. Warpine's own choices (unverified): reserved flags and NULL pointers `ERROR_INVALID_PARAMETER`; path elements that do not resolve are skipped whatever `SEARCH_IGNORENETERRS` says; only files match, directories do not; the names reported for the executable and built-in modules.

**System:**
DosQuerySysInfo (348), DosGetDateTime (230), DosSetDateTime (292), DosFlatToSel (425), DosSelToFlat (426), DosSetExceptionHandler (354), DosUnsetExceptionHandler (355)

`DosGetInfoSeg` (DOSCALLS 8; 16-bit programs and 32-bit programs calling the entry directly) returns the selectors of the global and local information segments (ADR-0040). `selector:0` is the segment; `DosSelToFlat` gives its flat address. The `GINFOSEG` holds the session clock's time (seconds since 1970, wrapping in 2106), the milliseconds since boot, the local date and time (time zone in minutes west of UTC), the version, the timer interval (320, tenths of a millisecond), the scheduler values `DosQuerySysInfo` reports, and boot drive C:. Its time fields are refreshed every 32 ms without another call. The `LINFOSEG` holds the process and parent ids, the calling thread's id, the process type and the module handle. A 32-bit program that calls the 16-bit entry through a Far16 thunk is not served (the thunk is bypassed).

Date and time (ADR-0039): Warpine cannot set the host's clock, so each process has a **session clock** — the host's time plus an offset. `DosGetDateTime` reports it in local time; the `DATETIME` time-zone field is minutes **west** of UTC (positive west of Greenwich, as the reference defines it) and the weekday 0 = Sunday. `DosQuerySysInfo(QSV_TIME_LOW / QSV_TIME_HIGH)` gives its seconds since 1970-01-01 UTC as two halves read at once (the low half wraps in 2106, the high half carries on). `DosSetDateTime` moves the clock of the calling process and of the children it starts afterwards, not of processes already running; a field out of range, hundredths over 99 or a year outside 1980–9999 fail with `ERROR_TS_DATETIME` and change nothing; its weekday and time zone are not used. `WARPINE_CLOCK` starts a session at a given date. Nothing here ends in 2038: the host's `time_t` is 64-bit, and Open Watcom programs, whose `time_t` is `unsigned long`, are good until 2106.

File times are local time in `FDATE` / `FTIME`, clamped to 1980-01-01 00:00:00 … 2107-12-31 23:59:58 (what the 7-bit year from 1980 can hold) and not shifted by the session clock. `DosSetFileInfo` / `DosSetPathInfo` (`FIL_STANDARD`, a `FILESTATUS3` of at least 24 bytes, else `ERROR_BUFFER_OVERFLOW`) set the last-access and last-write times; a date and time of 0 / 0 leave a time unchanged, an invalid date or time fails with `ERROR_INVALID_PARAMETER`. The creation time (Linux cannot set one) is not set. Of the attributes, `FILE_READONLY` takes effect on files: it clears the host file's write permission (clearing the attribute gives the owner write access back), so the file reports `FILE_READONLY`, cannot be opened for writing, and `DosDelete` refuses it with `ERROR_ACCESS_DENIED`. A directory keeps its write permission, so new files can still be created in it. Hidden, system and archive have no host counterpart: Warpine keeps them as one byte beside the file (the extended attribute `user.warpine.attr`, or a sidecar in the folder's `.os2ea`, which programs never see or reach; ADR-0091) and reports them in `DosQueryPathInfo`, `DosQueryFileInfo` and `DosFindFirst`, whose filter shows hidden and system files only when asked for. A file is archived until the attribute is cleared, and again when it is opened for writing; a directory has none of them unless set. `DosCopy` gives the copy the source's EAs and attributes, and `DosMove` keeps them. Warpine's own choices (unverified): archived at the opening for writing rather than at the first write; EAs or attributes that cannot be copied are left out without an error. `DosSetFileMode` sets the attributes the same way. `DosSetPathInfo` level 2 (`FIL_QUERYEASIZE`) sets extended attributes from an `EAOP2` (at least 12 bytes, else `ERROR_BUFFER_OVERFLOW`) whose `fpFEA2List` names an `FEA2LIST` (at most 64 KB): each entry is set in order, an empty value deletes its EA; a list that is not well formed (an entry past `cbList`, an empty name, no NUL after a name, a next offset inside its entry) sets nothing, gives `ERROR_EA_LIST_INCONSISTENT` and puts the bad entry's offset from the list's start in `oError`. `DosSetFileInfo` level 2 (by handle) is still accepted and ignored; other levels are `ERROR_INVALID_LEVEL`. `DosQueryPathInfo` level 5 (`FIL_QUERYFULLNAME`) writes the fully qualified name — the drive, then the drive's current directory for a relative name, `.` and `..` resolved (above the root: `ERROR_PATH_NOT_FOUND`) — whether or not the file exists, in the caller's case; a buffer too small for it and its NUL gives `ERROR_BUFFER_OVERFLOW`.

**Exception Handling:**
DosRaiseException (356), DosUnwindException (357), DosSetSignalExceptionFocus (378), DosSendSignalException (379), DosAcknowledgeSignalException (418)

`DosUnwindException(phandler, pTargetIP, pERepRec)` (ADR-0110):
- **The handlers:** those above `phandler` are called with `EH_UNWINDING`, newest first, and each leaves the chain when it returns. `END_OF_CHAIN` or `UNWIND_ALL` (0) unwinds the whole chain. A `phandler` that is not on the chain is refused with `ERROR_INVALID_PARAMETER`, and nothing is unwound.
- **The records they get:** `pERepRec` with `EH_UNWINDING` added to its flags, or a report of `XCPT_UNWIND` when it is NULL. The context record holds the caller's state.
- **Afterwards** the thread goes on at `pTargetIP` with the registers and stack of the call's return, or returns when `pTargetIP` is NULL.

`DosRaiseException` sets the report's `ExceptionAddress` to the address its call returns to.

**Traps:**
- The low 64 KB of the address space are not present, so a NULL pointer, or one just past it, raises `XCPT_ACCESS_VIOLATION`, as on OS/2. Its `ExceptionInfo[0]` is `XCPT_READ_ACCESS` or `XCPT_WRITE_ACCESS`, and `[1]` the address.
- A program may reload FS (Open Watcom's `longjmp` does) and still reach its TIB.

Samples `xcpt_unwind_test`, `wcxx_throw_test` (Open Watcom C++ exceptions, which unwind through `DosUnwindException`).

Signal exceptions (`XCPT_SIGNAL`, `ExceptionInfo[0]` = `XCPT_SIGNAL_INTR` 1 / `XCPT_SIGNAL_KILLPROC` 3 / `XCPT_SIGNAL_BREAK` 4) go to thread 1's exception handlers only. `DosSendSignalException(pid, signal)` sends INTR or BREAK (else `ERROR_INVALID_SIGNAL_NUMBER`) to the process itself (its own PID), to a running child, or to any other running process of the session (the parent, a sibling: found by its session record and reached through a host signal sent by pidfd after checking the process is still the recorded one, ADR-0090); other PIDs are `ERROR_INVALID_PROCID`. INTR and BREAK reach the handlers only while the focus count of `DosSetSignalExceptionFocus` (`SIG_SETFOCUS` +1, `SIG_UNSETFOCUS` −1, `ERROR_ALREADY_RESET` at 0, `ERROR_NESTING_TOO_DEEP` above 65535; `*pulTimes` gets the count) is above 0; otherwise — and when no handler returns `XCPT_CONTINUE_EXECUTION` — the process ends (exit-list routines get `TC_KILLPROCESS`, exit code 1 — unverified). After a signal is delivered, further ones of that type are held (one kept, not queued) until a handler returns `XCPT_CONTINUE_EXECUTION` or `DosAcknowledgeSignalException` is called (`ERROR_INVALID_SIGNAL_NUMBER` for numbers other than 1, 3, 4). Thread 1 gets a signal at once while it runs guest code, not while it runs 16-bit code. A blocking call it waits in is interrupted: `DosSleep`, `DosWaitEventSem`, `DosRequestMutexSem`, `DosWaitMuxWaitSem`, `DosWaitThread`, `DosWaitChild`, `DosConnectNPipe` and `DosWaitNPipe` return `ERROR_INTERRUPT` after the handler continued; `KbdCharIn`, `KbdStringIn` (nothing typed yet), `DosRead` of the keyboard or a pipe, `DosReadQueue`, `MouReadEventQue` and a waiting `WinGetMsg` / `WinPeekMsg` are made again (Warpine's choice where the reference lists no `ERROR_INTERRUPT`); the same holds for a thread `DosKillThread` ends. Ctrl+C typed in a VIO program (its window, the full-screen window, a terminal, or piped keyboard input) is `XCPT_SIGNAL_INTR`, and Ctrl+Break (Ctrl+Pause) is `XCPT_SIGNAL_BREAK`; neither is a character (the KBD binary mode is not implemented). A terminal has no Break key, so there Ctrl+\ stands for Ctrl+Break (ADR-0093, Warpine's choice). The host's `SIGINT` is `XCPT_SIGNAL_INTR`, `SIGQUIT` (Ctrl+\ at a terminal not in raw mode) is `XCPT_SIGNAL_BREAK`, and `SIGTERM` is `XCPT_SIGNAL_KILLPROC`. While thread 1 waits in `WinDlgBox`, `WinProcessDlg` or `WinMessageBox`, a signal reaches its handlers between two messages, and the dialog goes on when they continue. A named-pipe write blocked partway through a message stops for a signal or `DosKillThread`: the message counts as written, and its rest still reaches the reader whole and before any later message. Once a `DosTransactNPipe` / `DosCallNPipe` message is out, an interrupted wait for the reply fails with `ERROR_INTERRUPT`. `DosEnterMustComplete` / `DosExitMustComplete` open and close must-complete sections (a nesting count per thread in `*pulNesting`; `ERROR_ALREADY_RESET` with none open, `ERROR_NESTING_TOO_DEEP` above 65535 — unverified): while thread 1 is in one, signals and termination requests from outside wait and are delivered when it ends (ADR-0058). A blocking `connect` or `send`, `DosBeep`, `MCI_WAIT` playback and CMD.EXE waiting for a program are interrupted too: `connect` fails with `SOCEINTR` (the connection goes on), `send` returns what it sent (`SOCEINTR` when nothing), the tone stops, the MCI sound plays on, and CMD.EXE asks the program to end. Not available: `ERROR_INVALID_PROCID` from `DosSetSignalExceptionFocus` for PM programs; interrupting writes to anonymous pipes. Samples `thread_control_test`, `kill_test`, `pm_dlg_signal_test`, `npipe_cut_test`.

### QUECALLS (8 APIs)

DosCreateQueue (1040), DosOpenQueue (1039), DosCloseQueue (1035), DosReadQueue (1033), DosWriteQueue (1038), DosPurgeQueue (1034), DosQueryQueue (1036), DosPeekQueue (1037)

Each element has an element code. `DosPeekQueue` copies the first element (`*pElement` 0), or the one after the code given, without removing it, and returns its code. `DosReadQueue` takes the first element, or the one a code names (`ERROR_QUE_ELEMENT_NOT_EXIST` when it is gone). ### NLS (4 APIs)

DosQueryCtryInfo (NLS 5), DosQueryDBCSEnv (NLS 6), DosMapCase (NLS 7), DosQueryCollate (NLS 8) — the 32-bit NLS calls at the ordinals of `<bseord.h>` and Open Watcom's `os2386.lib`.

- The `COUNTRYCODE` codepage selects the codepage when it is not 0, else the process codepage is used; the country is not used (country data comes from the host locale).
- A buffer that is too small gets as much of the table as fits, in order, and the call returns `ERROR_NLS_TABLE_TRUNCATED` (399). The reference lists that code without saying when it is returned, so this is Warpine's choice.
- `DosQueryCollate` returns 256 sort weights. IBM's tables (COUNTRY.SYS) are not published: Warpine weighs each byte as its uppercase form, so letters sort without regard to case.
- The 16-bit `DOS16*` calls (NLS 1–4) are not implemented.

### Sockets (SO32DLL 30, TCP32DLL 64 APIs)

BSD socket calls on Linux sockets. `sock_errno` returns `SOCBASEERR` (10000) plus the BSD error number, as `<nerrno.h>` defines the `SOCE*` codes (`SOCEWOULDBLOCK` 10035). C programs built with the SDK declare the calls through its TCP/IP headers (`<sys/socket.h>` …; TCP/IP 4.0 layouts). Socket options use OS/2's BSD numbering (`SOL_SOCKET` 0xFFFF, `SO_REUSEADDR`, `SO_KEEPALIVE`, `SO_LINGER`, `SO_SNDBUF` / `SO_RCVBUF`, `SO_ERROR`, `SO_TYPE`, …, and `TCP_NODELAY`) and are translated; `SO_SNDTIMEO` / `SO_RCVTIMEO` and IP-level options fail with `SOCENOPROTOOPT`.

`select` takes the OS/2 TCP/IP `fd_set` of Open Watcom's `<types.h>`: a count (`u_short fd_count`, then 2 bytes of padding) and an array of up to 64 socket numbers (`int fd_array[64]`), not a bit mask, so any socket number fits (Warpine's start at `0xA000`). Every number must be an open socket (else `SOCENOTSOCK`); a count above 64 or a timeout with negative seconds or microseconds of 1 000 000 or more is `SOCEINVAL`; `nfds` is ignored. On return each set holds the ready sockets in their original order, and the result is their total (0 after the timeout). A socket counts as readable or writable also after an error or a hang-up. A signal interrupts the wait with `SOCEINTR`. `bsdselect` and `os2_select` are not provided; their ordinals are not known (ADR-0041).

**Utility routines** (`tcpip_util.rs`; at Warpine's own ordinals, linked by name — ADR-0123):
- SO32DLL: ioctl (50; `FIONBIO`, `FIONREAD`, `SIOCATMARK`, others `SOCEINVAL`), readv (51), writev (52) (at most 1024 vectors and 64 KB, one receive or send).
- TCP32DLL: inet_addr (50; `a`, `a.b`, `a.b.c`, `a.b.c.d`, decimal / octal / hex parts, `INADDR_NONE` for a bad string), inet_network (51), inet_ntoa (52; one buffer per process, overwritten by the next call), inet_makeaddr (53), inet_lnaof (54), inet_netof (55), bswap (56), lswap (57), htonl (58), htons (59), ntohl (60), ntohs (61), dn_comp (62; no compression, the name is written in full and added to `dnptrs`), dn_expand (63; pointers must point backwards), dn_skipname (64), _getshort (65), _getlong (66), putshort (67), putlong (68), setprotoent (69), getprotoent (70), endprotoent (71), setservent (72), getservent (73; the host's services database, read once), endservent (74), tcp_h_errno (75; `HOST_NOT_FOUND` after a failed `gethostbyname` / `gethostbyaddr`, the `h_errno` macro of the SDK's `<netdb.h>`), sethostent / gethostent / endhostent (76–78; the host's `/etc/hosts`, IPv4 entries, each with its first name and no aliases), setnetent / getnetent / endnetent (79–81) and getnetbyname / getnetbyaddr (82, 83; the host's `/etc/networks`, `AF_INET`), res_init (84; reads nothing ahead), res_mkquery (85; `QUERY` only, recursion desired; its length or -1), res_send (86; UDP to the host's name servers from `/etc/resolv.conf`, port 53, two rounds of five seconds a server; the answer cut to the buffer, its whole length or -1), res_query (87), res_search (88; the search list for a name without a dot) and res_querydomain (89; `name.domain`), which set `h_errno` (`HOST_NOT_FOUND` for NXDOMAIN, `NO_DATA` for no answer of the type, `TRY_AGAIN` without an answer, `NO_RECOVERY`). The records come back in one per-process buffer with a region each for the last hostent, servent and netent (names cut to fit). Warpine's choices (unverified): the host's databases, not `%ETC%\HOSTS` / `NETWORKS`; no `_res` resolver state.
- The protocol database (`getprotobyname`, `getprotobynumber`, `getprotoent`) is Warpine's own — ip 0, icmp 1, tcp 6, udp 17, each with its upper-case alias — as there is no `%ETC%\PROTOCOL` file.

### MSG (4 APIs)

DosInsertMessage (4), DosPutMessage (5), DosGetMessage (6), DosQueryMessageCP (8) — the 32-bit ordinals of Open Watcom's `os2386.lib` (MSG.6 is `DOS32TRUEGETMESSAGE`, MSG.8 `DOS32IQUERYMESSAGECP`; the library's `DosGetMessage` passes its message segment as an extra first argument, which Warpine skips).

`DosInsertMessage` replaces `%1` … `%9` by the insertion strings (at most 9, else `ERROR_MR_INV_IVCOUNT`) and returns `ERROR_MR_MSG_TOO_LONG` with what fits when the buffer is too small; other `%` sequences stay as they are. `DosQueryMessageCP` reports the process codepage for a file that exists (`ERROR_MR_UN_ACC_MSGF` for a missing one).

`DosGetMessage` reads message files in Warpine's own format (ADR-0105), which the SDK's `os2msg` compiles from text; IBM `MKMSGF` files are not read.
- **Where it looks:**
  1. the program's bound messages (`.msg` files given to `lx-link`), by file name;
  2. the file as named, if the name has a drive or directory;
  3. otherwise the current directory, then each `DPATH` directory.
- **The text:** errors and warnings start with their id (`ABC0001: `), and `%1` … `%9` take the insertion strings (at most 9, else `ERROR_MR_INV_IVCOUNT`).
- **Errors:** a message cut to the buffer returns `ERROR_MR_MSG_TOO_LONG`. With no file (`ERROR_MR_UN_ACC_MSGF`), a file in another format (`ERROR_MR_INV_MSGF_FORMAT`) or no such message (`ERROR_MR_MID_NOT_FOUND`), the buffer gets a text saying so.

The source `os2msg` reads:

```
; comment
ABC
ABC0001E: The file %1 was not found.
ABC0002I: Information,
on two lines.
ABC0003P: Continue (Y/N)?
```

### MDM / MMPM/2 (6 APIs)

mciSendCommand (10241), mciSendString (10242), mciGetErrorString (10243), mciSetSysValue (10250), mciQuerySysValue (10251), mciGetDeviceID (10256) — MDM 1–3, 10, 11 and 16, the ordinals of Open Watcom's `mmpm2.lib` (it has no MDM 4).

Device type: `waveaudio` (WAV files: uncompressed 8/16/24/32-bit PCM or 32-bit float). Constants, parameter blocks and error codes follow `<mcios2.h>` / `<meerror.h>`.

- **`mciSendCommand`:** `MCI_OPEN` (`MCI_OPEN_ELEMENT`, `MCI_OPEN_ALIAS`, `MCI_OPEN_TYPE_ID`), `MCI_CLOSE`, `MCI_PLAY` (`MCI_FROM`, `MCI_WAIT`, `MCI_NOTIFY` → `MM_MCINOTIFY`: mp1 = the notify code and the command's user parameter, mp2 = the device and `MCI_PLAY`), `MCI_STOP`, `MCI_SEEK`, `MCI_SET` (`MCI_SET_AUDIO | MCI_SET_VOLUME`, also changes a playing sound), `MCI_STATUS` (mode, length, position); `MCI_RECORD` returns `MCIERR_UNSUPPORTED_FUNCTION`.
- **`mciSendString`:** `open <file | waveaudio> [type t] [alias a] [wait]`, `play <a> [wait] [notify]`, `stop`, `close`, `seek <a> to <ms>`, `set <a> audio volume to <n>`, `status <a> mode`; devices are named by alias, element name or device ID.
- **`mciGetErrorString(ulError, pszBuffer, usLength)`:** the low word of `ulError` is the error code, the high word a device ID (0 for none; one that is not open gives `MCIERR_INVALID_DEVICE_ID`). The text and its NUL are copied, at most `usLength` bytes of them (a short buffer gets the text cut, without a NUL); a code `<meerror.h>` does not define gives `MCIERR_OUTOFRANGE`, a null or unwritable buffer `MCIERR_INVALID_BUFFER`. The texts are the codes' names in words ("File not found"; IBM's texts are not public, unverified).

- **`mciQuerySysValue` / `mciSetSysValue(iSysValue, pValue)`:** the `MSV_*` system values per process — closed captioning, master volume (0–100, 100 at first), headphones, speakers (on at first), the work path (`C:\` at first; a `CCHMAXPATH` buffer), the QoS value and error flag. A query returns `MCIERR_SUCCESS` (`MCIERR_INVALID_FLAG` for an unknown value), a set TRUE or FALSE (an unknown value, a volume above 100, an empty or overlong path). Warpine keeps the values; playback does not act on them.
- **Output:** sound is played by the main-thread SDL3 loop; headless runs (`WARPINE_HEADLESS=1`, or a CLI program whose stdout is not a terminal) are silent, and `DosBeep` then returns at once.

### PMSHAPI — profiles (10 APIs)

PrfQueryProfileSize (101), PrfOpenProfile (102), PrfCloseProfile (103), PrfQueryProfile (107), PrfReset (108), PrfQueryProfileInt (114), PrfQueryProfileString (115), PrfWriteProfileString (116), PrfQueryProfileData (117), PrfWriteProfileData (118)

- **Files.** `HINI_USERPROFILE` is `C:\OS2\OS2.INI`, `HINI_SYSTEMPROFILE` `C:\OS2\OS2SYS.INI`; `HINI_PROFILE` searches the user profile, then the system profile, and writes go to the user profile. `PrfOpenProfile` opens any other file (path resolved like `DosOpen`'s), creating it when missing; opening an open file again returns the same handle (one `PrfCloseProfile` per open). OS2.INI / OS2SYS.INI cannot be opened this way (`PMERR_INI_FILE_IS_SYS_OR_USER`).
- **`PrfQueryProfile` / `PrfReset`.** `PrfQueryProfile` writes the names of the user and system profiles into a `PRFPROFILE`; a length of 0 asks for the bytes a name needs (its NUL included), and a buffer too small gets the name cut to fit, NUL-terminated, and `PMERR_BUFFER_TOO_SMALL`. `PrfReset` makes another file the user profile of the whole session (made when missing; a name without a drive or directory is relative to the current directory), then posts `PL_ALTERED` to every message queue of the session; only the user profile can change: `pszSysName` must name the system profile (`PMERR_INVALID_PARM`), the system profile cannot become the user's (`PMERR_INI_FILE_IS_SYS_OR_USER`), and a file that cannot be made or read as a profile is `PMERR_OPENING_INI_FILE`. The choice lasts while the session does. Warpine's own (unverified): the lengths including the NUL, `PMERR_BUFFER_TOO_SMALL`, `PMERR_INVALID_PARM` for another system profile, `PL_ALTERED`'s parameters (0, 0).
- **Format.** Warpine's own text format, not OS/2's binary INI layout (which IBM does not document): a `; warpine-profile 1` line, then `["Application"]` sections with `"Key" = "value"` lines; names and values are quoted, with `\\`, `\"`, `\0`, `\t`, `\n`, `\r` and `\xHH` escapes, so binary data is kept exactly. A file in another format (for example a binary INI shipped with a program) fails with `PMERR_INI_FILE_CORRUPT`. Each change replaces the file atomically.
- **Queries.** Names are case-sensitive. A string is stored with its NUL; `PrfQueryProfileString` returns the bytes written including the NUL (truncated to the buffer, still NUL-terminated) or, for a missing key, the default (no default: 0 bytes) and records `PMERR_NOT_IN_IDX`. `PrfQueryProfileInt` reads an optional `-` and the digits that follow ("123xyz" → 123; no digits → 0); a missing key returns the default. A NULL application lists the applications, a NULL key the keys of an application: NUL-terminated names ending with a second NUL; the returned length leaves out the final NUL, and a list cut short by the buffer is not double-terminated. `PrfQueryProfileSize` reports the value's size, or the whole list's (both NULs included). `PrfQueryProfileData` copies what fits and sets `*pulBufferMax` to the bytes copied.
- **Writes.** NULL data deletes a key, a NULL key the whole application; deleting what does not exist succeeds. Values are limited to 64 KB.
- **Errors** (`WinGetLastError`): `PMERR_INVALID_INI_FILE_HANDLE`, `PMERR_NOT_IN_IDX`, `PMERR_INVALID_PARM` (NULL application for a write, a string or buffer outside guest memory, a value over 64 KB), `PMERR_OPENING_INI_FILE`, `PMERR_INI_FILE_CORRUPT`, `PMERR_INI_WRITE_FAIL`, `PMERR_INI_FILE_IS_SYS_OR_USER`.
- Not implemented: `PrfQueryProfile` / `PrfReset`, the program-list calls (`PrfAddProgram`, …), the 16-bit `PRF16*` entry points.

### PMCTLS — standard dialogs (5 APIs)

WinFontDlg (2), WinDefFontDlgProc (3), WinFileDlg (4), WinDefFileDlgProc (5), WinFreeFileDlgList (6) — ordinals from the Open Watcom import library `os2386.lib` (its PMCTLS records; the ordinal snapshot `doc/os2_ordinals.md` has no PMCTLS section).

- **File dialog.** An Open or Save As dialog (`FDS_OPEN_DIALOG` / `FDS_SAVEAS_DIALOG`) with the file name, the current directory, the type of file ("<All Files>" and `pszIType` / `papszITypeList`, matched against a file's `.TYPE` extended attribute), the drives (the mounted ones, or `papszIDriveList`), the directories and the files; OK / Cancel and, with `FDS_APPLYBUTTON` / `FDS_HELPBUTTON`, Apply / Help. `szFullFile` gives the starting drive, directory and file name or wildcard filter. A click on a file puts its name in the entry field, a double click is OK; a double click on a directory enters it. OK with a wildcard changes the filter, with a directory enters it, with a valid name in an existing directory ends the dialog (the name takes the case of an existing file). The dialog only sees Warpine's drives. It writes back `lReturn` (`DID_OK` / `DID_CANCEL`), `lSRC`, `szFullFile` and `ulFQFCount`; with `FDS_MULTIPLESEL` several files can be selected and `papszFQFilename` lists them until `WinFreeFileDlgList`. `FDS_CENTER`, `x` / `y`, `pszTitle`, `pszOKButton`, `FDS_ENABLEFILELB` (Save As disables the file list otherwise), `FDS_MODELESS` (returns the dialog's handle; it hides itself when done), `pfnDlgProc` (subclassing; pass the rest to `WinDefFileDlgProc`; the `FILEDLG` is in `QWL_USER`) and `FDS_CUSTOM` templates (`hMod` / `usDlgId`, filled by control id) are supported. Modal calls return TRUE (NULLHANDLE with `lSRC` set on an error). A dialog procedure is sent, through `WinDefFileDlgProc`, `FDM_FILTER` for each file listed (mp1 the name, mp2 its first `.TYPE` or NULL; FALSE leaves it out — the first call of the default procedure, normally for `WM_INITDLG`, filters the lists filled at creation), `FDM_VALIDATE` for each file OK or Apply takes (mp1 the fully qualified name, mp2 `DID_FILENAME_ED` or `DID_FILES_LB`; FALSE keeps the dialog open) and `FDM_ERROR` for a name it cannot use (mp1 `FDS_ERR_INVALID_DRIVE` or `FDS_ERR_INVALID_PATHFILE`); `WinDefFileDlgProc` answers TRUE, TRUE and 0. Not supported: a default error box for `FDM_ERROR`, `FDS_INCLUDE_EAS` / `FDS_PRELOAD_VOLINFO` / `FDS_FILTERUNION` are ignored, Help shows nothing, no overwrite question for Save As.
- **Font dialog.** Name (IBM Plex Mono / Sans / Serif; `FNTS_FIXEDWIDTHONLY` / `FNTS_PROPORTIONALONLY` filter them), style (Normal, Italic, Bold, Bold Italic), size (`pszPtSizeList` or a default list; any size can be typed), emphasis (outline, underscore, strikeout) and a sample (`pszPreview`, `clrFore` / `clrBack`) drawn in the chosen font; Reset / Apply / Help with `FNTS_RESETBUTTON` / `FNTS_APPLYBUTTON` / `FNTS_HELPBUTTON`. It starts from `fAttrs` (`FNTS_INITFROMFATTRS`) or `pszFamilyname` / `flStyle` / `fxPointSize`, and OK writes back the family name, `fxPointSize`, `sNominalPointSize`, `flStyle`, `flType`, `usWeight` / `usWidth`, the em / x heights and an `fAttrs` that `GpiCreateLogFont` turns into the same font. `FNTS_CENTER`, `FNTS_MODELESS`, `pfnDlgProc` with `WinDefFontDlgProc` and `FNTS_CUSTOM` templates work as for the file dialog. A dialog procedure is sent, through `WinDefFontDlgProc`, `FNTM_FILTERLIST` for each family and size listed (mp1 the text, mp2 `MPFROM2SHORT(DID_NAME or DID_SIZE, FNTI_*)`; FALSE leaves it out, a refused chosen family gives way to the first one left) and, when the choice changes, `FNTM_FACENAMECHANGED` (the family name), `FNTM_POINTSIZECHANGED` (the size as text and as FIXED) and `FNTM_STYLECHANGED` (a `STYLECHANGE`). Not supported: printer fonts, `FNTS_OWNERDRAWPREVIEW` (`FNTM_UPDATEPREVIEW`), colour choices (`FNTM_COLORCHANGED`), filtering the style list; `FNTS_BITMAPONLY` is ignored (all of Warpine's fonts are outline fonts); the sample does not show the emphasis.

### SOM — the SOM runtime kernel (ADR-0059 to ADR-0063, ADR-0070 to ADR-0073)

`SOM.DLL` is built in. A program imports its functions and data by name or, for IBM's SOM 1.0 exports, by **IBM's ordinals** (ADR-0070), as a program linked against IBM's `som.lib` does:
- **1–19, data:** `SOMCalloc` (1), `SOMClassCClassData` (2), `SOMClassClassData` (3), `SOMClassInitFuncName` (4), `SOMClassMgrCClassData` (5), `SOMClassMgrClassData` (6), `SOMClassMgrObject` (7), `SOMDeleteModule` (8), `SOMError` (9), `SOMFree` (10), `SOMLoadModule` (11), `SOMMalloc` (12), `SOMObjectCClassData` (13), `SOMObjectClassData` (14), `SOMOutCharRoutine` (15), `SOMRealloc` (16), `SOM_AssertLevel` (17), `SOM_TraceLevel` (18), `SOM_WarnLevel` (19).
- **20–47, functions:** `SOMClassMgrNewClass` (20), `SOMClassNewClass` (21), `SOMObjectNewClass` (22), `somAssert` (23), `somBeginPersistentIds` (24), `somCheckArgs` (25), `somCheckId` (26), `somCompareIds` (27), `somConstructClass` (28), `somEndPersistentIds` (29), `somEnvironmentNew` (30), `somIdFromString` (31), `somLPrintf` (32), `somParentResolve` (33), `somPrefixLevel` (34), `somPrintf` (35), `somRegisterId` (36), `somResolve` (37), `somSaveMetrics` (38), `somSetExpectedIds` (39), `somStringFromId` (40), `somTest` (41), `somTestCls` (42), `somTotalRegIds` (43), `somUniqueKey` (44), `somVprintf` (45), `somWriteMetrics` (46), `somDataResolve` (47).
- **48–3071** are left to IBM's later exports, whose numbers are not known; the SOM 2.x functions Warpine has (`somResolveByName`, `somClassResolve`, `somGetGlobalEnvironment`, `somIsObj`, `somSetOutChar`) are imported by name. Warpine's own exports (`Wrp*`, the root classes' method thunks) are at 3072–4095: the SOM module is 4096 ordinals wide (ADR-0071).

What they do:

- Functions (`_System`):
  - `somEnvironmentNew()` starts the runtime and returns `SOMClassMgrObject`;
  - `somResolve(obj, token)` / `somResolveByName(obj, name)` return the procedure of a method for an object, `somClassResolve(class, token)` for a class (parent calls);
  - `somDataResolve(obj, token)` the address of a class's instance data in an object (an object without that data raises `SOMERROR_BadArgument`, 20199); `somDataResolveChk(obj, token)` (Warpine's 3079, by name) returns 0 instead;
  - `somGetGlobalEnvironment()`, `somIdFromString` / `somStringFromId` / `somCompareIds`, `somIsObj`;
  - `somPrintf(fmt, …)` formats as C's `printf` to standard output (at most nine argument words, 64 KB);
  - `<Class>NewClass(major, minor)` for `SOMObject`, `SOMClass` and `SOMClassMgr` returns the class object (made with the runtime; every version is accepted);
  - `somParentResolve(parentMtab, token)` returns the procedure of a method in the first method table of a class's parent-table list (`<Class>CClassData.parentMtab`), or a procedure returning 0;
  - `somCheckId(id)` registers an id and returns it; `somRegisterId(id)` registers it and returns 1 if it was new, else 0; `somUniqueKey(id)` returns one key per string; `somTotalRegIds()` counts the registered ids; `somSetExpectedIds`, `somBeginPersistentIds` and `somEndPersistentIds` have no effect;
  - `somPrefixLevel(level)` writes two blanks per level (up to 64 levels); `somLPrintf(level, fmt, …)` writes them, then formats as `somPrintf`; `somVprintf(fmt, ap)` takes its arguments from a `va_list`; all write through `SOMOutCharRoutine`;
  - `somTestCls(obj, class, file, line)` returns the object when it is an instance of the class or a descendant's, else raises `SOMERROR_TestObjectFailure` (20109); `somTest(condition, severity, file, line, msg)` (the `SOM_Test` / `SOM_TestC` macros) raises `SOMERROR_FailedTest` with that severity when the condition fails — a fatal one always, any other only when `SOM_WarnLevel` is above 0 — and writes "Test passed: msg" when it holds and `SOM_AssertLevel` is above 0; `somAssert(condition, code, file, line, msg)` likewise raises `code` (a non-fatal one only above `SOM_WarnLevel` 0) and writes "Assertion passed: msg"; `somCheckArgs(argc, argv)` sets `SOM_TraceLevel` (`-somt` 1, `-somtc` 2), `SOM_AssertLevel` (`-soma` 1, `-somac` 2) and `SOM_WarnLevel` (`-somw` 1) (ADR-0072);
  - `somParentNumResolve(parentMtab, n, token)` (by name) resolves in the `n`th parent, from 1;
  - `somConstructClass`, `somSaveMetrics` and `somWriteMetrics` are stubs returning 0;
  - `WrpSomMetaclassFor(requested, parent)` (Warpine's) returns the metaclass for a new class: `requested` (0: the parent's metaclass) if it descends from the parent's metaclass, the parent's if that descends from `requested`, else a metaclass derived from both, made once.
  - `WrpSomDataExport(ordinal)` (Warpine's, 3090) returns the address of SOM data export `ordinal` (1–19; 0 otherwise): programs linked by `lx-link`, whose imports are call thunks, reach the data exports through it (the SDK's `somapi.h` makes each name a macro for the variable);
  - `WrpSomInitCtrlNew(cls)` / `WrpSomInitCtrlFree(ctrl)` (Warpine's, 3091 / 3092): a control block of Warpine's initializer protocol for an instance of ready class `cls` (0 otherwise), and its release;
  - `WrpSomInitWalk(obj)` / `WrpSomDestructWalk(obj, doFree)` (Warpine's, 3093 / 3094): the protocol run by the kernel for `obj`'s class (below);
  - `somSetException(ev, major, exceptionName, params)`, `somExceptionId(ev)`, `somExceptionValue(ev)`, `somExceptionFree(ev)` (3096–3099, by name; IBM's ordinals unknown): an `Environment`'s exception — `_major` (`NO_EXCEPTION`, `USER_EXCEPTION`, `SYSTEM_EXCEPTION`), the name kept as given and the value (from `SOMMalloc`), owned by the `Environment` until `somExceptionFree` (which frees it and clears the `Environment`; setting another exception frees the one there); the id and value are 0 when there is none;
  - `somMainProgram()` (3100, by name) gives the runtime, as `somEnvironmentNew`; `somEnvironmentEnd()` (3101) has nothing to release; the SDK's `somapi.h` adds `SOM_MainProgram`, `SOM_Test`, `SOM_TestC`, `SOM_Expect`, `SOM_Assert` and `SOM_WarnMsg`;
  - `WrpSomSetDirectInitClasses(cls, n, names)` (Warpine's, 3095): the ancestors `cls`'s initializers visit, in that order, instead of its parents (`directinitclasses`; each must be an ancestor; 0 for success, 1 otherwise).
- Data:
  - `SOMObjectClassData`, `SOMClassClassData` and `SOMClassMgrClassData`, the root classes' `ClassData`: the class object, then one token per method in IBM's release order (32, 76 and 22 tokens, ADR-0072), as programs built with IBM's SOM headers read them;
  - `SOMObjectCClassData`, `SOMClassCClassData` and `SOMClassMgrCClassData`: `parentMtab`, a `somParentMtabStruct` (the class's own method table, `next` → the list of its parents' tables, the class object, the renew thunk 0, the instance size, the rest 0), then the instance-data token; `SOMObjectCClassData` then holds six `somDispatch*` procedures (not implemented);
  - `SOMClassInitFuncName`: a variable holding a procedure that returns "SOMInitModule", the name of a class library's initialization function;
  - `SOMClassMgrObject`;
  - `SOMMalloc`, `SOMCalloc`, `SOMRealloc`, `SOMFree`: variables holding the runtime's allocation procedures (which call `SOMError` with `SOMERROR_OutOfMemory`, 20099, when they cannot allocate; `somAllocate` / `somDeallocate` go through these variables, a program's replacements included) (zeroed blocks from the runtime's heap), called through as `SOMMalloc(n)`;
  - `SOM_TraceLevel`, `SOM_WarnLevel`, `SOM_AssertLevel` (`long`, 0);
  - `SOMOutCharRoutine(c)` — `somPrintf` writes its output through it, one character per call; `somSetOutChar(routine)` sets the calling thread's own routine instead, which comes first (0: the default, which writes to standard output); `somPrintSelf` and `somDumpSelf` write through the same routine;
  - `SOMLoadModule(className, fileName, functionName, major, minor, &handle)` — loads a class's DLL, runs its `_DLL_InitTerm`, calls its `functionName` (`SOMInitModule(major, minor, className)`) or else `<className>NewClass(major, minor)`, stores the module handle and returns 0 (`ERROR_MOD_NOT_FOUND`, `ERROR_INIT_ROUTINE_FAILED`, or `ERROR_PROC_NOT_FOUND` when the DLL has neither entry point; it stays loaded);
  - `SOMDeleteModule(handle)` — `DosFreeModule`;
  - `SOMError(code, file, line)` — writes `SOM error <code> in file <file>, line <line>` to standard error and ends the process when the code's last digit is 9.

  A program may store its own procedures in these four variables.
- Root classes:
  - `SOMObject`: `somInit`, `somUninit`, `somFree`, `somGetClass`, `somGetClassName`, `somGetSize`, `somIsA`, `somIsInstanceOf`, `somRespondsTo`, `somPrintSelf` (`{An instance of class C at address A}`), `somDumpSelf(level)` (that line, then `somDumpSelfInt`), `somDumpSelfInt`, `somDefaultInit(ctrl)` (calls `somInit`; the control block is not used), `somDestruct(doFree, ctrl)` (calls `somUninit`, then frees the object if `doFree`);
  - `SOMClass`: `somNew`, `somNewNoInit`, `somGetName`, `somGetParent`, `somGetInstanceSize`, `somGetInstancePartSize`, `somGetInstanceToken`, `somGetNumMethods`, `somGetNumStaticMethods`, `somDescendedFrom`, `somInitClass`, `somAddStaticMethod`, `somOverrideSMethod`, `somClassReady`, `somGetMethodToken`, `somSupportsMethod`, `somInitMIClass` (several parents, given as a sequence);
  - `SOMClassMgr`: `somFindClass(id, major, minor)` (a registered class, else its DLL loaded through `SOMLoadModule`: the file named after the class, the function the one `SOMClassInitFuncName` returns — a program's replacement is called; either way NULL when the class does not meet the version, by `somCheckVersion`'s rule), `somFindClsInFile(id, major, minor, file)`, `somLocateClassFile` (the class's name), `somLoadClassFile` (loads even a registered class), `somClassFromId` (registered classes only), `somRegisterClass`, `somUnregisterClass(cls)` (unregisters the class and frees its object; a class loaded from a file is unloaded with its file's classes; 0, or 1 if it was not registered; the root classes stay), `somUnloadClassFile(cls)` (frees every class the module of `cls` made, whose objects then resolve no method, and frees the module through `SOMDeleteModule`; a class no file made is freed alone, 0; an unregistered class raises `SOMERROR_NotRegistered`, 20159). When a program's class manager overrides `somLocateClassFile`, `somFindClsInFile` or `somLoadClassFile`, the lookup of a class not registered goes through those methods (`somFindClass` → `somLocateClassFile` → `somFindClsInFile` → `somLoadClassFile`).
- Building a class (as the C bindings of `samples/som_test` do):
  1. `_somNew(WrpSomMetaclassFor(requestedMetaclass, parent))` — a class object is an instance of its metaclass and carries the metaclass's instance data; the metaclass's `somInit` runs on it;
  2. `_somInitClass(cls, name, parent, instanceDataSize, maxMethods, major, minor)` or `_somInitMIClass`;
  3. `_somAddStaticMethod` per new method (its token), `_somOverrideSMethod` per override;
  4. `_somClassReady(cls)`, after which the class takes no more methods and `somNew` makes instances.
- `somNew` calls the new object's `somDefaultInit` (by default its `somInit`); `somFree` calls its `somDestruct` with doFree set (by default its `somUninit`, then the memory goes); all may be the program's overrides. `somIdFromString` gives the caller an id of its own, which it may free with `SOMFree`. `somGetNumStaticMethods` counts inherited methods too.
- Method tables (ADR-0072) have IBM's `somMethodTab` header — `classObject`, `classInfo` (0), `className`, `instanceSize`, `dataAlignment` (4), `mtabSize` (bytes, header included), `protectedDataOffset`, `protectedDataToken`, `embeddedObjs` (0) — then the procedures in token order.
- `SOMClass`'s `somRenew`, `somRenewNoInit`, `somRenewNoZero`, `somRenewNoInitNoZero(obj)` make an instance in the caller's memory at `obj` (zeroed unless NoZero, initialized as by `somNew` unless NoInit); `somGetMemberToken(offset, instanceToken)` a data token for a member of a class's part; `somGetMethodIndex(id)` a method's place in the class's table (-1 when none); `somGetNthMethodInfo(n, &descriptor)` its somId; `somGetMethodData(id, &md)` / `somGetNthMethodData(n, &md)` fill a `somMethodData` (id, type 0, descriptor 0, token, procedure, 0); `somGetMethodDescriptor` gives 0 (no descriptors are kept). `SOMObject`'s `somCastObj(cls)` makes the object answer as ancestor `cls` (its method table) until `somResetObj`, which is always TRUE. `SOMClassMgr`'s `somGetInitFunction` gives `SOMClassInitFuncName`'s name.
- `somGetParents` (the parents, left to right) and `_get_somInstanceDataOffsets` (each class's instance data offset, `SOMObject` first, the class last) return a sequence by value: the caller's buffer is a hidden first argument that the caller removes, as Open Watcom's `_System` passes it; the sequence's buffer comes from `SOMMalloc` (NULL when empty). From C with the SDK, `_somGetParents(cls)` / `__get_somInstanceDataOffsets(cls)` pass the buffer for GCC and clang. `somGetRelatedClasses(cls)` returns the class's affinity group, a NULL-terminated array to `SOMFree`: the class whose lookup loaded its module, then the module's classes newest first; NULL for a class no class file made.
- **The class manager's registry** (SOM Programming Reference): `somSubstituteClass(mgr, origClassName, newClassName)` makes `somFindClass`, `somFindClsInFile` and `somClassFromId` give the new class whenever they would give the original, and points the original's `ClassData.classObject` at it, so `<orig>New()` makes instances of the new class; both must be registered and the new one an immediate child (0, else `SOMERROR_NotRegistered` / `SOMERROR_NoParentClass`), and a class unregistered takes its substitution along. `SOM_SubstituteClass(Old, New)` makes both classes first. `somMergeInto(receiver, target)`: another class manager takes over (`SOMClassMgrObject`, when the receiver was it); the registry is the kernel's, so nothing needs copying, and a target that is no `SOMClassMgr` changes nothing. `_get_somRegisteredClasses` returns every registered class as a sequence by value (free its buffer with `SOMFree`); `_get_somInterfaceRepository` is NULL (there is none) and setting it does nothing. Warpine's own ordinals 3410–3414 (ADR-0123).
- **Dynamic dispatch** (ADR-0126): `somDispatch(retValue, methodId, ap)` calls the method named `methodId`, as the receiver's class resolves it, with the arguments of `ap` (the target object first, each argument widened as in a C `va_list`), its result to `retValue` (NULL for none); `somClassDispatch(clsObj, …)` resolves it on `clsObj`'s class; both return FALSE for an unknown method or one that cannot be applied. `somDispatchV` / `L` / `A(methodId, descriptor, ap)` call the object's own `somDispatch` and return its result (`somDispatchD`, whose `double` comes back in the FPU, is not implemented). `somApply(objPtr, retVal, mdPtr, args)` calls the method a `somMethodData` (from `somGetMethodData` / `somGetNthMethodData`) names. A method is applied through the apply stub its class's bindings registered — `somidl` writes one for every method, Warpine's own protocol — or, for a root method, directly; a method of a class built with IBM's tools has none, so `somApply` and `somDispatch` return FALSE for it. `somVaBuf_create` / `somVaBuf_add` (the Reference's TCKinds, widened; at most 64 KB) / `somVaBuf_get_valist` / `somVaBuf_destroy` build a `va_list`; `somvalistGetTarget` / `somvalistSetTarget` read and replace its first word. A `va_list` may be GCC's or Open Watcom's form. The SDK has `_somDispatch` / `_somClassDispatch` (varargs) and `SOMObject_somDispatch…` (va_list).
- **TypeCodes** (ADR-0128): `TypeCodeNew(kind, …)` takes the arguments the Reference gives for each kind — `tk_objref` an interface id; `tk_string` a bound (0: none); `tk_sequence` / `tk_array` an element TypeCode and a bound / length; `tk_pointer` a TypeCode; `tk_self` the name of an enclosing struct or union; `tk_foreign` a type name, a context and a size; `tk_struct` a name, then name / TypeCode pairs and NULL; `tk_union` a name, a discriminator TypeCode, then `TCREGULAR_CASE` / `TCDEFAULT_CASE`, label, name, TypeCode for each member and NULL; `tk_enum` a name, the enumerators and NULL; the basic kinds nothing — and returns NULL for anything else, a bad argument, or past the limits (32 deep, 1,024 members). It copies the strings and takes the TypeCodes it is given (one already held, or given twice, is copied); `TypeCode_free` frees those with it, and does nothing for a constant or a held TypeCode. `TypeCode_kind`, `_param_count` (Table 1: struct `2N+1`, union `3N+2`, enum `N+1`, …), `_size` and `_alignment` (the SDK's i386 C layout: `double` 8 bytes aligned to 4, a sequence 12, `any` 8), `_setAlignment` (a power of two up to 64; the size stays), `_equal` (kind, parameters, alignment), `_copy` (a TypeCode sharing nothing but constants), `_print` (the `TypeCodeNew` call, through `SOMOutCharRoutine`). `TypeCode_parameter(tc, ev, i)` returns an `any` whose `_type` is `TC_long`, `TC_string` or `TC_TypeCode` and whose `_value` points into the TypeCode (do not free it); out of range it raises `ex_TypeCode_Bounds` (`::TypeCode::Bounds`) in `ev`. The `TC_*` constants (each basic kind, `TC_Object`, `TC_string`) are shared and never freed. A TypeCode lives in guest memory, but the kernel answers from its own records. Warpine's own ordinals 3109–3120; the SDK's `TypeCode_parameter` is inline over `WrpTypeCode_parameter(result, tc, ev, i)` and the constants are macros over `WrpTypeCodeConstant(kind)`.
- Root methods of the release order Warpine does not implement (`somDispatchD`, the private slots, the class manager's repository and class-library methods) raise `SOMERROR_NotImplementedYet` with the Ignore severity (20171; IBM's 20179 is fatal) through `SOMError` and return 0. `SOMClass` also has `somCheckVersion` (same major version, at least the minor one; 0.0 asks for nothing; the root classes are 1.5), `somGetVersionNumbers`, `somFindMethod` / `somFindMethodOk`, `somFindSMethod` / `somFindSMethodOk`, `somLookupMethod` (the `…Ok` forms and `somLookupMethod` raise `SOMERROR_MethodNotFound`, 20039), `somGetClassMtab`, `somGetInstanceOffset`, `somAllocate` / `somDeallocate`. Errors the kernel raises go to a program's own `SOMError` (file `som.dll`), else to the default one.
- `somBuildClass(inheritVars, sci, major, minor)` (by name; ADR-0073) builds the class a `somStaticClassInfo` describes, as code from IBM's SOM compiler asks: layout versions 1–4; returns the class `ClassData.classObject` already names; parents and an explicit metaclass by name (`SOMERROR_NoParentClass` 20219, `SOMERROR_NoMetaClass` 20229; a malformed structure `SOMERROR_BadArgument` 20199); static methods (`smt`, and `mt`'s static, dynamic and nonstatic ones) with their tokens written into `ClassData`; overrides by name (`omt`, a scoped `Class::method` by its last part) and by token (`mt` action 6); a parent's implementation (`imt`, parents from 1); public data tokens (`nit`: the field at `basisForDataOffset − nitReferenceBase`, resolved by `somDataResolve`); procedure and `va_list` entries (`pmt`, `vft`); then `ClassData.classObject`, `CClassData.parentMtab` (a `somParentMtabStruct`) and `instanceDataToken`, and last the class init function. `inheritVars`, initializers, direct-init classes, DirectToSOM classes, migrated methods and `somDynamicSCI` are not used yet.
- Warpine's initializer and destructor protocol (ADR-0122; not IBM's, whose control-block layout is unpublished):
  - each ready class has a table of `somInitInfo` entries (`somapi.h`; 16 bytes: the class, the `somDefaultInit` it introduced or overrode or 0, the same for `somDestruct`, its data's offset in the instance): its ancestors once each, parents left to right with each one's ancestors first, the class itself last;
  - a `somInitCtrl` (16 bytes: the mask, the table, the entry size, the count; the mask's bytes follow) flags every entry but the class's own;
  - the SDK's `SOM_InitBegin` runs a class's flagged ancestors before it, in order; `SOM_DestructEnd` runs those before it last first, then frees the object when doFree is set. An initializer or destructor called without a control block for an object of a descendant class (one inherited) hands the walk to `WrpSomInitWalk` / `WrpSomDestructWalk`;
  - those run every entry's own initializer in order (`SOMObject`'s as the object's `somInit`), or destructor last first (`SOMObject`'s as `somUninit`), with a new block whose flags are cleared, then free it (and the object for doFree). With nothing but `SOMObject`'s in the table they are `SOMObject`'s `somDefaultInit` / `somDestruct`;
  - `SOMObject`'s own `somDefaultInit` / `somDestruct` are unchanged (`somInit`; `somUninit`, then the memory for doFree), so a class's destructor may still call its parent's with the null block it got;
  - `SOMObject`'s copy and assign initializers (`somDefaultCopyInit`, `somDefaultConstCopyInit`, `somDefaultVCopyInit`, `somDefaultConstVCopyInit`; `somDefaultAssign` and its three variants, which return the object): with a control block (as an entry of the protocol) they do nothing, `SOMObject` having no data; without one, a shallow copy of the whole instance from an object of the same class or a descendant (Warpine's default).
- C++ (`samples/som_test/include/som.xh`, ADR-0061): a SOM class is a C++ class without virtual functions; `new Cls` makes the object with `somNewNoInit` and its constructor initializes it once with `somDefaultInit`; `delete` calls `somDestruct(1)`. Methods dispatch through SOM, so an override is reached through a base-class pointer. Objects on the stack or in static storage are not SOM objects.

- Tokens: a method token names a method and its introducing class, and works on every descendant; `somGetInstanceToken` returns the class itself, and `somDataResolve(obj, cls)` finds that class's data in any descendant's object (`somDataResolveChk`: 0 if it has none).
- Multiple inheritance: a class's methods start with its first parent's; later parents add what it lacks, and a later parent's override replaces an implementation the earlier ones left at the introducer's. Each ancestor's data appears once. `somGetParent` returns the first parent.

Module names: imports and plain names given to `DosLoadModule` or SOM are searched beside the program and in `C:\OS2\DLL`; a full OS/2 path (`C:\LIBS\X.DLL`) is resolved through Warpine's drives, inside them only, and the module is named after its file (`X`). Exports by name are found in both names tables of a DLL. A program whose DLL's `_DLL_InitTerm` fails at start ends with `ERROR_INIT_ROUTINE_FAILED` (295) before it runs. Programs run at ring 3, as on OS/2, 32-bit and 16-bit alike (ADR-0113): privileged instructions (`CLI`, `HLT`, port I/O, moves to control registers …) raise `XCPT_PRIVILEGED_INSTRUCTION`, and a program cannot reach its page tables, the GDT, IDT or its TSS (`XCPT_ACCESS_VIOLATION`), nor have an API call write them for it (the call fails as with any address it cannot write). A process can have at most 736 threads at once (ADR-0115); `DosCreateThread` beyond that fails with `ERROR_MAX_THRDS_REACHED` (164), as at the session's `THREADS=` limit. `DosAllocMem` memory is zero, also when reused. It follows OS/2's page states (ADR-0114): without `PAG_COMMIT` its pages are reserved and fault until `DosSetMem` commits them (zeroed); `PAG_READ` without `PAG_WRITE` makes them read-only; `PAG_DECOMMIT` takes them back; `PAG_GUARD` makes guard pages, whose first touch raises `XCPT_GUARD_PAGE_VIOLATION` (continuable; with no handler the program goes on). `DosQueryMem` reports the run of pages with one state, `PAG_BASE` on an allocation's first page; on other memory it reports what the page tables hold: `PAG_FREE` for free pages, committed, read-only and `PAG_EXECUTE` for a program's code. A program's or DLL's object without the LX write flag (its code, its resources) is read-only: writing it raises `XCPT_ACCESS_VIOLATION`, also at ring 0. Memory freed with `DosFreeMem`, and memory never allocated, raises `XCPT_ACCESS_VIOLATION` when touched. `DosSetMem` on memory `DosAllocMem` did not allocate changes nothing. A thread's stack is sparse (`STACK_SPARSE`, the default): committed as it is used, and `XCPT_UNABLE_TO_GROW_STACK` near its bottom; `STACK_COMMITTED` commits it whole. The main thread's stack, the LX header's `STACKSIZE` below the entry ESP, is sparse the same way, and its TIB holds its bounds; `DosFreeModule` of a handle of no loaded module returns `ERROR_INVALID_HANDLE`.

Not yet available: SOM objects on the stack in C++, the initializer control blocks, `somBuildClass`, `SOMError` / `SOMOutCharRoutine`.

### REXX and REXXAPI — the REXX API (29 APIs, ADR-0085)

`REXX.DLL` and `REXXAPI.DLL` are built in, on Warpine's own REXX interpreter (the one the built-in CMD.EXE runs scripts with). The ordinals are those of Open Watcom's `rexx.lib`; `<rexxsaa.h>` declares the calls.

- **REXX:** RexxStart (1), RexxVariablePool (2), RexxSetHalt (3), RexxSetTrace (4), RexxResetTrace (5).
- **REXXAPI:**
  - queues: RexxCreateQueue (1), RexxDeleteQueue (2), RexxAddQueue (3), RexxPullQueue (4), RexxQueryQueue (5);
  - subcommand handlers: RexxRegisterSubcomDll (6), RexxRegisterSubcomExe (7), RexxQuerySubcom (8), RexxDeregisterSubcom (9);
  - system exits: RexxRegisterExitDll (11), RexxRegisterExitExe (12), RexxDeregisterExit (13), RexxQueryExit (14);
  - external functions: RexxRegisterFunctionDll (17), RexxRegisterFunctionExe (18), RexxDeregisterFunction (19), RexxQueryFunction (20).
- **Stubs (no macro space):** RexxAddMacro (22), RexxDropMacro (23), RexxClearMacroSpace (24), RexxLoadMacroSpace (25), RexxQueryMacro (26), RexxReorderMacro (27), RexxSaveMacroSpace (28): nothing is stored, nothing is found.

**RexxStart** runs a program in storage (`instore[0]`) or from a file (`procname`, with `.CMD` added when it has no extension, in the current directory or on the `PATH`), with its arguments, a call type (`RXCOMMAND` takes at most one argument), an initial ADDRESS environment (`CMD` by default) and a list of system exits. It returns 0 when the program ran, or minus the REXX error number when an error ended it, with the error written to standard error as the shell writes it. `retc` takes the result when it is a whole number from -32768 to 32767 (else 0). `result` takes the result string: in the caller's buffer when it is large enough, else in new memory the caller frees with `DosFreeMem`. A tokenized image (`instore[1]` alone) and the macro space are not supported (-3).

**While a program runs:**
- `SAY` writes to the program's standard output, `TRACE` to its standard error, and `PULL` reads its standard input, wherever those handles lead.
- `ADDRESS CMD` runs the command in the built-in shell, as `DosExecPgm("CMD.EXE")` does.
- An environment with a registered subcommand handler goes to the handler. RC takes its return string; `RXSUBCOM_ERROR` / `RXSUBCOM_FAILURE` raise ERROR / FAILURE.
- A function not found in the program, among the built-in functions or in REXXUTIL goes to a registered function handler, with `SESSION` as the queue name. A non-zero return is Error 40, and no result string is no value.
- The handlers are the program's own code, called on the thread that called RexxStart. A `…Dll` registration's entry point is looked up by name among the modules the program has loaded when it is called.

**System exits** (`RXSYSEXIT` list; names registered with `RexxRegisterExit…`):
- `RXINI` before the first clause and `RXTER` after the last (both may use the variable pool);
- `RXSIO`: `RXSIOSAY` (SAY's line), `RXSIOTRC` (a trace line), `RXSIOTRD` (a line of input);
- `RXHLT`: `RXHLTTST` after each clause, halting the program when it sets the flag.

`RXEXIT_NOT_HANDLED` lets the interpreter do the default; `RXEXIT_RAISE_ERROR` is Error 48. The other exits (`RXFNC`, `RXCMD`, `RXMSQ`, `RXTRC`) are accepted and never called.

**RexxVariablePool**, from inside a handler or exit of the thread's running program:
- **Codes:** `RXSHV_SET`, `FETCH`, `DROPV` (names as they are: upper case, a compound tail taken literally), `SYSET`, `SYFET`, `SYDRO` (symbols, the tail's variables substituted), `NEXTV` (each variable in turn, then `RXSHV_LVAR`) and `PRIV` (`PARM`, `PARM.n`, `SOURCE`, `VERSION`, `QUENAME`).
- **Values back.** A value goes into the SHVBLOCK's buffer (`RXSHV_TRUNC` when it is too short), or into new memory when it has none.
- **Results.** `RXSHV_NEWV`, `BADN`, `BADF` and `MEMFL` report as `<rexxsaa.h>` describes, and the call returns all the blocks' flags together. Outside a handler it returns `RXSHV_NOAVL`.

**Queues.** Each process has the `SESSION` queue: the running program's PUSH, QUEUE and PULL use it, and so do `RexxAddQueue` / `RexxPullQueue` before, between and after programs. `RexxCreateQueue` makes a named queue, or a new name when the requested one is taken (`RXQUEUE_DUP`). `RexxPullQueue` can wait (`RXQUEUE_WAIT`). The queues and registrations belong to the process, not to the system.

**Others.** `RexxSetHalt(pid, tid)` halts the programs a thread of this process runs (HALT). `RexxSetTrace` / `RexxResetTrace` turn tracing to `?R` / `O`.

### PMWP — the Workplace Shell (6 APIs, ADR-0086, ADR-0129, ADR-0130)

WinQueryObject (252): the handle of the stored Workplace object an object ID (`"<NAME>"`) names, from the user profile where the SDK's `WPAbstract` maps it; NULLHANDLE when it names none or the object is no longer stored (a file-system path names no object yet).

WinCreateObject (281), WinSetObjectData (250), WinDestroyObject (251): the host keeps no Workplace objects (their classes are the programs' own, `libwps`), so `WinCreateObject(class, title, setup, location, flags)` gives a handle at once and records the class with the title and setup string queued; a program that has the class makes the object when it asks for it (`wpclsQueryObject`: `wpSetupOnce` with what was queued), in that process or a later one. An object ID in the setup string that a stored object has already: `CO_FAILIFEXISTS` (0, and any unknown flag) gives NULLHANDLE, `CO_UPDATEIFEXISTS` (2) queues for that object and gives its handle, `CO_REPLACEIFEXISTS` (1) destroys it first. The class name must be 1–255 characters; the location is not used yet; a title's trailing carets are dropped. `WinSetObjectData(h, setup)` queues the string for a stored object (FALSE for none), applied with `wpSetup` when the object is next asked for. `WinDestroyObject(h)` removes the object's record, queue and IDs (FALSE when there is none); a process holding it awake keeps its copy until it frees it.

WinStoreWindowPos (207), WinRestoreWindowPos (208): a window's position, size and state (and a frame's normal and icon positions) are kept in the user profile under an application and key name, in Warpine's own record. Restoring a minimized or maximized frame sets its normal position, then the state. Presentation parameters are not kept. The rest of PMWP (Workplace Shell objects) is not built in.

**Workplace Shell classes** (ADR-0129) are not part of PMWP: they are SOM classes in the SDK's `libwps.a`, linked into a program built with GCC or clang (`$(OS2_LIBWPS)` before `$(OS2_LIBC)`; `#include <os2.h>` before `<wpobject.h>`; a class derived from them includes `<wpobject.idl>`). `WPObject` and `M_WPObject` have their first part, with the Reference's signatures (OIDL: no `Environment`):
- `wpclsNew(cls, title, setup, folder, lock)` makes an object of a class derived from `WPObject` (NULL for `WPObject` itself): `somNew` (which calls `wpInitData`), the title (the class's `wpclsQueryTitle`, by default its name, when none is given), the class's `wpclsQueryStyle` as its style, a lock when asked, `wpSetupOnce` (by default `wpSetup`; NULL and the object freed when it fails). `wpclsQueryDefaultView` is `OPEN_SETTINGS` by default; `wpclsInitData` runs when the class object is made, `wpInitData` / `wpUnInitData` when an object is made and freed, however it is.
- `wpSetup` reads `TITLE`, `OBJECTID` (`<NAME>`), `DEFAULTVIEW` (`SETTINGS`, `DEFAULT` or a digit, `OPEN_USER` + it) and `YES` / `NO` for `NOCOPY`, `NODELETE`, `NODRAG`, `NODROP`, `NOLINK`, `NOSHADOW`, `NOMOVE`, `NOPRINT`, `NORENAME`, `NOSETTINGS`, `NOTVISIBLE`, `TEMPLATE` and `LOCKEDINPLACE`; other keys are accepted and not used yet. `wpScanSetupString(obj, setup, key, value, &cb)` finds a key (any case; `^;` a semicolon; its last occurrence): NULL `value` gives the size, a buffer too small FALSE and the size.
- `wpSetTitle` (under 256 characters) / `wpQueryTitle`, `wpSetStyle` / `wpQueryStyle`, `wpSetDefaultView` / `wpQueryDefaultView` (the class's while it is `OPEN_DEFAULT`), `wpSetObjectID` / `wpQueryObjectID`, `wpSetError` / `wpQueryError`, `wpLockObject` / `wpUnlockObject` / `wpIsLocked`, `wpIsObjectInitialized`, `wpQueryFolder`.
- `wpAllocMem` / `wpFreeMem`: blocks freed with the object at the latest.
- `wpSaveString` / `wpSaveLong` / `wpSaveData` keep a value with the object by class name and key; `wpRestoreString` / `Long` / `Data` give it back (a NULL buffer the size; a buffer too small FALSE). `wpSaveImmediate` and `wpSaveDeferred` call `wpSaveState`; `WPObject`'s own `wpSaveState` / `wpRestoreState` keep nothing yet. Nothing reaches OS2.INI yet.
- `wpDelete(obj, flags)`: `wpConfirmDelete` (`NO_DELETE` for `OBJSTYLE_NODELETE`; no dialog), then `wpFree`, which frees the object.
- `WPObject`'s `wpSaveState` keeps its title, style, default view and object ID; its setters call `wpSaveDeferred` once the object is initialized.
- **`WPAbstract`** (`<wpabstract.h>`, `wpabstract.idl`): its objects are kept in the user profile — written when `wpclsNew` has made them and at every `wpSaveImmediate` / `wpSaveDeferred`, removed by `wpFree` (`somFree` makes one dormant and keeps it). `wpQueryHandle` gives the handle (NULLHANDLE for an object without storage); an object ID names one object (`wpSetObjectID` refuses one another stored object has). `wpclsQueryObject(cls, handle)` gives the awake object, or awakens the stored one (its class must be registered: make it first) with `wpRestoreState`.
- **`WPTransient`** (`<wptrans.h>`): objects never stored (`wpSaveImmediate` writes nothing).
- **`WPFileSystem`** (`<wpfsys.h>`) and **`WPDataFile`** (`<wpdataf.h>`): `wpclsQueryObjectFromPath(cls, path)` gives the object of a file or directory (a relative name is qualified first; an object ID goes through `WinQueryObject` and `wpclsQueryObject`), the same awake object for the same path in any case, locked; a new one is of the class its `WARPINE.WPSTATE` EA names when that class is registered and a `WPFileSystem`, else `WPDataFile` for a file; a directory's is a `WPFolder`. Its title is the file's name, or its `.LONGNAME` EA. `wpQueryRealName(obj, buf, &cb, qualified)` (NULL `buf`: the size; too small: FALSE and the size), `wpQueryFilename`, `wpSetRealName` (renames the file in its directory), `wpQueryAttr` / `wpSetAttr`, `wpQueryFileSize`, `wpQueryEASize`, `wpQueryCreation` / `LastAccess` / `LastWrite` (0, or the error), `wpQueryType` / `wpSetType` (the `.TYPE` EA, types separated by `\n`; `pfeal` more EAs to set), `wpQueryEASupport` (`NO_ERROR`), `wpRefresh` (the title read again). Changing an initialized object's title renames its file (characters a name cannot hold become `_`; the title goes to `.LONGNAME` when it differs from the name); `wpSaveImmediate` writes `WARPINE.WPSTATE` (the class and saved values); `wpFree` deletes the file (an empty directory) and then the object; `somFree` leaves the file. `wpclsNew(cls, title, setup, folder, lock)` makes a new file (a directory for a `WPFolder` class) in `folder`, named by the title (`_` for characters a name cannot hold), and adds it to the folder's content; NULL without a folder or for a name it has. `wpQueryFolder` gives the folder of the file's directory (unlocked; NULL for a root). `WPDataFile`'s class title is "Data file".
- **`WPFolder`** (`<wpfolder.h>`): `wpPopulate(folder, 0, NULL, foldersOnly)` adds the objects of the directory's entries to the content list, each locked (`wpQueryFldrFlags`: `FOI_POPULATEDWITHALL`, `FOI_POPULATEDWITHFOLDERS`; populating again adds nothing); `wpQueryContent(folder, obj, QC_FIRST | QC_NEXT | QC_LAST)`; `wpAddToContent` / `wpDeleteFromContent`; `wpContainsFolders(folder, &flag)`; `wpDeleteContents(folder, flags)` deletes every object (`NO_DELETE` when one is refused). `wpFree` on a folder deletes its contents first, then the directory. `wpclsQueryFolder(cls, location, lock)` gives the folder a path or object ID names (locked when `lock`). The class title is "Folder".
- `wpclsQueryObject` and `wpclsQueryObjectFromPath` return the object locked (the Reference): unlock it with `wpUnlockObject` when done.
- Make a class (`<Class>NewClass`, or `_Class` alone) before calling its class methods: `_wpclsNew( _Card, … )` may read the method's token before `_Card` makes the class.

### WARPINE — Warpine's own extensions (9 APIs)

`WARPINE.DLL` is not an OS/2 module: a program that can be recompiled loads it with `DosLoadModule("WARPINE")` (which fails on OS/2, so it can fall back) and finds the calls with `DosQueryProcAddr` by name or ordinal. They are `_System` (`APIENTRY`) calls returning an `APIRET`, and they take a signed 64-bit count of seconds since 1970-01-01 00:00 UTC (`long long`) on the session clock:

| Ordinal | Call | Does |
|--------:|------|------|
| 1 | `WrpTime64(long long *ptime)` | the current time |
| 2 | `WrpGetDateTime64(DATETIME *pdt, long long *ptime)` | the current time as a local `DATETIME` and as seconds, from one reading |
| 3 | `WrpLocalTime64(const long long *ptime, DATETIME *pdt)` | seconds → local `DATETIME` (hundredths 0) |
| 4 | `WrpMakeTime64(const DATETIME *pdt, long long *ptime)` | local `DATETIME` → seconds (hundredths, weekday and time zone ignored) |
| 5 | `WrpBuiltinWindowProc(HWND, ULONG, MPARAM, MPARAM)` | the window procedure of the built-in classes; programs get its address from `WinSubclassWindow`, `WinQueryWindowPtr(QWP_PFNWP)` or `WinQueryClassInfo` (see Subclassing) |
| 7 | `WrpRegisterUnwindTables(PVOID pBegin)` | the C++ unwind tables at `pBegin` (`.eh_frame` records ending with a zero word) belong to the module holding `pBegin` (ADR-0107); `ERROR_INVALID_ADDRESS` outside every module |
| 8 | `WrpDeregisterUnwindTables(PVOID pBegin)` | forget them (freeing the DLL also does) |
| 9 | `WrpQueryUnwindTables(PVOID pCode, PVOID *ppBegin)` | the tables of the module whose code holds `pCode`; `ERROR_INVALID_ADDRESS` when it registered none |
| 10 | `WrpQueryRuntimeBlock(PULONG *ppBlock)` | the calling thread's runtime block: 64 bytes every module of the process shares on that thread, zero when it starts, at the same address on every thread; words 0–1 are the SDK's C++ runtime's |

A null pointer, or a time whose year is outside 1–9999, is `ERROR_INVALID_PARAMETER`; a `DATETIME` that names no real date or time is `ERROR_TS_DATETIME`. Sample: `datetime_test`.

Ordinals 7–10 serve the SDK's run-time libraries, which import them directly (`os2/warpine.h`); sample: `cxx_test` with `cxxdll.dll`.

### PMWIN (218 APIs)

**Tracking (ADR-0089, `pm_track.rs`):** WinTrackRect (890), WinShowTrackRect (882). `WinTrackRect` tracks the `TRACKINFO` rectangle on the calling thread until the user accepts (TRUE) or cancels (FALSE), and leaves the rectangle in `rclTrack`:
- **Pointer:** the call captures the pointer for `hwnd`; pointer moves move the edges `fs` names (`TF_LEFT` / `TF_TOP` / `TF_RIGHT` / `TF_BOTTOM`, `TF_MOVE` all four), and releasing the button that was down accepts.

- **Messages:** messages other programs send the thread are run meanwhile; other queued messages wait, and `WM_QUIT` cancels.
- **Warpine's own choices (unverified):**
  - `rclTrack` holds the starting rectangle after a cancel;
  - a nested tracking fails;
  - with no button down, the next button press and its release end the tracking;

**Other programs' windows.** On the session's desktop (ADR-0052) every window handle names its program, so a program can work on another program's windows (ADR-0053): `WinIsWindow`, `WinQueryWindowProcess`, `WinQueryWindowPos`, `WinQueryWindowRect`, `WinQueryWindowText` / `WinQueryWindowTextLength` (in the caller's codepage), `WinIsWindowVisible`, `WinIsWindowEnabled`, `WinQueryClassName`, `WinQueryWindowULong` / `WinQueryWindowUShort`, `WinQueryWindow`, `WinPostMsg` (parameters passed as they are), `WinSetWindowText`, `WinSetWindowPos`, `WinShowWindow` and `WinSetActiveWindow`. Each call goes through the desktop server to the program that owns the window and waits at most 5 s for its answer; one that gets none fails with `PMERR_INVALID_HWND`. `WinSendMsg` to another program's window (ADR-0054) runs the window procedure on the window's thread when that thread next reads or waits for messages (`WinGetMsg`, `WinPeekMsg`, `WinWaitMsg`, a modal loop, its own `WinSendMsg`; `WinInSendMsg` is TRUE there) and returns its result; the sender waits as long as that takes and meanwhile runs the messages other programs send to its own queue. It fails (0, `PMERR_INVALID_HWND`) when the window, its queue or its program goes away first. The send hooks of the window's queue run on the receiving thread first (`fInterTask` TRUE). `WinQueryActiveWindow` names another program's frame while it is the active window. Minimizing, maximizing or restoring another program's frame asks its client with `WM_MINMAXFRAME` on the frame's thread (TRUE keeps the frame as it is), and the caller waits for that as for a send (ADR-0055). `WinBroadcastMsg` to the desktop (and with `BMSG_POSTQUEUE`) reaches every program's windows; the sends it makes to other programs are not waited for. `WinDestroyWindow` fails on another program's window, as on another thread's.

**Window lists.** `WinBeginEnumWindows(hwnd)` takes a snapshot of `hwnd`'s children, top first; `WinGetNextWindow` returns them one at a time and NULLHANDLE at the end, skipping this program's windows destroyed since; `WinEndEnumWindows` frees it (an unknown handle: `PMERR_INVALID_HENUM`). The desktop's children are the windows of every program on the session's desktop — frames in the session's stacking order, then each program's other windows —, another program's window lists its children, `HWND_OBJECT` the program's object windows. At most 64 enumerations may be open at once (`PMERR_HEAP_OUT_OF_MEMORY`).

**Atoms and DDE.** Atom tables (`WinCreateAtomTable`, `WinAddAtom`, …) hold string atoms from 0xC000 with usage counts; names are compared without regard to case, 1 to 255 bytes; integer atoms (`MAKEINTATOM(n)` or `"#n"`, 1 to 0xBFFF) stand for themselves (name `"#n"`). The system atom table (`WinQuerySystemAtomTable`) is the session's, kept by the desktop server: every program finds the atoms the others added, and they stay when those programs end (ADR-0056); tables made with `WinCreateAtomTable` are the process's. DDE reaches every program of the session: `WinDdeInitiate` sends `WM_DDE_INITIATE` to the clients of the other programs' frames, waiting for each (their `WinDdeRespond` arrives before it returns), then to its own program's frames — each receiver gets a `DDEINIT` in giveable shared memory, which it frees with `DosFreeMem`; `WinDdeRespond` sends `WM_DDE_INITIATEACK` and returns the client's answer; `WinDdePostMsg` posts `WM_DDE_*` messages with their `DDESTRUCT`. Within a program the `DDESTRUCT` is neither copied nor freed (`DDEPM_RETRY` / `DDEPM_NOFREE` change nothing); to another program it must be shared memory (`DosAllocSharedMem` giveable; else `PMERR_INVALID_PARM`), is given to the receiving process and, unless `DDEPM_NOFREE`, freed in the sender.

**Text controls.** Entry fields and MLEs support selection — Shift with the movement keys, or dragging with mouse button 1 — which typing, Backspace and Delete replace or remove, and the clipboard through the CUA keys (Ctrl+Insert copy, Shift+Delete cut, Shift+Insert paste) and `EM_CUT` / `EM_COPY` / `EM_PASTE` / `EM_CLEAR` (`MLM_*` for the MLE); the PM clipboard is shared with the host's. `EM_SETSEL` / `EM_QUERYSEL` and `MLM_SETSEL` / `MLM_QUERYSEL` set and report the selection in characters. Shift+click extends the selection; dragging above or below an MLE or list box scrolls it. PageUp / PageDown move by the visible rows less one in the MLE and list box. A read-only field (`ES_READONLY` / `MLS_READONLY`, or `EM_SETREADONLY` / `MLM_SETREADONLY`, queried with `EM_QUERYREADONLY` / `MLM_QUERYREADONLY`) can be selected and copied but not changed. The owner is told about focus changes with `EN_SETFOCUS` / `EN_KILLFOCUS`, `MLN_SETFOCUS` / `MLN_KILLFOCUS` and `LN_SETFOCUS` / `LN_KILLFOCUS` (mp2 = the control). `LM_DELETEITEM` returns the number of items left; `LM_DELETEALL` empties a list box. An MLE with `MLS_WORDWRAP` (switched with `MLM_SETWRAP`, reported by `MLM_QUERYWRAP`) wraps its lines at word boundaries. A list box with `LS_MULTIPLESEL` toggles an item per click or Space and moves only its cursor with the arrow keys; one with `LS_EXTENDEDSEL` selects ranges with Shift+click or Shift+arrows and toggles items with Ctrl+click. `LM_QUERYSELECTION` walks the selected items (from `LIT_FIRST`; `LIT_CURSOR` gives the cursor item). Enter or a double-click on an item sends `LN_ENTER`; a focused list box outlines its cursor item. A double click's second press arrives as `WM_BUTTON1DBLCLK` (`WM_BUTTON2DBLCLK` / `WM_BUTTON3DBLCLK` for the other buttons). The caret of the focused text control blinks at `SV_CURSORRATE` milliseconds (500 by default; `WinSetSysValue` changes it), and the host's input-method window opens at it. Holding the pointer still past the edge of a control while selecting keeps it scrolling.

**Codepages.** PM text follows the codepage of the message queue (`WinSetCp`), not the process codepage: window and dialog-item text, list-box items and typed characters use the queue of their window; a presentation space has its own codepage (`GpiSetCp` / `GpiQueryCp`), its window queue's when it is created. `WinQueryCpList` lists the codepages a queue can use: the process codepages plus 1004 ("Windows Extended"), which `DosSetProcessCp` refuses. `WinSetCp` refuses any other codepage, 0 included (`PMERR_RESOURCE_NOT_FOUND`; the Reference gives 0 no meaning), and an unknown queue (`PMERR_INVALID_HMQ`).

**Dialogs inside windows.** A dialog's parent decides where it lives (ADR-0042). With `HWND_DESKTOP` it is a window of its own on the desktop, with the template's chrome; its template position is relative to the desktop, and it becomes the active window with the focus on its first control. With another window as parent (`WinLoadDlg(hwndClient, …)`, a notebook page), it is a child of that window, as in PM. Its template position is relative to the parent, and it is drawn into the parent's frame, clipped to its own rectangle. The title bar and border its template asks for are drawn inside that rectangle (ADR-0069): the title bar with the inactive colours and no buttons, and not a window of its own (a click on it reaches the dialog). It is shown only when its template has `WS_VISIBLE`, and it takes no activation or focus when created. Its controls, and windows of the program's own classes inside it, work in place (clicks, focus, typing, `WinWindowFromPoint`); a click on its own area reaches the dialog procedure in its coordinates, and it is destroyed with its parent. Tab crosses between its controls and the controls of the client around it, both ways: from the dialog through `WinDefDlgProc`, from the client's controls through the client's `WinDefWindowProc`.

**Dialogs and the keyboard.** Dialog templates are read as `<pmwin.h>` lays them out (chrome from the template's `FCF_*` / `FS_*` flags, texts in the template's codepage); their entry fields, list boxes and buttons work like those in client windows. The first `WS_TABSTOP` control (or the template's focus item) has the focus when `WM_INITDLG` arrives. `WinDefDlgProc` moves the focus with Tab / Shift+Tab, presses the focused or default (`BS_DEFAULT`) push button on Enter, posts `WM_COMMAND(DID_CANCEL)` on Esc, and ends the dialog on any `WM_COMMAND` with the command value. Push buttons post `WM_COMMAND` with `CMDSRC_PUSHBUTTON`; other buttons send `WM_CONTROL(BN_CLICKED)`. Accelerator tables (`WinLoadAccelTable`, `FCF_ACCELTABLE`, `WinSetAccelTable`, `WinTranslateAccel`) are applied by `WinGetMsg` and inside modal dialogs: the active frame's table, then the queue's, then the system table, where Alt+F4 is `WM_SYSCOMMAND(SC_CLOSE)`; `WinDefWindowProc` turns that into `WM_CLOSE`. Arrow keys move the focus within a group of controls (from one `WS_GROUP` control to the next); a mnemonic (the letter after `~` in a control's text, shown underlined) typed with Alt — or plainly while a button has the focus — clicks that button or, for a label, focuses the control after it. While a modal dialog runs (`WinDlgBox`, `WinProcessDlg`) its owner's frame is disabled and takes no clicks; `WinDlgBox` destroys the dialog before it returns. `WinGetMsg` and `WinPeekMsg` (`PM_REMOVE` / `PM_NOREMOVE`) honour the window filter (the window and its descendants) and the message range; `WM_QUIT` passes every filter. `WinDestroyWindow` removes a window and its descendants; `WinIsWindow` reports whether a handle is still a window.

**Menus, message boxes and message queues.** `WinLoadMenu` and `WinCreateMenu` create the menu as the frame's `FID_MENU` window; the frame shows it once the application sends it `WM_UPDATEFRAME` with `FCF_MENU` (a menu loaded through `FCF_MENU` at creation is shown at once), so a menu bar is replaced by destroying the old `FID_MENU` window, loading the new one and sending `WM_UPDATEFRAME`. The menu bar works from the keyboard: F10, or Alt pressed and released alone, sends `WM_SYSCOMMAND(SC_APPMENU)`, and `WinDefWindowProc` highlights the bar's first item (as does `MM_STARTMENUMODE` sent to the `FID_MENU` window; `MM_ENDMENUMODE` ends it). Left / Right move along the bar, Down or Enter drops the pull-down, Up / Down / Home / End move in it (skipping separators and disabled items), Enter or an item's mnemonic letter chooses it — `WM_COMMAND` (`WM_SYSCOMMAND` / `WM_HELP` for `MIS_SYSCOMMAND` / `MIS_HELP` items) with `MPFROM2SHORT(CMDSRC_MENU, FALSE)` — and Esc closes the pull-down, then leaves; a row whose item has a submenu shows an arrow and opens it as a cascade beside the row with Right, Enter, its mnemonic or a click (Up / Down move in it, Enter, a mnemonic or a click chooses, Left or Esc closes it; the client gets `WM_INITMENU` with the row's item id first; one level of cascades is shown); F10, Alt or a click elsewhere leaves too. While the menu has the keyboard, keys do not reach the window that has the focus. F1 posts `WM_HELP` to the active frame's client (a system accelerator). The client hears the menu bar, used with the mouse or the keyboard: `WM_INITMENU` (mp1 = `FID_MENU` when the menu becomes active, the bar item's id before its pull-down drops; mp2 = the menu bar), `WM_MENUSELECT` (`MPFROM2SHORT(item, fPost)`) when the highlight moves to an item and, with fPost TRUE, when one is chosen — the command is posted only if the client returns TRUE, which `WinDefWindowProc` does — and `WM_MENUEND` when the menu is left. Before an `MIS_OWNERDRAW` item's pull-down first drops, its owner gets `WM_MEASUREITEM` (mp1 = the menu's id, mp2 = an `OWNERITEM` whose `rclItem` is the default row); the reply, or `rclItem.yTop` when the reply is 0, is the row height, and all rows of that pull-down take the tallest answer (at least the font's, at most 256). An `MIS_OWNERDRAW` pull-down item gets `WM_DRAWITEM` again when the keyboard highlight reaches or leaves it (`MIA_HILITED` in `fsAttribute`, the opposite in `fsAttributeOld`). A disabled item cannot be chosen with the mouse either. A menu window takes the item messages: `MM_QUERYITEMCOUNT`, `MM_QUERYITEMATTR` / `MM_SETITEMATTR` (so `WinCheckMenuItem`, `WinEnableMenuItem`, `WinIsMenuItemChecked`, `WinIsMenuItemEnabled` work), `MM_ISITEMVALID` (enabled, and so is its bar item), `MM_QUERYITEMTEXT` / `MM_QUERYITEMTEXTLENGTH` / `MM_SETITEMTEXT` (`WinSetMenuItemText`), `MM_ITEMPOSITIONFROMID` / `MM_ITEMIDFROMPOSITION`, `MM_QUERYITEM`, `MM_INSERTITEM`, `MM_DELETEITEM` / `MM_REMOVEITEM`; with `fIncludeSubmenus` they search the pull-downs too. Disabled items are drawn greyed and checked ones with a mark. Pull-downs are not windows of their own: `MM_QUERYITEM` gives the menu's own handle as `hwndSubMenu`, which reaches the pull-down's items through `fIncludeSubmenus`. `WinWindowFromID(frame, FID_SYSMENU)` gives a frame's system menu window, made when first asked for; what a program disables or checks there shows in the system menu, and with Close disabled `SC_CLOSE` does nothing — from the menu, Alt+F4 or the close button. `WinMessageBox` shows a modal PM dialog with the caption, the text, an icon for the `MB_ICON*` / `MB_ERROR` / `MB_WARNING` / `MB_INFORMATION` / `MB_QUERY` styles (Warpine's own pictures: a red circle with a line across it, "i", "!", "?") and the buttons of its `MB_*` style (default button from `MB_DEFBUTTON*`; `MB_HELP` adds a Help button, which sends `WM_HELP` to the box and leaves it open), and returns the `MBID_*` of the button pressed; other windows keep running while it is open and only its owner is disabled; Close (the close button, Alt+F4) returns `MBID_CANCEL` whatever the buttons, Esc only when the box has a Cancel button. Only a box with `MB_MOVEABLE` has a system menu and can be moved; `MB_SYSTEMMODAL` acts as application modal. `WinMessageBox2` takes an `MB2INFO`: its own buttons (`MB2D`: label with an optional `~` mnemonic, the id it returns, `BS_DEFAULT` for the default button; at most 16), an application icon (`MB_CUSTOMICON` with `hIcon`: a system icon or a loaded pointer) and `MB_NONMODAL`: such a box returns its window handle at once and leaves its owner enabled; `hwndNotify` (else the owner) gets `WM_MSGBOXINIT` (mp1 = the box, mp2 = `ulWindow`) when it opens and `WM_MSGBOXDISMISS` (mp1 = the box, mp2 = the button's id) when a button ends it, which hides it — destroying it is the owner's job. A NULL title shows "Error"; an unknown style flag fails with `MBID_ERROR` and `PMERR_INVALID_FLAG`. A thread has at most one message queue: a second `WinCreateMsgQueue` returns `NULLHANDLE`, and `WinDestroyMsgQueue` destroys only the calling thread's own queue, after which the thread may create a new one. The second press of a double click arrives as `WM_BUTTONnDBLCLK`. Dragging a window by its title bar moves its controls with it.

**Messages and hooks.** `WinPostQueueMsg` posts a message for no window (`QMSG.hwnd` NULLHANDLE) to a queue. `WinBroadcastMsg` posts (`BMSG_POST`) or sends (`BMSG_SEND`) a message to the children of a window — the desktop's are the main windows, `HWND_OBJECT`'s the object windows —, with `BMSG_DESCENDANTS` to all its descendants (parents first), with `BMSG_FRAMEONLY` to frame windows (standard frames and dialogs) only; `BMSG_POSTQUEUE` posts it to every message queue of the process instead. `WinWaitMsg` waits until a message in the range is in the caller's queue and leaves it there. A window procedure runs on the thread that sends the message (PM switches to the window's thread), so `WinInSendMsg` is TRUE while a thread runs a procedure for a message it sent to another thread's window, and `WinWaitEventSem` / `WinRequestMutexSem` wait like `DosWaitEventSem` / `DosRequestMutexSem`. `WinSetHook` / `WinReleaseHook` set hooks for the calling thread's queue (`HMQ_CURRENT`) or another queue of the process; `hmq` NULLHANDLE (a system hook) makes a hook for every queue of this process only — one OS/2 program runs per Warpine process. Hooks set last are called first, the queue's before the process'. Called: `HK_INPUT` (by `WinGetMsg` / `WinPeekMsg` with the `QMSG`, which it may change, and `PM_REMOVE` / `PM_NOREMOVE`; TRUE swallows the message: `WinGetMsg` and `WinPeekMsg(PM_REMOVE)` take the next one, `WinPeekMsg(PM_NOREMOVE)` returns FALSE; accelerators are translated after the hook), `HK_SENDMSG` (by `WinSendMsg` and `WinBroadcastMsg(BMSG_SEND)` before the window procedure, with an `SMHSTRUCT` (`model` `PM_MODEL_2X`) and `fInterTask`; the hooks of the receiving window's queue), `HK_MSGFILTER` (by `WinCallMsgFilter`, TRUE when a hook returned TRUE, and by the modal loops of `WinDlgBox` / `WinProcessDlg` / the standard dialogs with `MSGF_DIALOGBOX` and of `WinMessageBox` with `MSGF_MESSAGEBOX` for every message they take, after accelerator translation; the hook may change the `QMSG`, and TRUE swallows the message; `MSGF_TRACK` is never passed, frames are tracked by Warpine's desktop) and `HK_HELP` (by `WinDefWindowProc` for `WM_HELP` in a frame or its client: `HLPM_FRAME` with the frame's and the focus window's ids, `HLPM_MENU` with `FID_MENU` and the item for a menu command, and the frame's rectangle on the desktop; `WM_HELP` in another child window goes on to its parent). Other hook types are accepted and never called; an unknown type or a null procedure fails (`PMERR_PARAMETER_OUT_OF_RANGE`), as does releasing a hook that is not set. No hooks are called for what a hook procedure does. Warpine's own choices where the reference is silent are listed in the developer guide.

**System menu and keyboard move / size.** A frame with `FCF_SYSMENU` opens its system menu on a click on the icon, Alt+Space, Shift+Esc or `WM_SYSCOMMAND(SC_SYSMENU)`: Restore, Move, Size, Minimize, Maximize, Hide, Close and Window list, greyed by the frame's state and buttons (Window list is always greyed). A choice is posted as `WM_SYSCOMMAND(SC_*)` with `CMDSRC_MENU` to the client, which may handle it; `WinDefWindowProc` / `WinDefDlgProc` carry it out. Move and Size (also Alt+F7 / Alt+F8; no Size without `FCF_SIZEBORDER` or outside the normal state, no Move when maximized) take the arrow keys — sizing first picks an edge or corner — then Enter keeps and Esc restores. Programs cannot yet change the system menu's items (there is no `FID_SYSMENU` window), and `WinTrackRect` / `WM_TRACKFRAME` are not available. `WinPopupMenu` shows a loaded menu's items at a point in the parent window (`PU_POSITIONONITEM`, `PU_SELECTITEM`) and posts `WM_COMMAND` to the owner; submenus are shown greyed.

**Minimize, maximize and restore.** `WinSetWindowPos` with exactly one of `SWP_MINIMIZE`, `SWP_MAXIMIZE`, `SWP_RESTORE` changes a frame's state (no effect if it is already in that state); the frame's client first receives `WM_MINMAXFRAME` (mp1 = PSWP with the new position) and can return TRUE to cancel it, and gets `WM_SIZE` afterwards. `WinDefWindowProc` carries out `WM_SYSCOMMAND` `SC_MINIMIZE` / `SC_MAXIMIZE` / `SC_RESTORE` for frames created with `FCF_MINBUTTON` or `FCF_MAXBUTTON` and ignores them otherwise. `WinQueryWindowULong(QWL_STYLE)` reports `WS_MINIMIZED` / `WS_MAXIMIZED`; `WinQueryWindowUShort` / `WinSetWindowUShort` read and write `QWS_XRESTORE`, `QWS_YRESTORE`, `QWS_CXRESTORE`, `QWS_CYRESTORE` and `QWS_XMINIMIZE` / `QWS_YMINIMIZE` (-1 before the first minimize). A maximized frame fills the desktop; a minimized one becomes a small title bar at the bottom of the desktop. A frame created with `FCF_HIDEBUTTON` (or `FCF_HIDEMAX`) has a hide button, which sends `WM_SYSCOMMAND(SC_HIDE)`; `WinDefWindowProc` then hides the frame and the frames it owns. Minimizing or hiding the active frame makes the next visible frame active. `WinSetWindowPos` with `SWP_SIZE` sends `WM_SIZE` (old and new size) to the window, or to a frame's client. `WinQueryWindowPos` reports `SWP_MINIMIZE` / `SWP_MAXIMIZE` and, for frames, `SWP_ACTIVATE` / `SWP_DEACTIVATE` in `fl`. Alt+F5 restores, Alt+F9 minimizes, Alt+F10 maximizes, Alt+F4 closes; a title-bar double click maximizes or restores, and a double click on the system-menu icon closes the window. Not yet: F10 for the menu bar.

**Window destruction.** `WinDestroyWindow` hides the window and sends `WM_DESTROY` to it and then to its descendants (each parent before its children, all of them still existing while they handle it), destroys the windows owned by a destroyed frame, and then removes them all; it returns FALSE for an unknown handle (`PMERR_INVALID_HWND`) or a window of another thread, and TRUE for a window already being destroyed. `WinDlgBox` destroys its dialog the same way before returning.

**Frames, accelerator tables and other window calls.** `WinCreateFrameControls` (`FRAMECDATA`: `flCreateFlags`, `hmodResources`, `idResources`; a `cb` smaller than the structure fails with `PMERR_PARAMETER_OUT_OF_RANGE`) adds frame controls to a frame: the title bar, system menu, buttons and border styles are drawn as chrome, `FCF_MENU` loads the menu and `FCF_ACCELTABLE` the accelerator table from the module, `pszTitle` becomes the title, and `FCF_VERTSCROLL` / `FCF_HORZSCROLL` create the scroll bars `FID_VERTSCROLL` / `FID_HORZSCROLL` (as `WinCreateStdWindow` does), owned by the frame, which passes their `WM_VSCROLL` / `WM_HSCROLL` on to its client. The frame scroll bars take the pointer like any scroll bar (arrows, shaft, slider drag, repeat while held), and the client's drawing — GPI, `WinFillRect`, `GpiQueryPel`, `GpiBitBlt` — lies at its place above a horizontal bar and stays inside the client. A frame made with `WinCreateWindow(WC_FRAME)` takes the window created in it with the identity `FID_CLIENT` as its client and is then shown like a standard frame. The client sits below the title and menu bars and beside the scroll bars, which lie inside the border along the right and bottom edges, 16 pels thick (`SV_CXVSCROLL` / `SV_CYHSCROLL`). `WinCalcFrameRect` turns a frame rectangle into its client rectangle (`fClient` TRUE) or a client rectangle into the frame rectangle (FALSE) and fails when the result is empty or the window is no frame. `WinDefWindowProc` answers the frame messages `WM_QUERYFRAMECTLCOUNT` (the menu, scroll bars and client), `WM_FORMATFRAME` (fills the `SWP` array with their positions — `SWP_SIZE | SWP_MOVE` — and the client rectangle, and returns their count) and `WM_CALCFRAMERECT` (mp2 TRUE: the rectangle is the frame's). Warpine lays frames out itself and does not send these messages to a subclassed frame procedure. `WinFlashWindow` starts and stops flashing a frame's title bar (it alternates between active and inactive at the cursor rate, without a sound). `WinSetMultWindowPos` applies an array of `SWP`s as `WinSetWindowPos` would — a minimize, maximize or restore without `WM_MINMAXFRAME` — and changes nothing when a handle in it is invalid. `WinCreateAccelTable` makes an accelerator table from an `ACCELTABLE` in memory; `WinCopyAccelTable` copies a table out (at most `cbCopyMax` bytes; with a NULL buffer it returns the size needed); `WinQueryAccelTable` returns the table set for a window (`NULLHANDLE`: the queue's); `WinDestroyAccelTable` destroys one and takes it from the windows it was set for (`PMERR_INVALID_HACCEL` for an unknown table). `WinLoadMessage` reads `MESSAGETABLE` strings (`RT_MESSAGE`) as `WinLoadString` reads `STRINGTABLE` ones — 16 strings per bundle after the bundle's codepage — copying at most `cchMax - 1` bytes and a NUL; a missing string returns 0 with `PMERR_RESOURCE_NOT_FOUND`. `WinQueryVersion` reports version 20, release 45 (OS/2 Warp 4.5) in its two low bytes. `WinSetWindowBits` changes the masked bits of a window word; for `QWL_STYLE` the style itself (as `WinSetWindowULong(QWL_STYLE)` now does), so `WS_VISIBLE` and `WS_DISABLED` take effect. `WinSetDlgItemShort` writes a number, signed or unsigned, as an item's text; `WinQueryDlgItemShort` reads it back and returns FALSE (leaving the result alone) when the text, blanks aside, is not a number in the range.

**Check boxes and radio buttons.** `BM_SETCHECK` (mp1 0 unchecked, 1 checked, 2 indeterminate) returns the previous state; for radio buttons it also sets `WS_TABSTOP` when checked and clears it otherwise, so Tab enters a radio group on its checked button. `BM_QUERYCHECK` returns the state, `BM_QUERYCHECKINDEX` the index of the checked radio button of the group (-1 if none). Selecting an auto check box toggles it, an auto three-state button cycles unchecked → checked → indeterminate, an auto-radio button is checked and the other auto-radio buttons of its group unchecked; all check boxes and radio buttons send `WM_CONTROL(id, BN_CLICKED)`. In a dialog the arrow keys move within the group, wrapping around, and check an auto-radio button they move to unless it has `BS_NOCURSORSELECT`. Every button takes `BM_CLICK` (mp1 TRUE clicks it as the mouse would; FALSE only highlights it), `BM_SETHILITE` (returns the previous highlight; a highlighted push button is drawn pressed) and `BM_QUERYHILITE` (push buttons only; FALSE for other styles); `BM_SETDEFAULT` makes a push button the default button (Enter in a dialog) or not, and returns FALSE for other styles.

**Errors.** `WinGetLastError` returns the calling thread's last PM error — severity (`SEVERITY_ERROR`) in the high word, the `PMERR_*` code in the low word — and resets it to 0. Recorded: `PMERR_MSG_QUEUE_ALREADY_EXISTS`, `PMERR_INVALID_HMQ`, `PMERR_NO_MSG_QUEUE`; `PMERR_INVALID_HWND` from the calls that take a window (window state, position and text, window words, painting, focus, active window and capture, timers, dialog items, `WinCreateWindow`'s parent and owner, the window filter of `WinGetMsg` / `WinPeekMsg`, accelerator tables), which then fail with FALSE or NULLHANDLE; `PMERR_PARAMETER_OUT_OF_RANGE` for window-word indices outside the class's window words and a bad `WinQueryWindow` code; `PMERR_INVALID_FLAG` (`WinPeekMsg`), `PMERR_INVALID_HACCEL` (`WinSetAccelTable`), `PMERR_INVALID_HPTR` and `PMERR_RESOURCE_NOT_FOUND` (pointers). `WinEnableWindow` returns TRUE when it updates the state; `WinSetFocus` to the desktop window leaves no window with the focus. `WinGetErrorInfo` is not implemented.

**Window tree.** `WinIsWindowVisible` is TRUE when the window and all its parents have `WS_VISIBLE` (a covered window still counts as visible). `WinQueryWindowTextLength` returns the length of the window text without the null. `WinSetParent` moves a window under another window, the desktop (`HWND_DESKTOP`: it becomes a main window) or `HWND_OBJECT` (an object window, never shown); the new parent cannot be the window or one of its descendants. `WinSetOwner` changes the owner (NULLHANDLE: none). `WinQueryWindowPtr` / `WinSetWindowPtr` read and write pointers in the application's window words (indices 0 to `cbWindowData` − 4, the same words as `WinQueryWindowULong`) and the window procedure (`QWP_PFNWP`). A standard window's client takes the `flClientStyle` given to `WinCreateStdWindow`, so pass `WS_VISIBLE` there for a visible client.

**Subclassing.** `WinSubclassWindow` on a built-in control, a standard frame or a dialog returns the built-in window procedure (`WrpBuiltinWindowProc`, an export of Warpine's own `WARPINE.DLL`; `WinQueryClassInfo` and `WinQueryWindowPtr(QWP_PFNWP)` report the same address): call it from the subclass procedure to pass a message on, and set it back to remove the subclass. A subclassed control is still drawn and works like the built-in one; messages Warpine gives the control directly (repainting after `WinEndPaint`, a dialog pressing a button) do not pass through the subclass. A standard frame runs the system frame procedure, not its client's. When a subclassed frame is sized or its controls change, it is asked `WM_QUERYFRAMECTLCOUNT`, then `WM_FORMATFRAME` with a client `RECTL` and room for that many `SWP`s: the positions, sizes and visibility of the frame's children it returns are applied (how a tool bar or status line is added). `WinCalcFrameRect` asks a subclassed frame `WM_CALCFRAMERECT`. A `WC_FRAME` made with `WinCreateWindow` on the desktop is shown at once, with or without a client. `WinDefWindowProc` sends `WM_CHAR` on to the window's owner, so keys a control does not use reach its dialog; focus changes post `WM_SETFOCUS` (FALSE to the window losing it, then TRUE) to windows with a procedure of their own. When a thread ends, its windows are destroyed with it (no `WM_DESTROY`).

**Painting through other presentation spaces.** `WinGetPS` of a window inside a frame (a child of the client, a control) draws at that window's place, clipped to it. `WinBeginPaint` clips its presentation space to the update rectangle until `WinEndPaint` (not when nothing waits to be painted). `WinUpdateWindow` has the window and its descendants that need painting paint before it returns; `WinShowWindow` invalidates a window it shows.

**Dialog items of your own classes.** A control of the program's own class in a dialog takes the focus, Tab and the arrow keys like a built-in one when it is visible, enabled and `WS_TABSTOP`. A mnemonic no built-in control has is offered to such controls with `WM_MATCHMNEMONIC` (mp1 = the character) until one returns TRUE; it takes the focus. Built-in controls answer `WM_QUERYDLGCODE` (`DLGC_ENTRYFIELD`, `DLGC_BUTTON | DLGC_PUSHBUTTON` (with `DLGC_DEFAULT`), `DLGC_CHECKBOX`, `DLGC_RADIOBUTTON`, `DLGC_STATIC`, `DLGC_SCROLLBAR`, `DLGC_MENU`, `DLGC_MLE`) and `WM_MATCHMNEMONIC` (their `~` letter, any case).

**Coordinates and lookups.** `WinMapWindowPoints` maps points (a `RECTL` is two points) between windows and the desktop (`HWND_DESKTOP`: screen coordinates, origin bottom-left). A main window and a dialog are placed on the desktop; a standard frame's client lies inside the frame's left border, at its bottom edge; other windows are relative to their parent. `WinWindowFromPoint` returns the topmost visible window under a point given relative to `hwndParent` — with `fChildren` at any depth, else among the immediate children — `hwndParent` itself when no child is there and NULLHANDLE when the point is outside it; with `HWND_DESKTOP` it tests the frames and dialogs on the desktop. `WinQueryDesktopWindow` returns `HWND_DESKTOP` for the screen (NULLHANDLE or a window DC; `PMERR_INV_HDC` otherwise), `WinQueryAnchorBlock` the anchor block of `WinInitialize`. `WinIsChild` is TRUE for the window itself and every descendant, never for an object window. `WinQueryWindowProcess` gives the process id and the thread whose message queue owns the window. `WinMultWindowFromIDs` fills an array with the children whose ids lie in a range (NULLHANDLE where there is none) and returns how many it found. `WinEnumDlgItem` walks the immediate children of a dialog (or any window): `EDI_FIRSTTABITEM` / `EDI_LASTTABITEM` / `EDI_NEXTTABITEM` / `EDI_PREVTABITEM` over the visible, enabled `WS_TABSTOP` items, wrapping around; `EDI_FIRSTGROUPITEM` … `EDI_PREVGROUPITEM` within the `WS_GROUP` group of the item holding `hwnd`, skipping hidden and disabled items. `WinQueryClassName` writes "#1" for a frame or dialog, "#3" for a button and so on ("#" and the value of the `WC_*` constant), the registered name for an application class. `WinQueryClassInfo` reports an application class (style, window procedure, `cbWindowData`) or a preregistered one by its `WC_*` constant or "#nnnnn" name (`CS_PUBLIC`, `WinDefWindowProc` as the procedure: Warpine's built-in controls run in the host).

**Input state.** `WinGetKeyState` answers as of the input message the program read last: a key or mouse button (`VK_BUTTON1` … `VK_BUTTON3`) is down (0x8000) if it was down when that message arrived, and 0x0001 toggles with each press. `WinGetPhysKeyState` takes a hardware scan code and answers for the keyboard now: 0x8000 down, 0x0001 pressed since the last call. Shift, Ctrl, Alt (`VK_ALT`; right Alt is `VK_ALTGRAF`), Caps Lock, Pause and Print Screen are virtual keys, so pressing one alone sends `WM_CHAR` with `KC_VIRTUALKEY`. Every message carries the time it was posted (milliseconds since the host started) and the pointer position then in its `QMSG` (`ptl` is a `POINTL`); `WinQueryMsgTime` / `WinQueryMsgPos` return them for the message the queue read last. `WinQueryPointerPos` and `WinSetPointerPos` use desktop coordinates; setting the position moves the host pointer, except in a scripted session.

**System colours.** `WinQuerySysColor` returns the RGB value of a `SYSCLR_*` index; the defaults are the colours Warpine draws with (navy and dark grey title bars, the green desktop, the control face) and otherwise those of the PM Reference. `WinSetSysColors` (`LCOLF_INDRGB` index/value pairs or `LCOLF_CONSECRGB` values from a starting index, `LCOL_RESET` to the defaults first) checks every index before it changes anything, posts `WM_SYSCOLORCHANGE` (mp1 = the options) to every main window — a frame's goes to its client — and repaints all frames. The title bars follow the table at once, and a `SYSCLR_*` value used as a colour (`WinFillRect`, `GpiSetColor`, `WinDrawText`, …) draws in the current system colour.

**Mouse pointers.** `WinQuerySysPointer` gives handles to the system pointers (`SPTR_ARROW`, `SPTR_TEXT`, `SPTR_WAIT`, the sizing and move pointers, `SPTR_ILLEGAL`, the icons; `fCopy` returns a copy to destroy). `WinSetPointer` changes the mouse pointer — the host cursor follows — and `WinQueryPointer` reports it; NULLHANDLE removes it. `WinShowPointer` hides and shows it by a display level (`SV_POINTERLEVEL`). `WinLoadPointer` loads a `POINTER` resource (black-and-white or colour, single or a bitmap array) and `WinDestroyPointer` frees it. `WinDefWindowProc` shows the arrow when the pointer moves over a window, and a sizing arrow over a frame's sizing border (the double arrow of the edge, the diagonal one of a corner). A built-in control shows its own pointer — the I-beam over entry fields and MLEs, the arrow over the others — and asks its owner with `WM_CONTROLPOINTER` (mp1 = the control's id, mp2 = that pointer); the pointer the owner returns is shown instead (`WinDefWindowProc` returns mp2). Not yet: `WinCreatePointer`. (`WinQueryPointerPos` / `WinSetPointerPos`: see "Input state".)

**Rectangles and text.** The rectangle calls (`WinSetRect`, `WinSetRectEmpty`, `WinCopyRect`, `WinOffsetRect`, `WinInflateRect`, `WinPtInRect`, `WinIntersectRect`, `WinUnionRect`, `WinSubtractRect`, `WinIsRectEmpty`, `WinEqualRect`) treat a rectangle as empty when its left edge is not left of its right edge or its bottom not below its top; a point on the right or top edge is outside; with no intersection (or an empty union or difference) the result is (0, 0, 0, 0) and the call returns FALSE; `WinSubtractRect` returns the first rectangle when the difference is not a rectangle. `WinDrawText` draws one line — up to the first CR or LF — in the presentation space's font, placed by `DT_LEFT` / `DT_CENTER` / `DT_RIGHT` and `DT_TOP` / `DT_VCENTER` / `DT_BOTTOM` in the rectangle (its edges count as inside). It returns the string's length, or with `DT_WORDBREAK` the characters drawn: the words that fit, at least one, plus trailing blanks and the line end when the whole line fit, so a loop that advances by the result draws a paragraph. `DT_QUERYEXTENT` draws nothing and returns the text's bounding rectangle in `prcl`; `DT_ERASERECT` fills the rectangle with the background colour first; `DT_TEXTATTRS` uses the presentation space's colours; `DT_MNEMONIC` underlines the character after `~`; `DT_UNDERSCORE` / `DT_STRIKEOUT` draw a line under / through the text; `DT_HALFTONE` draws it in a colour halfway to the background. A reserved flag fails with `PMERR_INVALID_FLAG`. The text is not clipped to the rectangle.

**Painting.** Every window has an update region — what was invalidated since it last painted (ADR-0058). `WinInvalidateRect` adds a rectangle (NULL: the whole window), clipped to the window, and `WM_PAINT` follows while something is left to paint — one message however often the window is invalidated, read after posted messages and input. Children are invalidated with their parent when `fIncludeChildren` is TRUE or the parent lacks `WS_CLIPCHILDREN` (only visible children); a frame window passes the call on to its client; `HWND_DESKTOP` invalidates every frame. `WinValidateRect` removes a rectangle (NULL: everything), holes included; once nothing is left the waiting `WM_PAINT` is withdrawn. `WinQueryUpdateRect` returns TRUE and the region's bounding rectangle when there is something to paint, otherwise FALSE and (0, 0, 0, 0); its rectangle pointer may be NULL. `WinBeginPaint` returns that bounding rectangle in `prclPaint`, clips its presentation space to the region until `WinEndPaint` and empties it (the window is created, restored or maximized with the whole window to paint; a resized window with the whole of it when its class has `CS_SIZEREDRAW`, otherwise only with what the new size uncovers — nothing when it shrinks); `WinDefWindowProc` validates a window that passes `WM_PAINT` on. A child window's presentation space (`WinGetPS`) draws only inside its parent and their ancestors. `WinScrollWindow` moves the pels of the scroll rectangle (NULL: the window) by `lDx` / `lDy`; pels that land outside the clip rectangle (NULL: the scroll rectangle) are dropped, and the part of the scroll and clip rectangles no moved pel covers is uncovered: `prclUpdate` receives its bounding rectangle and the result is `RGN_NULL`, `RGN_RECT` or `RGN_COMPLEX` (an L shape); `SW_INVALIDATERGN` adds it to the update region (with the part of the old update region that moved), `SW_SCROLLCHILDREN` moves the children too (with a scroll rectangle, those it intersects); other option bits fail with `RGN_ERROR` and `PMERR_INVALID_FLAG`; `hrgnUpdate`, when given, is set to the uncovered area. `WinInvalidateRegion` / `WinValidateRegion` add / remove a region, `WinQueryUpdateRegion` sets a region to the update region and `WinExcludeUpdateRegion` takes it out of a presentation space's clip region; a region selected as a clip region fails these with `PMERR_HRGN_BUSY`. `WinDrawBorder` draws a border inside the rectangle — its right and top edges are outside —, `cx` pels wide at the left and right and `cy` at the bottom and top (times `SV_CXBORDER` / `SV_CYBORDER`, 1, with `DB_STANDARD`); borders that meet fill the whole rectangle, and with no border the rectangle is all interior. The border is `clrFore`, the interior (`DB_INTERIOR`) `clrBack`; `DB_AREAATTRS` takes the presentation space's area pattern and colours instead (reversed inside). `DB_PATCOPY` overpaints, `DB_PATINVERT` XORs, `DB_DESTINVERT` inverts the destination and `DB_AREAMIXMODE` uses the presentation space's foreground mix. `DB_DLGBORDER` draws the border in the active title-bar colour (with `DB_PATCOPY`) or the inactive one (with `DB_PATINVERT`) and the interior in `clrBack`. An unknown flag fails with `PMERR_INVALID_FLAG` (`DB_RAISED` / `DB_DEPRESSED` of later toolkits included), a raster operation above `DB_AREAMIXMODE` with `PMERR_INV_DRAW_BORDER_OPTION`, a bad presentation space with `PMERR_INV_HPS`.

**Presentation parameters.** `WinSetPresParam` gives a window an attribute (`PP_*`, or an application's own from `PP_USER`) with a value of up to 1024 bytes (at most 64 attributes per window; more, a longer value, attribute id 0 or an unreadable value fail with `PMERR_PARAMETER_OUT_OF_RANGE`); `WinCreateWindow`'s `pPresParams` and the `PRESPARAMS` of a dialog template (dialog and items, as Open Watcom `wrc` writes them) set them at creation. `WinQueryPresParam` looks for `id1`, then `id2` (0 = none), on the window and then up its owner chain — a frame's client counts as owned by its frame — unless `QPF_NOINHERIT`; it writes the attribute found to `pulId` (may be NULL) and up to `cbBuf` bytes of its value (a longer value is cut), and returns the number of bytes written (0: not found). `QPF_ID1COLORINDEX` / `QPF_ID2COLORINDEX` return a found colour index (`CLR_*`, `SYSCLR_*`) as its RGB value; `QPF_PURERGBCOLOR` changes nothing (every colour is pure on Warpine's 24-bit display); other flag bits fail with `PMERR_INVALID_FLAG`. `WinRemovePresParam` returns FALSE when the window has no such attribute of its own. A change is announced with `WM_PRESPARAMCHANGED` (mp1 = the attribute), *posted* to the window and every window inheriting the attribute from it that has a window procedure; built-in controls and dialogs repaint. The built-in controls draw in `PP_FOREGROUNDCOLOR` (text), `PP_FONTNAMESIZE` ("10.Helv": points × 1.6 as the line height in pels, the face through Warpine's face mapping; rows keep the system font's height), `PP_BACKGROUNDCOLOR` (statics and dialogs, inherited; entry fields, MLEs and list boxes only their own), `PP_BUTTONBACKGROUNDCOLOR` (push buttons, else their own `PP_BACKGROUNDCOLOR`) and `PP_BORDERCOLOR` (group boxes), each also as its `*INDEX` form where `<pmwin.h>` has one. Unverified choices: the limits, the truncation, which attributes each built-in control uses, and that a change is posted rather than sent.

**Static controls.** `SS_TEXT` is aligned by the `DT_*` bits of the style (`DT_LEFT` / `DT_CENTER` / `DT_RIGHT`, `DT_TOP` / `DT_VCENTER` / `DT_BOTTOM`), grey with `DT_HALFTONE`, on one line (`DT_WORDBREAK` is not applied). `SS_GROUPBOX` draws a frame with the text in its top edge and leaves the inside alone. `SS_FGNDRECT` / `SS_BKGNDRECT` / `SS_HALFTONERECT` fill the control with the foreground colour (`PP_FOREGROUNDCOLOR`, else `SYSCLR_WINDOWFRAME`), the background colour (`PP_BACKGROUNDCOLOR`, else the dialog face or a client's white) or a 50 % halftone of the two; `SS_FGNDFRAME` / `SS_BKGNDFRAME` / `SS_HALFTONEFRAME` draw a one-pel frame in them. `SS_ICON` ("#id": an `RT_POINTER` resource), `SS_SYSICON` ("#id": a system pointer; the `SPTR_ICON*` icons have pictures) and `SS_BITMAP` ("#id": an `RT_BITMAP` resource) draw the picture at the control's top-left corner, clipped to it; with `SS_AUTOSIZE`, or a control of no size, the control takes the picture's size, its top-left corner staying. Resources come from the executable. Unverified choices: the default colours, where pictures are placed and anchored.

**Class styles and painting control.** A window gets the window styles its class was registered with (`CS_SYNCPAINT`, `CS_SAVEBITS`, `CS_PARENTCLIP`, `CS_CLIPSIBLINGS`, `CS_CLIPCHILDREN`). `CS_SIZEREDRAW` repaints the whole window on every size change (built-in controls and dialogs always do). A `WS_SYNCPAINT` window that is invalidated gets its `WM_PAINT` before the invalidating call returns (the queued one is withdrawn when it paints). When a standard frame repaints — it is created, invalidated or its client changes size — the client gets `WM_ERASEBACKGROUND` (mp1 = a presentation space on the client, mp2 = the `RECTL` to erase) before its `WM_PAINT`; TRUE has the frame fill the rectangle with `SYSCLR_WINDOW`, `WinDefWindowProc` returns FALSE. `WinLockWindowUpdate` locks one window (`HWND_DESKTOP`: every frame) at a time — another lock fails with FALSE — and nothing is drawn into the frame it is in until `NULLHANDLE` unlocks it; then the frame is repainted with its children. Approximated: Warpine draws all windows of a frame into one surface without clipping one window against another, so `WS_CLIPSIBLINGS`, `WS_PARENTCLIP` and `WS_SAVEBITS` are kept but change nothing, and a lock covers the whole frame of the locked window.

**Scroll bars.** A `WC_SCROLLBAR` window is vertical with `SBS_VERT`, else horizontal. `SBM_SETSCROLLBAR` (mp1 = position, mp2 = `MPFROM2SHORT(first, last)`) sets its range and slider position, `SBM_SETPOS` moves the slider (a position outside the range goes to its nearest end), `SBM_QUERYPOS` and `SBM_QUERYRANGE` (`MRFROM2SHORT(first, last)`) report them, and `SBM_SETTHUMBSIZE` (`MPFROM2SHORT(visible, total)`) makes the slider proportional. `SBCDATA` control data given to `WinCreateWindow` sets the initial range, position and thumb size. A bar without a range, or whose visible part is the whole, is disabled: grey arrows, no slider, and it ignores the mouse. Clicking an arrow sends `SB_LINEUP` / `SB_LINEDOWN` (`SB_LINELEFT` / `SB_LINERIGHT`), clicking the shaft on either side of the slider `SB_PAGEUP` / `SB_PAGEDOWN` (`SB_PAGELEFT` / `SB_PAGERIGHT`), and releasing the button `SB_ENDSCROLL`; holding an arrow or the shaft repeats its command while the pointer stays on it. Dragging the slider sends `SB_SLIDERTRACK` whenever its position changes and `SB_SLIDERPOSITION` with the final position on release (no `SB_ENDSCROLL`). The notifications are posted to the scroll bar's owner as `WM_VSCROLL` / `WM_HSCROLL` with mp1 = the scroll bar's id and mp2 = `MPFROM2SHORT(slider position, command)` (the slider position is 0 except for the slider commands). The scroll bar does not move its slider for line and page commands: the application scrolls and sets the new position with `SBM_SETPOS`. Holding an arrow or the shaft first repeats after `SV_FIRSTSCROLLRATE` milliseconds, then every `SV_SCROLLRATE` (both 100 by default; `WinSetSysValue` changes them). With `SBS_AUTOTRACK` the slider itself follows a drag; without it the slider stays and an outline follows the pointer. A focused scroll bar takes the keyboard: the arrow keys along its axis send the line commands, Page Up / Page Down the page commands, and the key's release `SB_ENDSCROLL`; other keys go to its owner.

**Combination boxes.** A `WC_COMBOBOX` window is an entry field (`CBID_EDIT`) above a list box (`CBID_LIST`); its height includes the list. `CBS_SIMPLE` always shows the list; `CBS_DROPDOWN` drops it below the field when the arrow button is clicked or Alt+Down / F4 is pressed; `CBS_DROPDOWNLIST` does the same with a read-only field showing the selected item, and a click on the field drops the list too. The dropped list lies over the controls below it but stays inside the parent window. Picking an item puts its text into the field and closes the list; Up / Down change the selection from the field; Enter sends `CBN_ENTER` and closes the list; Esc closes it. `CBM_SHOWLIST`, `CBM_HILITE` and `CBM_ISLISTSHOWING` are supported, `LM_*` messages go to the list and `EM_*` messages to the field, and the box's window text is the field's. The owner gets `WM_CONTROL` with `CBN_EFCHANGE`, `CBN_EFSCROLL`, `CBN_MEMERROR`, `CBN_LBSELECT`, `CBN_SHOWLIST` and `CBN_ENTER` (mp2 = the combination box).

**Spin buttons.** A `WC_SPINBUTTON` is a spin field with up and down arrows (`SPBS_MASTER`) or without (a servant, joined to a master with `SPBM_SETMASTER`; the master's arrows spin the member that last had the focus). Values are a numeric range (`SPBM_SETLIMITS`, `SPBM_OVERRIDESETLIMITS`, `SPBM_QUERYLIMITS`) or an array of strings (`SPBM_SETARRAY`); `SPBM_SETCURRENTVALUE`, `SPBM_SPINUP` / `SPBM_SPINDOWN` (wrapping round at the ends), `SPBM_QUERYVALUE` with `SPBQ_UPDATEIFVALID` / `SPBQ_ALWAYSUPDATE` / `SPBQ_DONOTUPDATE`, `SPBM_SETTEXTLIMIT`. Holding an arrow repeats (faster with `SPBS_FASTSPIN`); Up / Down in the field spin it. `SPBS_NUMERICONLY`, `SPBS_READONLY`, `SPBS_JUSTLEFT` / `JUSTRIGHT` / `JUSTCENTER` and `SPBS_PADWITHZEROS` are honoured. Notifications: `SPBN_UPARROW`, `SPBN_DOWNARROW`, `SPBN_ENDSPIN`, `SPBN_CHANGE`, `SPBN_SETFOCUS`, `SPBN_KILLFOCUS`.

**Owner drawing.** A list box with `LS_OWNERDRAW` asks its owner for the item height with `WM_MEASUREITEM` when items are inserted and has each visible item drawn with `WM_DRAWITEM` (`OWNERITEM`: the item's rectangle relative to the list box, index, handle, `fsState` TRUE when selected); a FALSE reply lets the list box draw the item's text, and a TRUE reply with `fsState` ≠ `fsStateOld` makes the list box invert the item. Pull-down menu items with `MIS_OWNERDRAW` are drawn by the owner with `WM_DRAWITEM` into a picture of the item when the pull-down opens. A `BS_USERBUTTON` button is painted by its owner on `WM_CONTROL(BN_PAINT)` with a `USERBUTTON` (`BDS_HILITED`, `BDS_DISABLED`, `BDS_DEFAULT`). These messages are sent synchronously, before the call that caused the painting returns. List boxes also take `LM_QUERYITEMTEXT`, `LM_QUERYITEMTEXTLENGTH`, `LM_SETITEMTEXT`, `LM_SETITEMHANDLE`, `LM_QUERYITEMHANDLE`, `LM_SEARCHSTRING`, `LM_SETTOPINDEX`, `LM_QUERYTOPINDEX`, `LM_SETITEMHEIGHT` and sorted insertion (`LIT_SORTASCENDING` / `LIT_SORTDESCENDING`); entry fields take `EM_SETTEXTLIMIT` and align their text with `ES_CENTER` / `ES_RIGHT`. Sliders (`SLS_OWNERDRAW`) and value sets (`VIA_OWNERDRAW` items, `VS_OWNERDRAW` background) are owner-drawn the same way (see below). Not yet: `WM_MEASUREITEM` for menus.

**Circular sliders.** A `WC_CIRCULARSLIDER` (`WinRegisterCircularSlider` succeeds; the class is always there) is a round dial with tick marks every tick increment, its value in the middle, a knob at the value, a − and a + button at its lower corners (not with `CSS_NOBUTTON`) and its window text under it (not with `CSS_NOTEXT`; `CSS_NONUMBER` hides the value, `CSS_NOTICKS` the ticks). The dial sweeps 270° clockwise from lower left, a whole turn from the top with `CSS_360`. Messages: `CSM_SETRANGE` (mp1 = low, mp2 = high; FALSE unless low < high), `CSM_QUERYRANGE` (two PSHORT), `CSM_SETVALUE` (FALSE outside the range), `CSM_QUERYVALUE` (PSHORT), `CSM_QUERYRADIUS` (PUSHORT, pels), `CSM_SETINCREMENT` (mp1 = the step of the buttons and keys, not 0; mp2 = the tick spacing), `CSM_QUERYINCREMENT`, `CSM_SETBITMAPDATA` (kept, not drawn). Defaults: 0–100, value 0, step 1, a tick every 10. Dragging on the dial turns it (`CSS_POINTSELECT`: a press moves the value to the pointer); the buttons step; Left / Down and Right / Up step, Page Down / Page Up step by the tick spacing, Home / End go to the ends; `CSS_CIRCULARVALUE` with `CSS_360` wraps past the ends. The owner gets `WM_CONTROL` with `CSN_TRACKING` while the dial is dragged and `CSN_CHANGED` after a change (also from `CSM_SETVALUE`), mp2 = the value; `CSN_SETFOCUS` with mp2 = TRUE or FALSE. `CSN_QUERYBACKGROUNDCOLOR` is not sent. ADR-0120: the look and these details are Warpine's own.

**Sliders.** A `WC_SLIDER` is a horizontal (`SLS_HORIZONTAL`) or vertical (`SLS_VERTICAL`) shaft with an arm, created with `SLDCDATA` (`WinCreateWindow` control data or a dialog item's `CTLDATA`) giving the increments and spacing of two scales; the primary scale (`SLS_PRIMARYSCALE1` / `SLS_PRIMARYSCALE2`) sets the positions the arm steps between. A spacing makes the shaft as long as the increments need; a spacing of 0 divides a shaft that fills the window. Scale 1 lies above a horizontal shaft and right of a vertical one, scale 2 below / left; ticks (`SLM_SETTICKSIZE`, none until set) and texts (`SLM_SETSCALETEXT`) are drawn on the primary scale. Positions are pixels from home: the left or bottom end, or the right / top end with `SLS_HOMERIGHT` / `SLS_HOMETOP`. `SLS_CENTER` / `SLS_TOP` / `SLS_BOTTOM` (`SLS_LEFT` / `SLS_RIGHT`) place the slider across the window; `SLS_BUTTONSLEFT` / `RIGHT` (`BOTTOM` / `TOP`) add two arrow buttons at that end; `SLS_RIBBONSTRIP` fills the shaft from home to the arm; `SLS_SNAPTOINCREMENT` snaps a released arm to the nearest increment; `SLS_READONLY` takes no input, draws a narrow arm and no buttons. Messages: `SLM_SETSLIDERINFO` / `SLM_QUERYSLIDERINFO` (`SMA_SHAFTDIMENSIONS` — only the breadth can be set —, `SMA_SHAFTPOSITION`, `SMA_SLIDERARMDIMENSIONS`, `SMA_SLIDERARMPOSITION` as `SMA_RANGEVALUE` pixels or `SMA_INCREMENTVALUE`), `SLM_SETTICKSIZE` (one tick or `SMA_SETALLTICKS`), `SLM_QUERYTICKSIZE`, `SLM_QUERYTICKPOS`, `SLM_SETSCALETEXT`, `SLM_QUERYSCALETEXT`, `SLM_ADDDETENT`, `SLM_REMOVEDETENT`, `SLM_QUERYDETENTPOS`. The mouse drags the arm, a click on the shaft moves it one increment towards the pointer, a click on a button one increment in its direction (both repeat while held), a click on a detent moves it there; Left / Right (Down / Up on a vertical slider) step one increment, with Shift to the next detent, and Home / End go to the ends. The owner gets `WM_CONTROL` with `SLN_SLIDERTRACK` while the arm is dragged and `SLN_CHANGE` when it has moved (mp2 = the new position in pixels from home; also when `SLM_SETSLIDERINFO` moves it), `SLN_SETFOCUS` and `SLN_KILLFOCUS`. A focused slider shows a black square on its arm. `SLS_OWNERDRAW` asks the owner (`WM_DRAWITEM`, `idItem` = `SDA_BACKGROUND`, `SDA_SLIDERSHAFT`, `SDA_RIBBONSTRIP`, `SDA_SLIDERARM`) to draw each part; FALSE lets the slider draw it. Button 2 moves the arm's middle to the pointer and drags it until released (`SLN_SLIDERTRACK`, then `SLN_CHANGE`). The sizes (shaft breadth 8, arm 10 × 20, buttons 16 pels) are Warpine's own.

**Notebooks.** A `WC_NOTEBOOK` holds pages in order, each with an id (`BKM_INSERTPAGE`: mp1 = a reference page, mp2 = `MPFROM2SHORT(style, BKA_FIRST / BKA_LAST / BKA_NEXT / BKA_PREV)`; returns the id, 0 on failure).

*Pages.* A page's style gives it a major tab (`BKA_MAJOR`) or a minor tab (`BKA_MINOR`; shown while the top page lies in its major section), a status line (`BKA_STATUSTEXTON`), and a page window sized to the page (`BKA_AUTOPAGESIZE`). The first page inserted is the top page. Only the top page's window (`BKM_SETPAGEWINDOWHWND`, usually a dialog loaded with the notebook as parent) is shown; the others are hidden. `BKM_SETPAGEINFO` can have the notebook load the page's dialog itself, from a dialog resource (`BFA_PAGEFROMDLGRES`: `idPageDlg`, `hmodPageDlg`) or a `DLGTEMPLATE` in memory (`BFA_PAGEFROMDLGTEMPLATE`: `pdlgtPage`), with `pfnPageDlgProc` and `pPageDlgCreateParams` (`WM_INITDLG`'s mp2); `bLoadDlg` TRUE loads it at once, FALSE when the page is first turned to (ADR-0064).

*Layout.* Major tabs run down the right (`BKS_MAJORTABLEFT` / `TOP` / `BOTTOM` move them) and minor tabs along the bottom (along the right for top or bottom major tabs). The status line (`BKS_STATUSTEXT*` alignment) and two page buttons, previous and next, lie under the page, and back-page edges right of and below it. `BKS_TABBEDDIALOG` puts the major tabs in a row on top, with no minor tabs, status line or buttons. Tabs that do not fit their band scroll: two arrows at its end move it by one tab, and the current tab is brought into view at every turn. A tab shows its bitmap (`BKM_SETTABBITMAP`, stretched) instead of its text, on its own colour (`BKM_SETTABCOLOR`: mp2 an RGB colour, `BKA_AUTOCOLOR` for the notebook's). Notebook buttons (`BKM_SETNOTEBOOKBUTTONS`: mp1 = how many, at most 32, mp2 → `NOTEBOOKBUTTON`s; ids up to `BKA_MAXBUTTONID`) are push buttons of kind `BS_NOTEBOOKBUTTON` in a row along the notebook's bottom, common to all pages; their `WM_COMMAND` goes to the top page's window.

- `BKM_TURNTOPAGE`;
- `BKM_QUERYPAGEID` (mp2 = `MPFROM2SHORT(BKA_FIRST / LAST / NEXT / PREV / TOP, style filter)`);
- `BKM_QUERYPAGECOUNT` (mp1 / mp2 = first / last page, 0 = the ends, both counted);
- `BKM_QUERYPAGESTYLE`;
- `BKM_SET` / `QUERYPAGEDATA`, `BKM_SET` / `QUERYPAGEWINDOWHWND`, `BKM_SET` / `QUERYTABTEXT`, `BKM_SET` / `QUERYSTATUSLINETEXT` (queries through a `BOOKTEXT`; a NULL pointer gives the length), `BKM_SET` / `QUERYTABBITMAP`, `BKM_SETTABCOLOR`, `BKM_SETNOTEBOOKBUTTONS`;
- `BKM_SETDIMENSIONS` (`BKA_MAJORTAB` / `MINORTAB` / `PAGEBUTTON`);
- `BKM_CALCPAGERECT` (TRUE: notebook rectangle → page rectangle, FALSE: back);
- `BKM_SETNOTEBOOKCOLORS` (the `BKA_*COLOR[INDEX]` attributes);
- `BKM_INVALIDATETABS`;
- `BKM_SETPAGEINFO` / `QUERYPAGEINFO` (`BFA_PAGEDATA`, `PAGEFROMHWND`, `PAGEFROMDLGRES`, `PAGEFROMDLGTEMPLATE`, `STATUSLINE`, the tab texts and bitmaps).

A bad page id gives `BOOKERR_INVALID_PARAMETERS`.

*Input.* A click on a tab turns to its page, and the page buttons turn one page. On a focused notebook, PageUp / PageDown turn one page, Left / Up and Right / Down go to the previous / next major tab, and Home / End to the first / last page. Other keys go to the notebook's owner, so in a dialog Tab moves from the notebook into its top page's controls and from the page's last control on to the dialog's next one.

*Notifications* go to the owner as `WM_CONTROL`. Every turn first sends `BKN_PAGESELECTEDPENDING` (mp2 → `PAGESELECTNOTIFY`); setting its `ulPageIdNew` to 0 keeps the current page. `BKN_PAGESELECTED` (mp2 → `PAGESELECTNOTIFY`: notebook, current and new page) and `BKN_PAGEDELETED` (mp2 → `DELETENOTIFY`: notebook, page window, page data, tab bitmap) are sent, so the owner has read them when the call that caused them returns. `BKN_NEWPAGESIZE` is posted when the notebook's size changes.

A notebook button shows its `hImage` (a bitmap) left of its text. `BKS_ROUNDEDTABS` / `BKS_POLYGONTABS` cut the tabs' outer corners round or straight (square by default); `BKS_SPIRALBIND` draws loops along the page's bound edge; `BKS_BACKPAGESBR` / `BL` / `TR` / `TL` put the back pages towards that corner (bottom right by default), the binding on the other side. Sizes, colours and these shapes are Warpine's own.

**Containers.** A `WC_CONTAINER` shows records that live in the application's memory (ADR-0043).

*Records.* `CM_ALLOCRECORD` (mp1 = bytes of application data after the core, mp2 = number of records) returns the first of a chain of zeroed `RECORDCORE`s (`MINIRECORDCORE`s with `CCS_MINIRECORDCORE`) linked by `preccNextRecord`, with `cb` set to the core size. The application fills `pszIcon`, `pszText`, `pszName`, `pszTree` and its own fields directly; the container reads them when it paints, so a change shows after `CM_INVALIDATERECORD`. `CM_INSERTRECORD` (a chain) and `CM_INSERTRECORDARRAY` (an array) take a `RECORDINSERT`: `pRecordOrder` is `CMA_FIRST`, `CMA_END` or the record to insert after, `pRecordParent` a parent for the tree hierarchy. They return the number of records, or 0 (a record not allocated by this container, or inserted already: `PMERR_RECORD_CURRENTLY_INSERTED`). `CM_REMOVERECORD` (mp2 = `MPFROM2SHORT(count, CMA_FREE | CMA_INVALIDATE)`, count 0 = all) also removes the records' children and returns the number left. `CM_FREERECORD` refuses inserted records. `CM_QUERYRECORD` walks `CMA_FIRST` / `CMA_LAST` / `CMA_NEXT` / `CMA_PREV` / `CMA_PARENT` / `CMA_FIRSTCHILD` / `CMA_LASTCHILD`.

*Views.* `CM_SETCNRINFO` / `CM_QUERYCNRINFO` exchange a `CNRINFO`. Its `flWindowAttr` chooses the view:
- `CV_TEXT` shows `pszText`, `CV_NAME` shows `pszName`, both in one column or flowing into columns with `CV_FLOW`.
- `CV_DETAIL` shows one column per field info (`CM_ALLOCDETAILFIELDINFO`, `CM_INSERTDETAILFIELDINFO` with a `FIELDINFOINSERT`, `CM_QUERYDETAILFIELDINFO`, `CM_REMOVEDETAILFIELDINFO`, `CM_FREEDETAILFIELDINFO`). A column reads `CFA_STRING`, `CFA_ULONG`, `CFA_DATE` (`CDATE`, in the country's date format) or `CFA_TIME` (`CTIME`) at `offStruct` in each record. It is aligned by `CFA_LEFT` / `CFA_RIGHT` / `CFA_CENTER`, separated by `CFA_SEPARATOR` / `CFA_HORZSEPARATOR`, hidden by `CFA_INVISIBLE`, and sized to its contents when `cxWidth` is 0. `CA_DETAILSVIEWTITLES` shows the column titles.
- `CA_CONTAINERTITLE` shows `pszCnrTitle` (`CA_TITLELEFT` / `CA_TITLERIGHT`, `CA_TITLESEPARATOR`).
- `CV_ICON` (the default) shows each record's icon at `ptlIcon` (its lower-left corner, in workspace coordinates; `CNRINFO.ptlOrigin` is the workspace point at the work area's lower-left corner) with `pszIcon` centred under it, one line per line of the text. `CM_ARRANGE(CMA_ARRANGESTANDARD, 0)` places the shown records in rows from the upper left, writing their `ptlIcon`, and scrolls back to the origin; with `CCS_AUTOPOSITION` the container does that whenever records are inserted, removed, filtered, sorted or invalidated. The icon view scrolls by pels.
- Pictures: the icon, name (icon left of `pszName`) and tree views (unless `CV_TREE | CV_TEXT`) draw each record's `hptrIcon`, or `hbmBitmap` with `CA_DRAWBITMAP` (unless `CA_DRAWICON` is also set), stretched to `slBitmapOrIcon` (the tree view: `slTreeBitmapOrIcon`; 0 = 32 × 32, 16 × 16 with `CV_MINI` and in the tree view). `CV_MINI` uses `hptrMiniIcon` / `hbmMiniBitmap` when set. Icons are pointers (`WinLoadPointer`, `WinQuerySysPointer`: Warpine draws its own pictograms for `SPTR_FILE`, `SPTR_FOLDER`, `SPTR_MULTFILE`, `SPTR_PROGRAM`, `SPTR_APPICON` and the message-box icons). A `CFA_BITMAPORICON` detail column draws the handle stored at `offStruct`.
- A mini-record container shows `pszIcon` in every view.

*Selection.* `CCS_SINGLESEL` (the default), `CCS_MULTIPLESEL` or `CCS_EXTENDSEL`:
- A click selects and moves the cursor. With extended selection, Shift extends from the anchor and Ctrl toggles.
- The arrow keys, PageUp / PageDown and Home / End move the cursor, and the selection with it except in multiple selection or with Ctrl. Space toggles the selection.
- `CM_SETRECORDEMPHASIS` (mp2 = `MPFROM2SHORT(on, CRA_*)`) and `CM_QUERYRECORDEMPHASIS` (the next record with all the given bits) work on `flRecordAttr`.

*Tree view.* `CV_TREE` shows the top-level records and, under each expanded record (`CRA_EXPANDED`), its children, indented by `cxTreeIndent` (16 pels by default). It shows `pszTree`. A record with children has an expander box: a click on it, `+` / `-`, or Right / Left on the cursored record opens and closes it. Right on an open record goes to its first child, and Left on a child goes to its parent. `CM_EXPANDTREE` / `CM_COLLAPSETREE` (mp1 = record, NULL = every record) do the same in code. Each change sends `CN_EXPANDTREE` / `CN_COLLAPSETREE` (mp2 = the record). Collapsing a record moves the cursor out of its hidden children. `CA_TREELINE` draws lines from each record to its children, `cxTreeLine` pels wide (1 by default). An expander is a picture when the record's `TREEITEMDESC` (`pTreeItemDesc`: `hbmExpanded`, `hbmCollapsed`, `hptrExpanded`, `hptrCollapsed`) or `CNRINFO` (`CMA_TREEICON` / `CMA_TREEBITMAP`) has one for its state — icons first, bitmaps with `CA_DRAWBITMAP` alone — drawn 16 pels wide. `CM_MOVETREE` (mp1 → `TREEMOVE`) moves a record and its descendants (with `flMoveSiblings` also the siblings after it) under `preccNewParent` (NULL: the top level) at `pRecordOrder` (`CMA_FIRST`, `CMA_END` or a child); a record cannot move under itself or its descendants.

*Sorting.* `CM_SORTRECORD` (mp1 = `SHORT EXPENTRY pfnCompare(PRECORDCORE p1, PRECORDCORE p2, PVOID pStorage)`, mp2 = `pStorage`) sorts each level, the top level and each record's children separately. It calls the function once per comparison before it returns, and the result is stable. A negative or 0 result keeps p1 first. With `CNRINFO.pSortRecord` set (`CMA_PSORTRECORD`), each insertion sorts the parent's children with that function (`pStorage` NULL). If the function adds or removes records meanwhile, the order is left as it was and `CM_SORTRECORD` returns FALSE.

*Scrolling.* When the rows do not fit (and the view does not flow), a vertical scroll bar (`CID_VSCROLL`, `WinWindowFromID(hwndCnr, CID_VSCROLL)`) appears on the right. Its arrows, shaft and slider scroll the rows, and each move sends `CN_SCROLL` (mp2 → `NOTIFYSCROLL`: container, pels scrolled, `CMA_VERTICAL`). When the details view's columns, or the icon view's workspace, are wider than the container, a horizontal scroll bar (`CID_HSCROLL`) appears at the bottom and scrolls across (16 pels an arrow), sending `CN_SCROLL` with `CMA_HORIZONTAL`; `CM_SCROLLWINDOW(CMA_HORIZONTAL, pels)` scrolls across from the program.

*Split details view.* `CNRINFO.pFieldInfoLast` (`CMA_PFIELDINFOLAST`) names the last column of the left pane and `xVertSplitbar` (`CMA_XVERTSPLITBAR`) where the split bar stands, in pels from the left (0: the middle). Each pane scrolls across on its own, with its own scroll bar (`CID_HSCROLL` on the left, `CID_RIGHTHSCROLL` on the right). Dragging the split bar with button 1 moves it, and `CM_QUERYCNRINFO` reports its new place; `CM_QUERYVIEWPORTRECT(MPFROM2SHORT(CMA_WINDOW, TRUE))` gives the right pane's area.

*Owner drawing.* With `CA_OWNERDRAW` the owner draws every record, and a column with `CFA_OWNER` its cells: `WM_DRAWITEM` (mp1 = the container's id, mp2 → `OWNERITEM` with the item's rectangle relative to the container, `idItem` = `CMA_ICON` or `CMA_TEXT`, `fsState` TRUE when selected, `fsAttribute` = `flRecordAttr`, `hItem` → `CNRDRAWITEMINFO` with `pRecord` and `pFieldInfo`) is sent before the call that painted returns. TRUE keeps what the owner drew; FALSE lets the container draw the item.

*Filtering.* `CM_FILTER` (mp1 = `BOOL EXPENTRY pfnFilter(PRECORDCORE p, PVOID pStorage)`, mp2 = `pStorage`) calls the function for every record before it returns; records it answers FALSE get `CRA_FILTERED` and are not shown, the others are shown. mp1 = NULL shows every record again. `CM_QUERYRECORD` with `CMA_FILTER` added to the command (`MPFROM2SHORT(CMA_NEXT | CMA_FILTER, CMA_ITEMORDER)`) passes over filtered records.

*Direct editing.* Alt + button 1 on a record's text, the container title or a column heading, or `CM_OPENEDIT` (mp1 → `CNREDITDATA` with `pRecord` and, in the details view, the `CFA_STRING` column's `pFieldInfo`), opens an MLE (`CID_MLE`) over the text with all of it selected and sends `CN_BEGINEDIT`. A click in the container or `CM_CLOSEEDIT` keeps the edit: `CN_REALLOCPSZ` asks the owner for room (`cbText` = the new text's bytes with the NUL); when it returns TRUE the container copies the text into the string `*ppszText` then points to — the owner may point it at a new buffer —, and `CN_ENDEDIT` follows. Esc, Alt + button 1 or scrolling discards the edit (`CN_ENDEDIT` only). Every notification's mp2 points to a `CNREDITDATA` (`ppszText` = the record's `PSZ` field, `id` = the container's id, `CID_LEFTDVWND` in the details view). `CCS_READONLY`, `CRA_RECORDREADONLY` and `CFA_FIREADONLY` prevent editing. The container title and column headings cannot be edited yet.

`CM_SEARCHSTRING` finds a record by prefix or substring, with or without case. `CM_QUERYRECORDRECT` gives a shown record's rectangle (`fsExtent`: `CMA_ICON` the icon, `CMA_TEXT` the text, both the two together), and `CM_QUERYVIEWPORTRECT(CMA_WINDOW)` gives the rows' area. `CM_QUERYRECORDFROMRECT` (mp1 = `CMA_FIRST` or the record to search after, mp2 → `QUERYRECFROMRECT`) returns the next shown record lying partly (`CMA_PARTIAL`) or wholly (`CMA_COMPLETE`) in the rectangle, in item order or, with `CMA_ZORDER`, topmost first. `CM_SCROLLWINDOW(CMA_VERTICAL)` scrolls by rows (by pels in the icon view).

*Notifications* go to the owner as `WM_CONTROL`:
- `CN_EMPHASIS` (mp2 → `NOTIFYRECORDEMPHASIS`: container, record, changed bits) and `CN_ENTER` (mp2 → `NOTIFYRECORDENTER`: container, `fKey`, record; from a double click or Enter) are sent, so the owner has read them when the call that caused them returns.
- `CN_SETFOCUS` / `CN_KILLFOCUS` are posted.

*Drag and drop.* A container takes part in drags (see "Drag and drop" below): `WM_BEGINDRAG` over it sends `CN_INITDRAG` to the owner (mp2 → `CNRDRAGINIT`: container, record under the pointer or NULL, desktop position, offset to the record's origin), and as a target it asks the owner with `CN_DRAGOVER` / `CN_DRAGLEAVE` / `CN_DROP` (mp2 → `CNRDRAGINFO`: the `DRAGINFO` and the record under the pointer), passing the owner's reply to `DM_DRAGOVER` on. With `CA_ORDEREDTARGETEMPH` in the name, text and details views it sends `CN_DRAGAFTER` instead, naming the record the drop goes after (`CMA_FIRST`: before the first; a row's upper half puts the drop before it, its lower half after it); with `CA_MIXEDTARGETEMPH` the middle half of a row is `CN_DRAGOVER` on that record. While the owner answers `DOR_DROP` the container draws target emphasis: an outline round the record (round the whole container over white space), or an insertion line for `CN_DRAGAFTER`. Records with `CRA_TARGET` are outlined too.

The title is edited with `CNREDITDATA.id` = `CID_CNRTITLEWND` (not with `CA_TITLEREADONLY`): `ppszText` points to a cell holding the title's `PSZ`, which the owner may change in `CN_REALLOCPSZ`, and the string it then names becomes the title. A column heading is edited with `CID_LEFTCOLTITLEWND` / `CID_RIGHTCOLTITLEWND` and `pFieldInfo` (not with `CFA_FITITLEREADONLY`); `ppszText` points to its `pTitleData`.

*Icon view, more.* The icon view stacks its records: insertion puts them on top, `RECORDINSERT.zOrder` = `CMA_BOTTOM` at the bottom; drawing, hits and `CM_QUERYRECORDFROMRECT` with `CMA_ZORDER` follow the stacking. `CM_SETGRIDINFO` (mp1 → `GRIDINFO`: `cxGrid` × `cyGrid`, up to 1024) sets the grid square, `CM_QUERYGRIDINFO` reports it with the rows and columns of the work area, and `CM_ARRANGE(CMA_ARRANGEGRID, 0)` puts the icons in squares row by row from the upper left; mp2 = `CMA_ARRANGESELECTED` arranges only the selected records. `CM_ERASERECORD` (mp1 = record) leaves a record out of the view until `CM_INVALIDATERECORD` names it or every record. `CM_QUERYVIEWPORTRECT(MPFROM2SHORT(CMA_WORKSPACE, …))` gives the workspace in workspace coordinates (the icon view: everything its items cover and the work area; the other views: their content from (0, 0)).

*Context menus, help, the wheel.* `WM_CONTEXTMENU` on a container — a button-2 click or Shift+F10 — sends `CN_CONTEXTMENU` to the owner with the record under the pointer (from the keyboard: the cursored record; mp2 NULL over no record), and `WM_HELP` sends `CN_HELP` with the cursored record. The mouse wheel scrolls the rows like the scroll bar (`CN_SCROLL`).

*Not yet:* `CA_OWNERPAINTBACKGROUND`, the grid's square list (`pGrid`, `CN_GRIDRESIZED`), and records shared between containers.

**Context menus and the wheel.** Clicking button 2 without moving the pointer far enough to start a drag sends `WM_CONTEXTMENU` (Warp 4; mp1 = the point in the window, mp2 = TRUE) to the window under the pointer after its `WM_BUTTON2UP`; Shift+F10 sends it to the focus window instead of a `WM_CHAR` (mp1 = 0, mp2 = FALSE). Each notch of the mouse wheel sends three `WM_VSCROLL` messages (mp1 = 0, mp2 = `MPFROM2SHORT(0, SB_LINEUP / SB_LINEDOWN)`) to the window under the pointer, or a scroll bar's owner, as OS/2 wheel drivers do (ADR-0067).

**Drag and drop** (PMDRAG; between programs below). Pressing button 2 (the drag button) and moving the pointer 4 pels posts `WM_BEGINDRAG` (mp1 = the press point in the window's coordinates, mp2 = TRUE) to the window under the press. A source then builds a `DRAGINFO`:
- `DrgAllocDraginfo(cditem)` returns it zeroed with its sizes, `usOperation` = `DO_DEFAULT` and the pointer position; `DrgSetDragitem` / `DrgQueryDragitem` / `DrgQueryDragitemPtr` / `DrgQueryDragitemCount` fill and read its `DRAGITEM`s.
- String handles (`DrgAddStrHandle`, `DrgQueryStrName` / `Len`, `DrgDeleteStrHandle`, `DrgDeleteDraginfoStrHandles`) hold the type list (`"type[,type…]"`, the first the true type), the rendering mechanisms and formats (`<mech,fmt>` pairs and `(m1,m2)x(f1,f2)` cross products, the first pair native) and the container, source and target names.
- `DrgVerifyType` / `DrgVerifyTrueType` / `DrgVerifyTypeSet` / `DrgQueryTrueType`, `DrgVerifyRMF` (NULL = any) / `DrgVerifyNativeRMF` / `DrgQueryNativeRMF` test them.

`DrgDrag(hwndSource, pdinfo, pdimg, cdimg, vkTerminate, pRsvd)` runs the drag and returns when it ends: `VK_BUTTON1`..`3` or `VK_ENDDRAG` (button 2) end it on release, Esc abandons it.
- Each move sends `DM_DRAGOVER` (mp1 = the `DRAGINFO`, mp2 = the pointer in desktop coordinates) to the window under the pointer and `DM_DRAGLEAVE` to the one it left. The reply `MRFROM2SHORT(DOR_*, DO_*)` decides the pointer: the illegal sign unless `DOR_DROP`. After `DOR_NEVERDROP` the window gets no more `DM_DRAGOVER` until the pointer leaves it. `WinDefWindowProc` answers `DOR_NEVERDROP`; built-in controls other than containers never accept.
- On the release, `DM_DROP` goes to the window if its last reply was `DOR_DROP`, and `DrgDrag` returns that window; otherwise the window gets `DM_DRAGLEAVE` and `DrgDrag` returns NULLHANDLE. `xDrop` / `yDrop` hold the last pointer position.
- While `DrgDrag` runs, `DrgFreeDraginfo` of its `DRAGINFO` fails with `PMERR_SOURCE_SAME_AS_TARGET`: the target only reads it, the source frees it after `DrgDrag` returns. `DrgQueryDragStatus` reports `DGS_DRAGINPROGRESS`.
- Ctrl, Shift and Ctrl+Shift held set `usOperation` to `DO_COPY`, `DO_MOVE` and `DO_LINK` (none: `DO_DEFAULT`) before each `DM_DRAGOVER` and the `DM_DROP`; pressing or releasing them sends `DM_DRAGOVER` again (ADR-0068).
- Button 2 coming up after `WM_BEGINDRAG` without a drag running sends `WM_ENDDRAG` (mp1 = the point in the window, mp2 = TRUE) to the window under the pointer. `WinDefWindowProc` sends `WM_BEGINDRAG`, `WM_ENDDRAG` and `WM_CONTEXTMENU` on to the window's owner, as it does `WM_CHAR`, so a child window's gestures reach the window that owns it.

**Files** (ADR-0068). A file item is a `DRAGITEM` with the RMF `<DRM_OS2FILE,DRF_UNKNOWN>`, the file's directory (with its trailing backslash) as the container name, its name as source and target name, type `Unknown` unless given, `fsSupportedOps` = `DO_COPYABLE | DO_MOVEABLE`, and `DC_CONTAINER` for a directory; a target reads the file itself by the two names.
- `DrgDragFiles(hwnd, apszFiles, apszTypes, apszTargets, cFiles, hptrDrag, vkTerminate, fSourceRender, ulRsvd)` drags such items, one per fully qualified file name (types and target names may be NULL), from window `hwnd` as `DrgDrag` does, with pointer `hptrDrag` over a target that accepts; it frees the `DRAGINFO` and its string handles and returns TRUE when the files were dropped.
- Host files dropped on the desktop (from a file manager; `drop X Y PATH` in a GUI script) reach the window under the pointer as the same items, with no source window (`hwndSource` NULLHANDLE): `DM_DRAGOVER`, then `DM_DROP` if it answers `DOR_DROP`, else `DM_DRAGLEAVE`. They run on the window's own thread, as messages sent from elsewhere. After `DM_DROP` the `DRAGINFO` is the target's to free (`DrgDeleteDraginfoStrHandles`, `DrgFreeDraginfo`). Only files inside the program's drives are named, by their OS/2 paths; others are left out (ADR-0066). On the session's desktop the server sends the drop to the program under the pointer.
- `DrgQueryDraginfoPtr(pdinfo)` walks the program's `DRAGINFO`s (NULL: the first; NULL after the last), `DrgQueryDraginfoPtrFromHwnd(hwnd)` finds the one whose source is `hwnd`, and `DrgReallocDraginfo(pdinfo, cditem)` returns a `DRAGINFO` for `cditem` items with the old header and the items that fit, freeing the old one (not while it is dragged).

**Between programs** (on the session's desktop, ADR-0057), the window under the pointer may be another program's: it gets `DM_DRAGOVER` / `DM_DRAGLEAVE` / `DM_DROP` on its own thread, as a message sent from another program (`WinInSendMsg` TRUE), and a container there asks its owner with `CN_*`. `DrgDrag` waits for each reply and meanwhile runs the messages sent to its thread, so a target's `DM_RENDER` reaches the source during `DM_DROP`. `DrgAllocDraginfo` and `DrgAllocDragtransfer` then allocate in the session's shared memory: the source's `DRAGINFO` is given to the target's process before it is sent there (`DrgAccessDraginfo` succeeds in the target, whose `DrgFreeDraginfo` lets its access go), `DrgPushDraginfo` gives it to a window's process, and `DrgSendTransferMsg` / `DrgPostTransferMsg` to another program's window give it the `DRAGTRANSFER` array (`DrgFreeDragtransfer` lets it go). String handles are the session's: a handle one program adds names the same string in every program, and `DrgDeleteStrHandle` / `DrgDeleteDraginfoStrHandles` anywhere drop its count. Warpine's choices (unverified): handles outlive the program that added them; a string is at most 16 KB of text.

`DrgAllocDragtransfer` / `DrgFreeDragtransfer`, `DrgSendTransferMsg` / `DrgPostTransferMsg` (which clear `fsReply` and send or post), `DrgGetPS` / `DrgReleasePS` and `DrgSetDragPointer` support the rendering conversation and target emphasis between the program's windows. The drag image: `DrgDrag`'s `DRAGIMAGE`s (`DRG_ICON`: a pointer handle; `DRG_BITMAP`: a bit map; stretched to `sizlStretch` with `DRG_STRETCH`), each with its lower-left corner at `cxOffset` / `cyOffset` from the pointer's hot spot, the first at the bottom, are drawn as the pointer (at most 256 × 256 pels round the hot spot); over a window that refuses the drop a red "no" sign covers the hot spot; a pointer set with `DrgSetDragPointer` shows instead over a window that accepts. `DrgSetDragImage` replaces the images while the `DRAGINFO`'s drag runs (outside one it only checks the `DRAGINFO`). *Not yet:* `DrgAcceptDroppedFiles`, `DrgQueryFormat`, lazy drag, polygon and `DRG_TRANSPARENT` images, the position of a host drop on real displays (the last pointer position is used; SDL's drop events give none here).

**Value sets.** A `WC_VALUESET` is a grid of items created with `VSCDATA` (rows × columns; 1 × 1 without). Items are addressed by `MPFROM2SHORT(row, column)` from 1, rows from the top, columns from the left — from the right with `VS_RIGHTTOLEFT`. An item is a bit map (`VIA_BITMAP`, the default), an icon (`VIA_ICON`, a pointer handle), a text (`VIA_TEXT`, with a `~` mnemonic underlined), an RGB colour (`VIA_RGB`) or a colour index (`VIA_COLORINDEX`); the `VS_*` style of the same name sets the type of every item, `VM_SETITEMATTR` changes one item's type or sets `VIA_DISABLED` (shown dimmed, cannot be selected), `VIA_OWNERDRAW`, `VIA_DRAGGABLE` and `VIA_DROPONABLE` (see drag and drop below). Items fill the window divided by rows and columns until `VM_SETMETRICS(VMA_ITEMSIZE)` sets their size; `VMA_ITEMSPACING` sets the gaps (0 by default). `VS_BORDER` draws a border round the control, `VS_ITEMBORDER` one round each item, `VS_SCALEBITMAPS` stretches bit maps to the item (else they are centred). Messages: `VM_SETITEM`, `VM_QUERYITEM` (a text item through a `VSTEXT`; a buffer length of 0 returns the length), `VM_SETITEMATTR`, `VM_QUERYITEMATTR`, `VM_SELECTITEM`, `VM_QUERYSELECTEDITEM`, `VM_SETMETRICS`, `VM_QUERYMETRICS`. Row 1, column 1 is selected at first; the selected item has a black box, the selection cursor of a focused value set a dotted outline. A click selects an item, a double click or Enter sends `VN_ENTER`; the arrow keys move the selection, Home / End to the ends of the row, Ctrl+Home / Ctrl+End to the first / last item, PageUp / PageDown to the top / bottom row. The owner gets `WM_CONTROL` with `VN_SELECT` and `VN_ENTER` (mp2 = `MPFROM2SHORT(row, column)`), `VN_SETFOCUS` and `VN_KILLFOCUS`. A `VIA_OWNERDRAW` item is drawn by the owner (`WM_DRAWITEM`, `idItem` = `VDA_ITEM`, `hItem` = `MPFROM2SHORT(row, column)`), and a `VS_OWNERDRAW` value set has its background drawn by the owner (`VDA_BACKGROUND`). Drag and drop: `WM_BEGINDRAG` on a `VIA_DRAGGABLE` item sends `VN_INITDRAG` (mp2 → `VSDRAGINIT`: the value set, the pointer in desktop coordinates, its offset to the item's origin, the row and column); as a target the value set asks its owner with `VN_DRAGOVER` / `VN_DRAGLEAVE` / `VN_DROP` (mp2 → `VSDRAGINFO`: the `DRAGINFO` and the row and column of the `VIA_DROPONABLE` item under the pointer, 0 and 0 elsewhere), passing the reply to `DM_DRAGOVER` on. Not yet: `VN_DROPHELP`, `VN_HELP`.

**Text cursor.** `WinCreateCursor` creates the cursor of the calling thread's message queue (a queue has one; a new one replaces it) in window coordinates — a zero width or height is one pel —, solid, halftone (`CURSOR_HALFTONE`) or a frame (`CURSOR_FRAME`), blinking at `SV_CURSORRATE` with `CURSOR_FLASH`, clipped to the window and to the clip rectangle if one is given; `CURSOR_SETPOS` only moves the existing cursor. A new cursor is hidden: `WinShowCursor(TRUE)` shows it, `WinShowCursor(FALSE)` hides it again, and the calls count (it shows when every hide is matched by a show; showing a visible cursor returns FALSE). `WinQueryCursorInfo` fills a `CURSORINFO` (FALSE without a cursor), and `WinDestroyCursor` destroys the cursor if it belongs to the window; destroying the window or the queue destroys it too. The cursor inverts the pels under it on the screen and is never part of the window's own drawing, so painting under it leaves no trace.

**Keyboard and mouse input (type-ahead).** Input waits in one system queue and is routed when a thread reads it with `WinGetMsg` or `WinPeekMsg` (or inside a modal dialog), as in PM: a key goes to the window that has the focus at that moment, so keys typed while a program is busy follow a focus change the program makes when it handles an earlier key. A thread gets its posted messages first (in the order they were posted), then input, then `WM_PAINT`, then `WM_TIMER`; input is handed out in order: an event for another thread's window waits until that thread reads it. Typed characters are encoded in the codepage of the queue that receives them. A mouse message goes to the deepest visible window under the pointer — a child window of any class, a control, a grandchild — unless the capture or a built-in control held with button 1 takes it; static controls let it through, a disabled window passes it to its parent (ADR-0058). A window whose class has `CS_HITTEST` is first sent `WM_HITTEST` (mp1 = the point in its coordinates, mp2 = 0) when the message is read: `HT_TRANSPARENT` passes it to the windows beneath, `HT_DISCARD` drops it, `HT_ERROR` drops it but still activates the frame of a press; `WinDefWindowProc` answers `HT_ERROR` for a disabled window, else `HT_NORMAL`. A mouse move right behind a move not yet read replaces it. `WinQueryQueueStatus(HWND_DESKTOP)` returns the `QS_*` kinds waiting for the calling thread (posted messages, input, `WM_PAINT`, `WM_TIMER`, `WM_SEMn`, messages sent from other programs) in the high word and those added since its previous call in the low word. Unverified: statics letting the pointer through, no alarm for `HT_ERROR`, only `WinQueryQueueStatus` resetting the low word.

**Text layout and character attributes.** A presentation space carries an angle (`GpiSetCharAngle`: the baseline runs towards the `GRADIENTL`; (0, 0) restores the default (1, 0)), a shear (`GpiSetCharShear`: the characters' vertical strokes run towards the `POINTL`; `y` = 0 fails with `PMERR_INV_CHAR_SHEAR_ATTR`, a negative `y` turns the characters upside down), a direction (`GpiSetCharDirection`: `CHDIRN_LEFTRIGHT`, `RIGHTLEFT`, `TOPBOTTOM`, `BOTTOMTOP`; `CHDIRN_DEFAULT` = left to right), extra spacing (`GpiSetCharExtra` adds a FIXED amount to every character, `GpiSetCharBreakExtra` to the space), an alignment (`GpiSetTextAlignment`: `TA_LEFT` / `TA_CENTER` / `TA_RIGHT` and `TA_TOP` / `TA_HALF` / `TA_BASE` / `TA_BOTTOM` about the start point; "normal" starts the string at the start point in its direction, "standard" is left (right for right-to-left) and bottom (top for top-to-bottom)) and a character mode (`GpiSetCharMode`, stored only), each with its query. `GpiCharString`, `GpiCharStringAt`, the current-position advance, `GpiQueryTextBox` (corners in `TXTBOX_*` order — top left, bottom left, top right, bottom right, concatenation point — relative to the start point, rotated, sheared and aligned like the drawn string) and the calls below all follow them. Rotated and sheared characters are rasterised from the transformed glyph outlines. Right-to-left text places each character left of the previous one; top-to-bottom and bottom-to-top text stacks the characters one line height apart, centred on the line through the start point (which is the top / bottom centre of the first character cell). `GpiCharStringPos` / `GpiCharStringPosAt` take `CHS_VECTOR` (an increment per byte replaces the widths and the extra spacing; a DBCS character moves by the sum of its two bytes' increments), `CHS_OPAQUE` (the rectangle, exclusive at the right and top, is first filled with the background colour), `CHS_CLIP` (the string is clipped to the rectangle), `CHS_UNDERSCORE`, `CHS_STRIKEOUT` and `CHS_LEAVEPOS` (the current position stays); other bits fail with `PMERR_INV_CHAR_POS_OPTIONS`, a missing rectangle with `PMERR_INV_RECT`. `GpiQueryCharStringPos` / `GpiQueryCharStringPosAt` return the position of each byte's character (both bytes of a DBCS character get its origin) and the concatenation point, `lCount` + 1 points, without moving the current position. `GpiQueryWidthTable` returns the advance, extra spacing included, of up to 65 536 code points in the presentation space's codepage (above 0xFF a DBCS pair, lead byte high; one that is no valid pair has width 0). Positions are in the presentation space's pels; the strings of all these calls are cut at 4096 bytes.

**Regions and clipping.** A region (`GpiCreateRegion`, `GpiSetRegion`) is the union of rectangles that include their left and bottom edges and exclude the right and top ones, in the presentation space's pels; `GpiCombineRegion` (`CRGN_OR` / `COPY` / `XOR` / `AND` / `DIFF`; the destination may be a source), `GpiQueryRegionBox` (a null region gives left = right, bottom = top), `GpiQueryRegionRects` (`RGNRECT` paging from `ircStart`, at most `crc`, the four `RECTDIR_*` orders, optionally cut to a bound; `crcReturned` reports how many), `GpiPtInRegion`, `GpiRectInRegion`, `GpiOffsetRegion` and `GpiEqualRegion` report `RGN_NULL` / `RGN_RECT` / `RGN_COMPLEX`. `GpiPaintRegion` fills a region with the area pattern (both colours by the foreground mix); `GpiFrameRegion` paints the pels less than `cx` / `cy` inside its boundary. `GpiSetClipRegion` selects a clip region and returns the old one, which is the application's to destroy; while selected only the clip calls may change it (`PMERR_REGION_IS_CLIP_REGION`, another PS: `PMERR_HRGN_BUSY`) and it is destroyed with the presentation space. `GpiIntersectClipRectangle` / `GpiExcludeClipRectangle` take an inclusive rectangle and create a clip region when there is none, `GpiOffsetClipRegion` moves it, `GpiQueryClipBox` reports the inclusive bounds of everything that clips (right < left when nothing is left). Every drawing call through the presentation space — GPI primitives, text, areas, paths, `GpiBitBlt` / `WinDrawBitmap`, `WinFillRect`, `WinDrawText`, `WinDrawBorder` — keeps only the pels inside its clip region and clip path; `GpiQueryPel` is not clipped. At most 16384 rectangles per region (more fails with `PMERR_INSUFFICIENT_MEMORY`), 16384 regions, coordinates within ±2²⁷.

**Areas, paths, polygons and curves.** Between `GpiBeginArea` and `GpiEndArea` (or `GpiBeginPath` and `GpiEndPath`) lines, polylines, arcs, curves and boxes build figures instead of drawing (`GpiMove` starts a new one; text draws nothing). `GpiEndArea` fills them as one area by `BA_ALTERNATE` or `BA_WINDING` in the pattern and colours of `GpiBeginArea` time, with the boundary pels (`BA_INCL`) or without the bottom and right edges (`BA_EXCL`), and draws the boundary lines for `BA_BOUNDARY`. **Coordinate spaces.** World coordinates pass through the model transform (`GpiSetModelTransformMatrix`), the viewing transform (`GpiSetViewingTransformMatrix`), the default view matrix (`GpiSetDefaultViewMatrix`) and the page viewport to device pels. Matrices are `MATRIXLF`s (FIXED scale / rotation, LONG translation; `lCount` 0–9 elements, the rest from the identity; elements 3, 6, 9 must be 0, 0, 1) combined by `TRANSFORM_REPLACE`, `ADD` (existing first) or `PREEMPT` (new first); a result beyond the FIXED range fails with `PMERR_COORDINATE_OVERFLOW`. `GpiTranslate`, `GpiScale` and `GpiRotate` (degrees, counter-clockwise, about a centre) update a `MATRIXLF` in memory. ## Guest Memory Layout

All addresses are guest physical (GPA = GVA in Warpine's flat model):

| Address | Size | Purpose |
|---------|------|---------|
| `0x00010000` – `0x00FFFFFF` | — | The program area: a 32-bit program's objects, which must lie wholly inside it and not overlap (ADR-0094) |
| `0x00100000` | — | NE (16-bit) segment base |
| `0x00F00000` | — | NE API thunk stubs |
| `0x01000000` | 21,504 B | LX API thunk stub area (`MAGIC_API_BASE`, `STUB_AREA_SIZE`) |
| `0x010003FE` | 1 B | PM callback return trap |
| `0x010003FF` | 1 B | Exit trap address |
| `0x01800000` | 256 KB | The system area (ADR-0094): Warpine's own structures, outside every program |
| `0x01800000` | 49,200 B | GDT (6150 entries: 6 fixed + 4096 data tiles + 2048 code tiles) |
| `0x0180D000` | 256 B | IDT (32 exception vectors) |
| `0x0180D800` | — | IDT handler stubs |
| `0x01810000` | 4 KB | Thread Information Block (TIB) — thread 1 |
| `0x01811000` | 4 KB | Process Information Block (PIB) |
| `0x01812000` | 4 KB | Environment string block |
| `0x0181F000` | 4 KB | The thread-local page (`TLM_PAGE`, ADR-0088) |
| `0x01820000` | 72 B | `GINFOSEG` (global information segment, a tile of its own, ADR-0040) |
